CHAPTER 01

시작하기 — Orca란 무엇이고 어떻게 설치·설정하나

Orca는 여러 AI 코딩 에이전트를 한 화면에서 나란히 돌리는 데스크톱 앱입니다. 이 장에서는 Orca가 어떤 도구인지, 설치와 첫 실행, 세 에이전트를 동시에 경주시키는 첫 세션, 알림·설정·개인정보, 그리고 문제가 생겼을 때 고치는 방법까지 한 번에 훑습니다.

1. Orca란?

Orca는 여러 AI 코딩 에이전트를 나란히 실행하는 데스크톱 앱, ADE(에이전트용 개발 환경 — 코드 편집·실행·검토를 에이전트와 함께 한곳에서 하는 프로그램)입니다. AI 코딩 에이전트(말로 시키면 스스로 코드를 고치는 AI 프로그램)를 여러 개 동시에 부리는 “작업 지휘실”이라고 보면 됩니다. 핵심은 “작업 하나 = 독립된 작업 공간 하나”라는 점입니다. 작업마다 다음 세 가지가 따로 주어집니다.

자기만의 워크트리(git worktree)

같은 저장소(프로젝트 파일과 변경 기록을 담은 폴더)를 폴더만 하나 더 만들어 다른 브랜치로 꺼내 둔 사본입니다. 에이전트끼리 서로의 파일을 덮어쓰지 않습니다.

자기만의 에이전트 터미널

Claude Code, Codex, Cursor CLI 같은 에이전트가 그 워크트리 안에서 실행됩니다. 터미널(글자로 명령을 입력하는 검은 창)에서 돌아갑니다.

자기만의 브라우저 탭

작업별로 웹 화면을 따로 띄워 결과를 확인할 수 있습니다.

쉬운 말로 풀면

git(코드 변경 이력을 저장·관리하는 도구)은 코드의 “저장 기록장”입니다. 브랜치(branch)(원래 코드에서 갈라져 나온 별도의 작업 줄기)는 “원본을 건드리지 않고 따로 고쳐 보는 갈림길”이고, 워크트리(worktree)(한 저장소의 브랜치를 별도 폴더에 동시에 꺼내 두는 git 기능)는 그 갈림길마다 책상을 하나씩 더 놓아 주는 것이라고 생각하면 됩니다. 책상이 따로 있으니 세 명(에이전트)이 동시에 일해도 서류가 섞이지 않습니다. 그래서 작업을 바꿀 때마다 변경을 잠시 치워 두는 stash(고치던 것을 임시 보관함에 넣기)나 브랜치를 이리저리 바꾸는 번거로움이 없습니다.

언제 Orca를 쓰면 좋은가

  • 같은 버그를 에이전트 셋에게 동시에 시켜 보고 가장 잘한 쪽을 고르고 싶을 때
  • AI가 만든 diff(파일이 어떻게 바뀌었는지 줄 단위로 보여 주는 비교 결과)를 내보내기 전에 꼼꼼히 검토하고 싶을 때
  • 이미 Claude Code, Codex, Cursor CLI 요금을 내고 있고, 이들을 한곳에서 지휘하고 싶을 때
  • 에이전트를 다른 컴퓨터에서 돌리고 싶을 때 — SSH(다른 컴퓨터에 암호화된 통로로 접속하는 방법), 직접 운영하는 Orca 서버, 필요할 때만 켜는 VM(클라우드에 빌려 쓰는 가상 컴퓨터) — 그러면서도 화면은 그대로 쓰고 싶을 때

누구를 위한 도구인가

Orca는 이미 코드를 직업으로 쓰는 사람이 AI를 “대체재”가 아니라 “지렛대”로 쓰도록 설계됐습니다. diff를 읽고, 커밋(변경 내용을 하나의 저장 단위로 기록하는 것)을 신경 쓰고, 워크트리를 깔끔하게 관리하는 사람을 전제로 합니다. 코드를 몰라도 되는 노코드(no-code) 도구를 찾는다면 Orca는 그런 도구가 아닙니다.

Orca가 아닌 것
  • AI 모델이 아닙니다. 이미 쓰는 에이전트를 실행할 뿐입니다. Claude, Codex, OpenCode 구독은 본인 것을 가져옵니다.
  • git을 대체하지 않습니다. 모든 워크트리는 진짜 git worktree입니다. 언제든 터미널에서 그 폴더로 들어가(cd(폴더 이동 명령)) 평범한 git 명령을 써도 됩니다.
  • 서버를 빌려주는 서비스가 아닙니다. VPS(월세로 빌리는 인터넷 서버 컴퓨터) 같은 상품을 팔지 않습니다. 기본은 내 컴퓨터에서 돌고, 다른 컴퓨터를 쓰더라도 내가 관리하는 기기·클라우드 계정(SSH 대상, 직접 운영하는 Orca 서버, Cloud VM/워크트리별 환경)을 씁니다.
다음 순서로 읽으세요

설치 → 첫 3-에이전트 세션(공식 문서가 “가장 중요한 페이지”라고 부르는 부분) → 노트북 밖에서 돌리고 싶어지면 실행 방식(Ways to run).

2. 설치

Orca는 보통 프로그램처럼 다운로드 → 더블클릭 → 설치하면 끝입니다. 공식 사이트의 Send download link(다운로드 링크 보내기)로 내 메일에 링크를 보내 두고, 설치할 컴퓨터에서 열 수도 있습니다. 내 운영체제 탭의 첫 줄만 읽으면 됩니다.

다운로드 → 더블클릭 → 설치. Apple Silicon(M1 이후 칩)용과 Intel용 중 내 Mac에 맞는 것을 받습니다. 첫 실행 때 macOS가 “정말 열까요?” 하고 물으면 열기를 누르면 됩니다.

다운로드 → 더블클릭 → 설치. 설치 프로그램(installer)을 받아 실행합니다.

다운로드 → 더블클릭(또는 설치) → 실행. 자동 업데이트를 원하면 AppImage(설치 없이 파일 하나로 실행되는 형식)를 고르세요.

예전 버전은 GitHub Releases 페이지에서 언제든 받을 수 있습니다. 지금 업데이트가 마음에 안 들면 이전 버전으로 돌아가도 됩니다.

첫 실행 때 일어나는 일

① 홈 폴더 접근 권한 요청 — 저장소(repo)를 추가할 수 있도록 홈 폴더(내 사용자 이름으로 된 기본 폴더) 접근을 물어봅니다. 허용하면 됩니다.

② 기존 설정 가져오기 제안 — ~/.claude, ~/.codex, Ghostty 터미널 설정이 있으면 가져올지 물어봅니다. (~는 내 홈 폴더라는 뜻입니다.) 처음 쓰는 사람은 가져올 것이 없으니 넘어가면 됩니다.

③ 빈 시작 화면 — 아무것도 없는 랜딩 화면이 나오고, 여기서 첫 저장소를 추가합니다.

업데이트: 안정판과 RC

Orca는 기본적으로 자동 업데이트되며 stable(안정) 채널을 따라갑니다. 초보자는 아무것도 바꾸지 않아도 됩니다. 안정판은 검증을 거친 버전이고, RC(release candidate, 출시 후보 — 새 기능이 먼저 들어간 시험판)는 거의 매일 나오기도 합니다.

4. 첫 3-에이전트 세션

시작 전 준비물 — 이 둘이 없으면 1단계에서 막힙니다
  1. AI 코딩 에이전트 1개 설치·로그인. Orca는 AI 모델을 주지 않고, 내가 이미 쓰는 에이전트(Claude Code, Codex 등)를 돌립니다 — 그 에이전트의 구독(대부분 유료)은 직접 준비해야 합니다. 에이전트를 설치한 뒤 아무 터미널에서 한 번 로그인해 두면, Orca가 그 로그인 정보를 자동으로 가져다 씁니다. 아래 예시처럼 세 종류를 비교하려면 각 에이전트마다 이 준비가 필요합니다.
  2. git 저장소 폴더 1개. 1단계에서 고를 “프로젝트 폴더”는 git으로 관리되는 폴더(저장소)여야 합니다 — Orca의 워크트리는 모두 진짜 git 워크트리이기 때문입니다. 그런 폴더가 없다면 팀의 개발자에게 쓸 저장소를 받아 내 컴퓨터에 받아 두거나(clone(서버의 저장소를 내 컴퓨터로 복사해 오기)), 저장소 주소(clone URL)로 추가하는 방법을 물어보세요.

공식 문서가 “가장 중요한 페이지”라고 부르는 흐름입니다. 빈 앱에서 시작해 5분 안에 같은 작업을 에이전트 셋에게 동시에 시켜 보고, 그중 가장 잘한 것으로 PR(Pull Request — “내 변경을 원본에 합쳐 주세요”라는 요청서)을 냅니다. 아래 그림에서 빨간 테두리가 깜빡이는 곳을 차례로 누르면 됩니다.

1. 저장소 추가 — Add Repo 누르기: 사이드바의 Add Repo를 누르고 내 컴퓨터에 있는 프로젝트 폴더를 고릅니다.

Orca는 그 폴더의 git 상태를 읽고 기본 브랜치를 기준 브랜치(base ref(저장소의 기본 기준 — 보통 서버에 있는 원본 줄기 origin/main))로 잡습니다. 새 워크트리는 기본적으로 여기서 갈라져 나옵니다. 기준 브랜치는 나중에 저장소 설정에서 바꿀 수 있습니다.

2. 워크트리 만들기 — + 누르고 이름 적기: 저장소 이름 옆 +를 누르고 작업 이름을 적습니다(예: fix-login-race). 비워 두면 Orca가 해양 생물 이름을 붙여 줍니다.

  • 화면에는 Workspace(워크스페이스 — 워크트리와 같은 것)라는 말도 나옵니다. 원클릭 Workspace 실행기(launcher)가 열리고, 기본 에이전트가 미리 선택돼 있습니다(Settings → Agents에서 변경). 빈 터미널만 열 수도 있습니다.
  • 출발점(start-from ref(이 새 워크트리가 갈라져 나오는 지점))은 보통 그대로 둡니다. 대개 기준 브랜치와 같은 기본값 origin/main은 “인터넷 서버(GitHub 등)에 있는 원본 줄기”라는 뜻입니다. 원하면 다른 브랜치나 커밋에서 시작해도 됩니다.

3. 에이전트 고르기 — 선택 상자에서 고르기: 새 워크트리에 터미널이 열리고 에이전트 선택 상자가 보입니다. Claude Code, Codex, Cursor CLI 등을 고르면 됩니다.

Orca가 올바른 작업 폴더에서 그 에이전트의 CLI(글자 명령으로 쓰는 프로그램)를 실행하고, 내 구독 자격 증명(내가 이미 결제·로그인한 계정 정보)을 넘겨줍니다. 그래서 시작 전 준비물 ①대로 터미널에서 한 번 로그인해 두었다면 Orca 안에서 따로 로그인할 필요가 없습니다.

4. 세 에이전트 경주 — 사이드바에 워크트리 3개: 2~3단계를 두 번 더 반복해 워크트리를 셋으로 만들고, 세 곳에 똑같은 부탁(프롬프트)을 붙여 넣습니다.

브랜치 셋, diff 셋, 프롬프트 하나. 이제 일하게 둡니다.

5. 창을 셋으로 나누기 — 탭을 가장자리로 끌기: 워크트리의 탭을 다른 창(pane)의 오른쪽이나 아래쪽 가장자리로 끌어다 놓으면 화면이 분할됩니다.

세 에이전트가 일하는 모습을 동시에 지켜볼 수 있습니다.

6. 승자 고르기 → diff 검토 → 내보내기: 에이전트들이 멈추면 각 워크트리의 diff 화면을 엽니다. Annotate AI Diff로 줄마다 의견을 달아 가장 잘한 에이전트에게 돌려보내고, 다 되면 Commit(저장)과 Push(내 컴퓨터의 저장 기록을 인터넷 서버에 올리기)를 Orca 안에서 바로 합니다.

코드를 못 읽어도 “가장 잘한 것” 고르는 법
  • 결과 화면 비교 — 워크트리마다 있는 브라우저 탭에서 결과를 직접 눌러 보고, 내가 부탁한 대로 동작하는 쪽을 고릅니다.
  • 바뀐 줄 수 — diff 화면 위쪽 작은 표시(칩)에 더한 줄·지운 줄 수가 나옵니다. 결과가 비슷하면 덜 바꾼 쪽이 검토하기 쉽습니다.
  • 자동 검사 통과 여부 — PR을 올린 뒤 Checks 패널에서 검사(CI)가 통과했는지 봅니다. 셋의 결론이 같으면 아마 정답입니다.

자세한 검토 순서는 6장 레시피: AI diff를 줄 단위로 리뷰하기를 보세요.

나머지 두 워크트리는 클릭 한 번으로 지울 수 있고, 그 브랜치도 함께 지워집니다.

레시피: 같은 작업으로 에이전트 셋 경주시키기

같은 작업을 여러 에이전트에게 병렬로 시키는 것은 Orca의 “필살기”입니다. 정리하면 다음과 같습니다.

  1. 같은 출발점에서 워크트리 3개같은 출발점(start-from ref)에서 fix-bug, fix-bug-2, fix-bug-3을 만듭니다.
  2. 서로 다른 에이전트각각 Claude Code, Codex, Cursor CLI를 띄웁니다.
  3. 같은 프롬프트세 곳에 똑같이 붙여 넣습니다.
  4. 창 분할탭을 가장자리로 끌어 일하는 모습을 함께 봅니다.
  5. diff 검토끝나면 각 diff를 보고, 승자에게 Annotate AI Diff를 씁니다. 승자는 결과 화면·바뀐 줄 수·검사 통과로 고릅니다(위 4절 6단계의 “고르는 법” 참고).
  6. 승자에서 PR이긴 워크트리에서 커밋·push·PR 열기.
  7. 패자 정리나머지 둘을 삭제합니다. 클릭 한 번이면 워크트리와 브랜치가 함께 지워집니다.

6. 알림과 받은 편지함(Notifications & Inbox)

Orca는 그냥 터미널이 아니라 에이전트를 돌리기 때문에, 에이전트가 진짜로 끝났는지 잠시 멈춘 건지 구분할 수 있습니다. 알림은 이 신호를 이용합니다. 에이전트 셋을 걸어 두고 자리를 비웠다가, 첫 번째가 끝나면 돌아오면 됩니다.

기능설명
Agent-finished pings(완료 알림)에이전트가 작업 중 → 쉬는 중으로 바뀌면 시스템 알림·소리·워크트리 칩(사이드바 워크트리 이름 옆에 붙는 작은 꼬리표 모양 표시)이 나갑니다. 한 에이전트가 끝난 직후 다른 에이전트가 끝나도 완료음은 빠지지 않고 울립니다.
Persistent bell(상시 벨)머리글 벨에 모든 워크트리의 읽지 않은 알림이 모입니다. 알림을 누르면 해당 워크트리·창으로 이동합니다.
Dock 배지 (macOS)같은 읽지 않음 개수가 Dock 아이콘에도 표시되어 Orca를 앞으로 꺼내지 않아도 알 수 있습니다. 해당 워크트리를 방문하면 사라집니다.
Mark unread(읽지 않음으로 표시)알림을 오른쪽 클릭해 다시 읽지 않음으로 만듭니다. 일단 확인했지만 나중에 다시 보고 싶을 때 씁니다.
Tuning(세부 조정)Settings → Notifications에서 종류별(system, sound, chip-only)로 끌 수 있습니다.

알림을 띄울 기기 고르기, 알림 소리 바꾸기, 채팅 화면에서의 예외 동작은 아래 접힌 상자에 있습니다.

한눈에 정리
  • Orca는 작업마다 워크트리·에이전트 터미널·브라우저 탭을 따로 주는 ADE(에이전트용 개발 환경)입니다. AI 에이전트의 구독은 직접 준비합니다.
  • 설치는 다운로드 → 더블클릭 → 설치. macOS·Windows·Linux를 지원합니다.
  • 실행 위치는 로컬 · SSH · 원격 Orca 서버 · Cloud VM(실험) 네 가지지만, 초보자는 화면과 일하는 곳이 같은 “로컬”만 알면 됩니다.
  • 첫 세션 전에 에이전트 1개 설치·로그인과 git 저장소 폴더를 준비합니다. 흐름은 저장소 추가 → 워크트리 → 에이전트 → 창 분할 → 변경 검토 → 내보내기입니다.
  • 같은 부탁을 에이전트 셋에게 시키고, 결과 화면·바뀐 줄 수·검사 통과로 승자를 고릅니다. 셋이 일치하면 아마 정답, 갈리면 어려운 지점이라는 신호입니다.
  • Agents 피드는 자리 비운 뒤의 따라잡기 화면이고, 에이전트가 끝나면 시스템 알림·소리·칩·벨·Dock 배지로 알려 줍니다.
  • 설정은 Cmd+,(macOS)로 열어 검색하며, 처음엔 General·Agents·Notifications만 보면 됩니다.
  • 텔레메트리는 익명이고 내용·경로를 보내지 않으며, Settings → Privacy에서 끕니다.

이 장의 나머지 소절과 🔧 세부는 완전 가이드 1장에 있습니다.

CHAPTER 02

Orca의 핵심 모델 — 워크트리·세션·화면 배치·복원·빠른 이동

Orca는 "작업 하나 = 폴더 하나(워크트리)"라는 생각 위에 세워져 있습니다. 이 장에서는 그 바탕이 되는 git 워크트리부터, 에이전트 세션의 상태 표시, 탭과 화면 분할, 앱을 껐다 켜도 그대로 돌아오는 세션 복원, 그리고 키보드로 순식간에 이동하는 검색창까지 Orca의 뼈대를 차례로 살펴봅니다.

먼저 알아 둘 것 — 브랜치·체크아웃·워크트리

Orca의 모든 것은 git(파일이 바뀐 기록을 저장하고 되돌리거나 합칠 수 있게 해 주는 버전 관리 도구)의 워크트리라는 기능 위에 있습니다. git을 처음 들어도 괜찮도록 세 단어부터 풀어 보겠습니다.

저장소(repo)

프로젝트 파일과 그 변경 기록 전체를 담은 상자입니다. 보통 컴퓨터의 폴더 하나로 보입니다.

브랜치(branch)

기록의 "갈래"입니다. main이라는 큰 줄기에서 feature/login 같은 가지를 뻗어, 원본을 건드리지 않고 따로 고쳐 볼 수 있습니다.

체크아웃(checkout)

어떤 브랜치의 파일들을 실제 폴더에 "꺼내 놓는" 일입니다. 폴더 안 파일은 지금 체크아웃된 브랜치의 모습입니다.

워크트리(worktree)

같은 저장소를 폴더 여러 개에 동시에 체크아웃하는 git 기능입니다. 폴더마다 다른 브랜치가 꺼내져 있습니다.

쉽게 비유하면 보통 방식은 책상 하나에서 숙제를 바꿔 가며 하는 것과 같습니다. 수학을 하다 국어로 바꾸려면 수학 책을 치워야(stash) 하죠. 워크트리는 숙제마다 책상을 따로 주는 것입니다. 수학 책상과 국어 책상이 나란히 있으니 치울 필요도 없고, 두 사람(두 에이전트)이 동시에 앉아도 서로의 공책을 건드리지 않습니다.

Orca는 워크트리 중심(worktree-native)으로 설계되었습니다. 한 체크아웃에서 브랜치를 바꾸고 stash(하던 변경을 잠시 치워 두기)하는 대신, 모든 기능 개발이나 버그 수정마다 git worktree로 저장소의 디스크 사본을 따로 만듭니다. 이것이 여러 에이전트를 병렬로 돌려도 안전한 이유입니다 — 에이전트끼리 서로의 파일을 건드리지 않습니다.

에이전트 세션과 상태 표시

에이전트 세션이란 워크트리 하나 안의 터미널 하나에서 도는 CLI 에이전트 하나입니다. CLI(마우스 대신 글자 명령으로 쓰는 프로그램) 에이전트는 Claude Code·Codex처럼 터미널 창 안에서 일하는 AI 도우미를 말합니다. Orca는 그 일생을 추적해서, 탭마다 들어가 보지 않아도 어떤 세션이 일하고 어떤 세션이 쉬는지 알려 줍니다. 모든 워크트리 카드 안에 상태 기호가 바로 보입니다.

기호뜻
Spinner(돌아가는 원)작업 중
? 주황 물음표나를 기다림(권한 요청 / 입력 필요). 사이드바 "Needs You" 개수도 같은 기호
초록 체크(대시보드) 또는 초록 점(사이드바)완료 / 조용히 활성
빨간 점막힘, 중단됨, 실패
회색 점쉬는 중(idle) — 끝난 뒤 오래 조용한 상태
표시 없음평범한 셸 — Orca가 아는 에이전트 CLI가 아님
시간 순서로 보면작업 중(돌아가는 원) → 끝나면 초록 + 🔔 끝남 알림 → 오래 두면 회색(쉬는 중 — 대시보드는 약 30분 조용하면 Idle 칸). 원문은 끝남 알림이 울리는 순간도 "idle"이라고 부르지만, 이 가이드는 그 순간을 "끝남", 오래 조용한 상태만 "쉬는 중"이라고 부릅니다.

Orca는 이 상태를 어떻게 알까요? 에이전트가 일하는 동안 "나 지금 일해요", "끝났어요" 하고 신호를 보내기 때문입니다. Claude Code, Codex 등 여러 에이전트가 이 신호를 내보냅니다.

상태 표시가 안 보이면그 세션의 에이전트 CLI를 Orca가 인식하지 못한 것입니다. 실행 파일 이름을 손으로 치지 말고 에이전트 콤보 상자로 시작하세요.

세션의 일생

Launch — 실행

콤보 상자에서 에이전트를 고르면 Orca가 CLI를 띄웁니다.

Work — 작업

에이전트가 보내는 신호로 상태 기호가 바뀝니다. 터미널 출력은 검색·복사가 됩니다.

끝남 (원문: Idle)

Orca가 "작업 중 → 조용해짐"으로 바뀌는 순간을 감지해 agent-finished(에이전트 끝남) 알림을 보냅니다. 그대로 오래 두면 회색 "쉬는 중"으로 보입니다.

Exit — 종료

에이전트 프로그램이 끝나면 탭에 Restart 칩이 나타납니다.

Restart 칩

에이전트가 끝나면(정상 종료든 충돌이든) 탭에 Restart 칩이 뜹니다. 한 번 누르면 같은 에이전트를 같은 작업 폴더에서 다시 살립니다.

실행 기본값 — 에이전트가 허락을 묻는가

에이전트는 파일을 고치거나 명령을 실행하기 전에 "이거 해도 될까요?" 하고 사람에게 물을 수 있습니다. Orca는 기본으로 묻지 않게 해서 에이전트를 띄웁니다. 매번 허락 창이 떠서 흐름이 끊기지 않게 하려는 것이고, 그래도 되는 이유로 워크트리 자체가 안전 울타리라는 점을 듭니다 — 에이전트는 자기 작업 폴더에서 일하고, 그 결과(변경점)는 합치기 전에 사람이 골라 담거나 버릴 수 있습니다.

"묻지 않게"는 에이전트를 켤 때 권한 생략 플래그(프로그램을 켤 때 뒤에 붙이는 옵션 글자. 여기서는 "확인 절차를 건너뛰어라"라는 뜻)를 미리 붙여 두는 방식으로 이루어집니다. 이 기본값은 Settings → Agents(설정 → 에이전트)의 Agent permissions(에이전트 권한)에서 바꿀 수 있습니다 — 플래그가 붙은 지금 상태가 Yolo(묻지 않음)이고, Manual(매번 묻기)로 바꾸면 허락 창이 돌아옵니다. 그 사이의 Auto는 지원하는 에이전트(Claude, Claude Agent Teams, Codex)가 일상적인 동작만 스스로 승인하는 모드입니다.

주의 — 에이전트가 묻지 않고 실행합니다기본 상태에서는 에이전트가 파일 수정·명령 실행을 확인 없이 합니다. Codex의 플래그는 이름대로 승인 절차와 샌드박스(프로그램이 하는 일을 가둬 두는 격리 공간)를 모두 건너뜁니다. 워크트리가 작업 폴더를 분리해 주긴 하지만, 원하지 않으면 위의 설정에서 Manual로 바꾸세요.

세션 복원 — 껐다 켜도 그대로

Orca를 닫았다가 다시 열면 작업 공간 전체가 되살아납니다. 어떤 브랜치에서 어떤 에이전트를 돌리고 있었는지 기억하는 건 사용자가 아니라 Orca의 일입니다.

비결은 데몬(화면 없이 뒤에서 계속 도는 프로그램)입니다. 데몬을 앱을 꺼도 뒤에서 터미널을 붙잡고 있는 관리인이라고 생각하면 됩니다. 에이전트가 일하는 터미널은 앱 창이 아니라 이 관리인이 쥐고 있어서, 창을 닫아도 일이 멈추지 않습니다. 다만 관리인도 컴퓨터 안에 사는 프로그램이라, 컴퓨터 자체가 꺼지면 함께 꺼집니다.

복원되는 것

  • 열린 워크트리 — 사이드바에 열려 있던 모든 워크트리
  • 탭과 분할 — 워크트리별 창 배치(중첩 분할 포함)와 초점이 있던 탭
  • 실행 중인 에이전트 — 데몬(관리인)이 터미널을 쥐고 있으므로 앱 창을 닫아도 Claude Code·Codex 등이 작업 도중 죽지 않습니다. 다음 실행 때 새로 띄우지 않고 살아 있던 그 에이전트에 그대로 다시 연결합니다.
  • 터미널 스크롤백(위로 굴려 다시 볼 수 있는 지난 출력) — 각 터미널의 출력 기록. Orca가 닫혀 있던 동안 나온 출력도 포함
  • 초점 워크트리와 탭 — 닫을 때 보던 화면으로 열림

복원되지 않는 것

  • 데몬은 컴퓨터와 운명을 같이합니다. 재부팅, OS 업데이트, 커널 패닉(운영체제가 심각한 오류로 갑자기 멈추는 일), 강제 전원 끄기처럼 기계 전체가 꺼지면 실행 중인 에이전트는 모두 끝납니다. 다음 실행 때 워크트리·탭·분할·마지막 스크롤백은 돌아오지만 에이전트 프로세스는 없습니다. 아무 탭에서 에이전트를 다시 실행해 이어 가세요.
  • Orca가 닫혀 있는 동안 데몬이 충돌해도 그 데몬이 붙잡던 세션은 같은 결과가 됩니다. 레이아웃과 스크롤백은 여전히 복원됩니다.

언제 복원이 일어나나 — 상황별로 보기

데몬 살아남음 → 에이전트 계속 실행. Cmd-Q(macOS)는 평소의 종료 방법이며, 에이전트는 뒤에서 계속 일합니다.

데몬 살아남음. 업데이트 설치를 위해 Orca가 다시 켜져도 에이전트는 영향받지 않습니다.

데몬 살아남음. Orca 자체가 충돌해도 데몬이 세션을 살려 두고, 다음 실행 때 다시 붙습니다.

데몬 죽음 → 에이전트 사라짐, 레이아웃은 복원. 노트북 재시작, OS 업데이트, 커널 패닉, 강제 전원 끄기. 워크트리·탭·분할·마지막으로 저장된 스크롤백은 돌아옵니다.

깨끗하게 새로 시작하고 싶다면복원은 매번 실행할 때마다 일어나며, "새 세션으로 열기" 같은 모드는 없습니다 — Orca는 항상 복원합니다. 그러니 종료 전에 워크트리를 직접 닫으세요. 닫은 워크트리는 닫힌 채로 남습니다.
한눈에 정리
  • 워크트리 = 같은 저장소를 작업마다 다른 폴더에 꺼내 둔 것. 에이전트끼리 파일을 밟지 않아 병렬 작업이 안전합니다.
  • 일생: Create → Work → Review → Ship → Archive/Delete. 생성은 백그라운드, 출발점은 보통 기준 브랜치(base ref), 필요하면 로컬 브랜치·커밋·원격 브랜치.
  • gitignore된 파일은 Shared Paths·orca.yaml(공유) / .worktreeinclude(복사)로 채웁니다.
  • 사이드바: 프로젝트별 묶음, 숨기기 필터, 고정·다중 선택·자식 칩. 일괄 삭제 시 미병합 브랜치는 보존 후 검토.
  • 상태 기호: 돌아가는 원(작업) · 주황 ?(나를 기다림) · 초록(완료) · 빨강(실패) · 회색(쉬는 중). 끝나면 초록 → 오래 두면 회색. 대시보드는 실험 기능.
  • 에이전트는 묻지 않는 모드(Yolo, 권한 생략 플래그)가 기본 — 원치 않으면 Settings → Agents의 Agent permissions에서 Manual(매번 묻기)로.
  • 탭은 끌어서 분할, 레이아웃은 워크트리별 저장. 데몬 덕에 앱을 꺼도 에이전트는 계속, 재부팅 땐 레이아웃만 복원.
  • Cmd-P 파일, + 탭·파일·URL·웹 검색, Cmd-J 워크트리·탭 이동(macOS 키).

이 장의 나머지 소절과 🔧 세부는 완전 가이드 2장에 있습니다.

CHAPTER 03

에이전트와 터미널 — 지원 에이전트, 채팅 UI, 기록, 사용량

Orca의 심장은 “코딩 에이전트를 터미널에서 돌리는 일”입니다. 이 장에서는 코딩 에이전트와 터미널이 무엇인지부터 시작해, Orca가 어떤 에이전트를 지원하고, 그 에이전트와 대화하는 두 가지 화면(터미널·채팅), 지난 대화 다시 열기, 쉬는 에이전트 재우기, 사용량 확인, 그리고 터미널의 모든 기능을 차례로 살펴봅니다.

코딩 에이전트와 터미널, 먼저 쉽게 알기

한 줄 비유 터미널은 컴퓨터에게 글자로 명령을 내리는 “채팅창”이고, 코딩 에이전트는 그 채팅창 안에 들어와 앉은 “AI 개발 도우미”입니다. 여러분이 “로그인 버튼 고쳐 줘”라고 쓰면, 에이전트가 직접 파일을 열어 보고, 고치고, 테스트 명령을 실행합니다.

터미널(Terminal)이란

마우스로 아이콘을 누르는 대신, npm test처럼 글자로 명령을 입력해 컴퓨터를 움직이는 창입니다. 명령을 받아 실행해 주는 프로그램을 셸(shell)(터미널 안에서 명령을 알아듣고 실행하는 프로그램. zsh, bash, PowerShell 등)이라 부릅니다. 이렇게 글자 명령으로 쓰는 프로그램을 CLI(Command Line Interface — 버튼 화면 없이 글자 명령으로 쓰는 프로그램)라고 합니다.

코딩 에이전트(Coding Agent)란

Claude Code, Codex 같은 AI가 들어 있는 CLI 프로그램입니다. 일반 챗봇과 달리 내 컴퓨터의 코드를 읽고, 파일을 고치고, 명령을 실행할 수 있습니다. 대부분 터미널 안에서 돌아가는 글자 화면, 즉 TUI(Terminal User Interface — 터미널 안에 글자로 그린 화면)를 갖고 있습니다.

핵심: Orca는 어떤 CLI 에이전트와도 함께 씁니다 Orca의 에이전트 선택 상자(agent combobox)는 결국 “터미널에 프로세스 하나를 띄우는” 일을 합니다. 그래서 목록에 없는 CLI 에이전트도 터미널에서 직접 실행하면 쓸 수 있습니다. 아래 표의 에이전트들은 여기에 더해 한 번 클릭으로 실행·설정되도록 미리 준비되어 있고, 일부는 더 깊은 기능(훅·상태·사용량·계정 전환)까지 지원합니다.

지원 에이전트 한눈에 보기

Orca의 기본 에이전트 선택기(built-in agent picker)에는 40여 개 에이전트가 미리 들어 있고, 모두 한 번 클릭으로 실행·설정됩니다. 그중 Orca 기능을 가장 많이 함께 쓰는 것은 깊은 통합이 붙은 아래 네 가지입니다. 어느 것을 고를지 모르겠다면 이 넷 중에서 시작하세요.

권한 기본값 — 왜 “확인 없이” 실행할까

코딩 에이전트는 보통 명령을 실행하기 전에 “이거 실행해도 될까요?”라고 매번 묻습니다. 예를 들어 파일을 지우거나 고치기 전에 “이 파일 지워도 될까요? [예/아니오]” 같은 확인 창을 띄우는 식입니다. Orca는 새로 실행하는 에이전트에 이 확인을 건너뛰는 옵션(flag(프로그램을 실행할 때 명령 뒤에 붙이는 켜기/끄기 스위치. 예: --yolo))을 미리 붙여 둡니다. 이런 “확인 없이 실행” 상태를 흔히 Yolo라고 부릅니다.

무엇이 위험할까

확인을 건너뛰면 에이전트가 파일을 고치거나 지우는 셸 명령도 여러분에게 묻지 않고 바로 실행합니다. 잘못된 명령이 있어도 중간에 막을 기회가 없습니다.

그래도 괜찮다고 보는 이유

에이전트는 원본이 아니라 자기 전용 워크트리(버려도 되는 작업용 복사본)에서 일합니다. 결과는 원본에 합치기(병합) 전에 사람이 보고 마음에 드는 것만 골라 담거나 통째로 버릴 수 있습니다.

용어 풀이 워크트리(worktree)(같은 프로젝트를 다른 폴더에 하나 더 펼쳐 놓은 “연습장”), 브랜치(branch)(프로젝트의 작업 갈래. main은 보통 기본 갈래), 체리픽(cherry-pick)(변경 중 마음에 드는 것만 골라 가져오기), 병합(merge)(작업 결과를 원본 갈래에 합치기).

권한 모드 바꾸기

  1. 전체 전환: Settings → Agents → Agent Permissions따로 손대지 않은(uncustomized) 터미널 에이전트 실행을 Yolo(확인 없이)와 Manual(매번 확인) 사이에서 한 번에 바꿉니다.
  2. Claude·Codex 새 세션의 기본값같은 곳에서 새 Claude·Codex의 터미널 세션과 구조화 채팅 세션 기본값도 정합니다. 이미 열린 채팅은 자기 모드를 그대로 유지합니다.
  3. 한 에이전트만 다시 묻게 하기Settings에서 그 에이전트의 기본 인수(arguments)나 환경 변수(environment)(프로그램이 시작할 때 읽어 가는 이름=값 설정)를 직접 고칩니다.

직접 고친 에이전트 설정은 전체 전환 스위치가 건드리지 않습니다. 구조화 채팅에서는 Manual · Auto · Yolo 세 가지 중 고를 수 있습니다(뒤의 네이티브 채팅 참고).

이미지 붙여넣기 (Codex)

업데이트된 로컬 Codex 채팅에서는 앱 메뉴나 클립보드로 이미지를 붙여넣습니다. 보내기 전 지울 수 있는 썸네일로 보이고, 눌러서 크게 볼 수 있습니다.

끊겨도 남는 초안

보내지 않은 글과 첨부는 호스트가 복원할 수 있으면 연결이 끊겼다 이어져도 남습니다. 같은 세션이 재연결되는 동안 이미 끝난 대화 기록도 화면에서 지워지지 않습니다(데스크톱·모바일 공통).

@ 파일 고르기

초안에 @를 치면 워크트리 파일을 골라 경로로 넣습니다. 모바일 Chat UI에도 같은 팝오버가 뜹니다.

찾기 · 인용 · 이전 프롬프트

Cmd+F(macOS) / Ctrl+F(Windows·Linux)로 채팅 내 검색. 답변 일부를 선택하고 Add to chat으로 작성창에 인용. 빈 초안에서 ↑/↓로 보냈던 모든 프롬프트를 불러옵니다.

숫자 키로 답하기

에이전트가 번호 선택지가 있는 질문을 하면 숫자 키로 답하고, 다음 질문으로 넘어갑니다.

분할 · 이동

새 채팅은 가능하면 첫 메시지로 이름이 지어지고, 탭 동작에서 이름을 바꿀 수 있습니다.

구조화 채팅은 맡긴 일·뒤에서 도는 일을 메인 턴 동안과 그 뒤에도 보이게 합니다.

  • 백그라운드 작업 띠: 뒤에서 도는 작업 수와 상태가 작성창 근처에 보입니다.
  • 계획 체크리스트: 에이전트가 세운 계획이 체크리스트로 보입니다.
  • 끝나면: 바뀐 파일과 추가/삭제 줄 수 요약이 나오고, 백그라운드에서 끝난 채팅에는 안 읽음 표시가 붙습니다.
  • 에이전트의 질문: 에이전트가 묻는 것은 질문 카드로 보이고, 카드의 Submit으로 답합니다.
  • 채팅 ↔ 터미널: 탭을 우클릭해 같은 대화를 채팅 화면과 터미널 화면 사이에서 바꿉니다.
  • Hand Off: 다른 에이전트에게 일을 넘깁니다.
  • 한도 후 자동 이어가기: 사용 한도에 걸려 멈춘 채팅을, 한도가 풀리면 Orca가 이어 가게 할 수 있습니다.

CHAPTER 04

워크트리별 내장 브라우저와 디자인 모드

Orca에는 워크트리마다 따로 쓰는 진짜 Chromium 브라우저가 들어 있습니다. 사람은 이 브라우저로 만든 화면을 확인하고, 에이전트는 글자 명령(CLI)으로 같은 브라우저를 조작합니다. 디자인 모드를 켜면 화면의 요소를 클릭하는 것만으로 “이걸 고쳐 줘”를 에이전트에게 전할 수 있습니다.

워크트리마다 하나씩 있는 브라우저

쉽게 말하면 워크트리(worktree)(같은 프로젝트를 여러 폴더로 펼쳐 놓고 폴더마다 다른 작업을 동시에 하게 해 주는 기능)는 “같은 프로젝트의 작업용 복사본 책상”이라고 생각하면 됩니다. Orca는 책상마다 브라우저를 한 대씩 따로 놓아 줍니다. A 책상에서 열어 둔 탭은 B 책상으로 옮겨 가면 보이지 않고, 다시 A로 돌아오면 그대로 남아 있습니다.

이 브라우저는 흉내만 낸 미리보기 창이 아니라 진짜 Chromium(Google Chrome의 바탕이 되는 공개 브라우저 엔진) 창입니다. 주소창, 방문 기록(history), 개발자 도구(DevTools)를 모두 갖추고 Orca의 한 pane(칸)(Orca 화면을 나눈 한 구역. 터미널·편집기·브라우저 등을 칸마다 띄움)에 들어 있습니다. 탭이 워크트리 단위로 묶이기 때문에, 지금 만들고 있는 앱의 화면이 다른 작업의 탭과 섞이지 않습니다.

  • 새 탭은 화면에 보이지 않아도 뒤에서 미리 로드되므로, 전환했을 때 주소·제목·이동 상태가 이미 준비되어 있습니다. 단, 재시작 후 되살린 탭 가운데 아직 보고 있지 않은 탭은 열어 볼 때 로드될 수 있습니다.
  • DevTools(개발자 도구) 버튼으로 현재 페이지를 검사합니다. 도구 창을 칸의 한쪽에 붙이거나(dock), 크기를 조절하거나, 공간이 부족하면 별도 창으로 떼어 낼(pop out) 수 있습니다.
  • 링크에 마우스를 올리거나 포커스를 주면 페이지 아래쪽에 목적지 주소가 표시됩니다.
  • 칸이 좁아지면 부가 도구는 overflow 메뉴(⋯)로 접히고, 이동 버튼·주소창·Cmd+F는 계속 쓸 수 있게 남습니다.
  • 터미널이나 채팅에서 연 링크는 그 링크를 준 칸 옆에 열립니다.
  • 에이전트가 브라우저를 쓰는 중이면 페이지 위에 에이전트 커서와 활동 배지가 나타납니다. 채팅에 있는 브라우저 링크를 누르면 그 페이지로 바로 이동합니다.

새 창·팝업이 열리는 규칙, HTML 미리보기와 브라우저 탭의 전환, 페이지에 포커스가 있을 때의 단축키 동작은 아래 접힌 상자에 있습니다.

원격 워크트리에서 화면 그리기

회사 서버 등 원격 컴퓨터에서 작업하지 않으면 이 절은 건너뛰세요.

왜 필요할까? 작업 폴더가 내 PC가 아니라 다른 컴퓨터(예: 회사 서버)에 있을 때가 있습니다. Orca에서는 이런 작업 공간을 Workspace(워크스페이스 — 워크트리와 같은 것)라고도 부르는데, 이 장에서는 “원격 워크트리”라고 하겠습니다. 이럴 때도 브라우저를 쓸 수 있고, 연결 방식은 두 가지입니다.

  • Remote Orca Server(Orca 원격 서버)와 짝지은(paired) 원격 워크트리 — 다른 컴퓨터에 Orca 서버를 띄워 내 Orca와 짝지은 경우
  • SSH(다른 컴퓨터에 안전하게 접속해 명령을 실행하는 방법) 원격 워크트리

짝지은 원격 서버에서는 기본적으로 화면은 내 PC에서 그리고, 웹사이트와 주고받는 인터넷 통신은 원격 컴퓨터를 거쳐 나갑니다. 그래서 키보드 입력·글자 선택·팝업은 내 PC에서 자연스럽게 동작하면서도, 웹사이트 입장에서는 원격 컴퓨터에서 접속한 것으로 보입니다. 브라우저 툴바의 호스트 표시(통신이 어느 컴퓨터를 거쳐 가는지 보여 주는 표시)로 확인할 수 있습니다.

Settings → Browser → Remote server workspaces(설정 → 브라우저 → 원격 서버 워크트리)에서 This device(이 기기)를 고르면 위 그림처럼 동작합니다(기본값). 입력·선택·팝업이 이 기기에서 자연스럽게 처리됩니다.

다만 이렇게 내 PC에서 그리는 페이지는 내 PC가 켜져 있어야 합니다. 에이전트가 이 페이지를 조작하는데 PC가 꺼지거나 잠들거나 연결이 끊기면 오류가 납니다.

같은 설정에서 Server (streamed)(서버, 스트리밍)를 고르면 페이지가 원격 서버에서 실행되고 화면만 내 PC로 전송됩니다. 내 PC가 연결되어 있지 않아도 돌아가므로, 오래 걸리거나 사람이 지켜보지 않는 자동화에 더 알맞습니다.

설정은 새 페이지에만 적용이미 열려 있는 페이지를 옮기지는 않습니다. 내 PC에서 그리려던 원격 페이지가 시작되지 못하면 Reopen on server(서버에서 다시 열기)를 눌러 마지막 주소로 서버 쪽 새 페이지를 열 수 있습니다. 이때 로그인 상태나 입력 중이던 양식 내용은 다를 수 있습니다.

SSH 원격 워크트리에서는 Browse through SSH workspace hosts(SSH로 접속한 컴퓨터를 거쳐 탐색) 설정이 브라우저의 인터넷 통신(주소 찾기 포함)을 SSH로 접속한 컴퓨터로 보낼지, 이 기기에서 직접 보낼지를 정합니다.

내 PC에서 그리는 원격 페이지에서 받은 다운로드는 원격 컴퓨터에 저장되고, 업로드할 파일도 먼저 그 컴퓨터에 옮겨 놓은 뒤 페이지에 전달됩니다.

디자인 모드(Design Mode)

디자인 모드는 Orca 브라우저를 “화면을 가리키면 그 부분의 코드로 이어지는” 도구로 바꿉니다. 켜고 나서 화면의 아무 버튼·글상자 같은 요소나 클릭하면, 그 요소의 정보가 에이전트 채팅에 첨부됩니다. 함께 가는 정보는 DOM(웹 페이지를 이루는 부품 구조), 계산된 CSS(그 부품에 실제로 적용된 색·글꼴·간격 같은 모양 값), 그리고 스크린숏입니다.

켜기

브라우저 툴바의 Design Mode 토글을 누릅니다. 마우스 커서가 요소를 고르는 도구(picker)로 바뀌고, 마우스를 올린 요소가 강조 표시됩니다. Annotate page element(페이지 요소에 메모 달기) 동작은 Settings → Shortcuts(설정 → 단축키)에서 원하는 키로 바꿀 수 있는 단축키로도 제공됩니다.

이것들이 첨부 하나로 묶여 지금 쓰고 있는 에이전트 창에 들어가고, 사용자는 바꾸고 싶은 내용을 글로 적기만 하면 됩니다.

디자인 모드 순환

에이전트가 코드를 고치면 핫 리로드(코드를 고치면 화면이 저절로 새로 고쳐지는 기능)로 브라우저 화면이 바로 바뀝니다. 다시 클릭해 확인하고, 맞을 때까지 반복합니다.

페이지 메모 모아 보내기(annotation tray)

요소마다 메모를 달아 두었다가 한꺼번에 보낼 수도 있습니다.

  • 메모 트레이에 여러 개의 메모를 쌓아 두었다가 한꺼번에 에이전트에게 보낼 수 있습니다.
  • 메모 위에 마우스를 올리고 Edit(편집)을 누르면 그 자리에서 코멘트나 의도(intent)를 고칠 수 있고, 끝나면 Save(저장) 또는 Cancel(취소)을 누릅니다.
  • Send(보내기)와 Copy(복사)는 기본적으로 메모마다 짧은 요약만 담습니다. 메모에 이미지를 붙여 넣을 수도 있습니다.
  • 페이지 전체 세부 정보까지 보내려면 Send 메뉴에서 Include page details(페이지 세부 정보 포함)를 고릅니다. Orca는 이 선택을 그 브라우저 칸에 기억합니다.
  • 프롬프트가 전달되면 Orca는 보낸 메모를 페이지에서 지웁니다. 전달이 진행되는 동안 새로 추가하거나 고친 메모는 페이지에 남습니다.

레시피: 디자인 모드로 UI 버그 고치기

시작하기 전에이 레시피는 지금 만들고 있는 앱이 내 컴퓨터에서 실행 중이고, 그 화면을 이 브라우저에서 localhost 주소(내 컴퓨터 안에서 실행 중인 앱을 여는 주소. 예: localhost:3000)로 열어 둔 상태를 전제로 합니다. 앱이 실행 중이어야 코드를 고쳤을 때 화면이 저절로 새로 고쳐지는 핫 리로드(코드를 고치면 화면이 저절로 새로 고쳐지는 기능)가 동작합니다. 앱 실행은 에이전트에게 부탁해도 됩니다(예: “앱을 실행하고 열 주소를 알려 줘”).

디자인 모드는 “저 버튼 이상해 보여”에서 “고친 결과를 저장”까지의 과정을 1분 안쪽으로 줄여 줍니다.

1. 페이지 열기

그 워크트리의 브라우저 칸을 열고 버그가 있는 페이지로 이동합니다.

2. 디자인 모드 켜기

툴바의 Design Mode 토글을 켭니다.

3. 문제 요소 클릭

망가진 요소를 클릭합니다. 그 요소가 풍부한 첨부로 에이전트 채팅에 들어갑니다.

4. 원하는 수정 적기

예: “이 padding(안쪽 여백)이 너무 좁아. 위쪽 카드들과 같게 늘려 줘.”

5. 에이전트가 수정

에이전트가 코드를 고치면 핫 리로드(화면 자동 새로 고침)로 브라우저가 바로 바뀝니다.

6. 다시 클릭해 확인

요소를 다시 클릭해 확인합니다. 아직 틀리면 4단계부터 반복합니다.

7. 작업 저장 지점 만들기

맞게 되면 commit(지금까지 바꾼 내용을 기록에 한 덩어리로 저장해, 나중에 돌아올 수 있는 지점을 만드는 일)합니다.

왜 빠를까?

스크린숏을 직접 찍을 필요도, 페이지의 부품 구조(DOM)를 뒤질 필요도, 그 부품을 가리키는 주소(선택자, selector)를 복사할 필요도 없습니다. 에이전트는 사용자가 가리킨 바로 그 요소의 코드(HTML), 실제 모양 값(계산된 CSS), 잘라 낸 이미지를 받습니다. 사람 검토자라도 받고 싶어 할 바로 그 정보입니다.

한눈에 정리
  • 워크트리마다 진짜 Chromium 브라우저가 있고, 탭·스크롤 위치는 워크트리별로 저장·복원됩니다.
  • (macOS) Cmd+T 새 탭, Cmd+Shift+T 닫은 탭 복원, Cmd+F 찾기, Cmd+Option+B 오른쪽 분할 탭. Hard Reload는 캐시를 건너뜁니다.
  • 쿠키는 Chrome·Edge·Vivaldi·파일에서 가져오되 Google 로그인은 Orca 안에서 직접 해야 합니다.
  • 원격 워크트리는 기본적으로 화면은 내 PC, 인터넷 통신은 원격 컴퓨터를 거침. 사람이 지켜보지 않는 자동화엔 Server (streamed).
  • 링크 라우팅·Hold Shift…로 Orca/시스템 브라우저를 고르고, 확장은 실험 기능, 아티팩트 공유는 파일당 10 MiB(약 10MB)·같은 폴더의 사진 등 따로 불러오는 파일은 제외.
  • 프로필은 쿠키·저장소·캐시가 완전히 분리된 신원이며, 에이전트 명령도 활성 프로필을 따릅니다.
  • 디자인 모드: 요소 클릭 → HTML·CSS·스크린숏·소스 위치가 채팅에 첨부 → 에이전트 수정 → 핫 리로드(화면 자동 새로 고침) → 다시 확인 → commit(저장 지점 만들기).
  • 에이전트는 마우스 대신 화면 요소에 번호표를 붙이고, 그 번호표를 보고 누르거나 입력합니다. 같은 브라우저·같은 탭이라 하는 일을 화면에서 지켜볼 수 있습니다.

이 장의 나머지 소절과 🔧 세부는 완전 가이드 4장에 있습니다.

CHAPTER 05

파일 편집과 보기 — 에디터, 마크다운, 뷰어, 파일 탐색기

Orca 안에서 파일을 직접 고치고, 문서를 보기 좋게 다듬고, PDF·이미지·영상·표·노트북을 열어 보고, 파일을 찾아 에이전트에게 건네는 방법을 다룹니다.

한눈에 보는 편집 영역

Orca의 각 워크트리(에이전트마다 따로 꺼내 주는 프로젝트 폴더의 작업용 복사본)에는 왼쪽에 파일 탐색기, 가운데에 파일을 여는 탭이 있습니다. 파일을 열면 종류에 맞는 화면이 자동으로 열립니다. 코드는 Monaco 에디터, 마크다운 문서는 리치 에디터, PDF·이미지·영상·표·노트북은 전용 뷰어로 열립니다.

쉽게 말하면Orca는 "모든 기능이 다 든 개발 도구(IDE)"보다는 "잘 만든 메모장 + 각종 미리보기 창"에 가깝습니다. 원문도 Orca가 일부러 editor-first, not IDE-first(IDE보다 에디터 우선)라고 말합니다. 그래서 코드의 실수를 찾아 주는 검사 도구(원문 용어로 타입 검사기·린터)는 Orca에 들어 있지 않습니다. 문서의 맞춤법 검사기 같은 이 도구는 터미널(명령을 글자로 입력하는 창)에서 따로 실행하면 됩니다.

코드 에디터(Monaco)와 자동 저장

Orca의 코드 에디터는 Monaco입니다. VS Code(널리 쓰이는 코드 편집 프로그램)가 쓰는 바로 그 편집기라서 VS Code를 써 본 사람은 거의 같은 감각으로 쓸 수 있고, 여기에 Orca만의 몇 가지 조정이 더해졌습니다.

자동 저장과 "디스크에서 바뀜" 배너

무엇인가 — 파일은 저절로 저장됩니다. 다른 곳을 클릭해 에디터에서 벗어날 때, 그리고 잠깐 타이핑을 멈추고 있을 때 저장됩니다. 그래서 다른 편집기에서 흔히 보는 "아직 저장 안 됨" 표시 점이 없습니다. 평소에는 저장 안 된 변경이 생기지 않기 때문입니다.

왜 검사가 필요한가 — Orca에서는 사람과 에이전트가 같은 파일을 만질 수 있습니다. 그래서 Orca는 저장하기 직전에 "이 탭이 마지막으로 파일을 읽거나 저장한 뒤에 디스크의 파일이 바뀌었나?"를 확인합니다.

1. 평소처럼 편집

파일을 고치고 다른 탭이나 터미널을 클릭하면(또는 잠시 손을 멈추면) 자동 저장됩니다.

2. 그 사이 에이전트가 같은 파일을 수정

탭이 마지막으로 읽거나 쓴 뒤 디스크의 파일이 바뀌었습니다. 다음 저장 직전 Orca가 이를 알아챕니다.

3. 자동 저장 멈춤 + changed-on-disk(디스크에서 바뀜) 배너

배너가 뜨고 자동 저장이 멈춥니다. 내가 친 내용은 탭 안에 그대로 남아 있어 사라지지 않습니다.

4. 네 가지 중 선택
  • compare(비교) — 디스크 쪽 내용과 내 편집을 비교합니다.
  • reload(다시 불러오기) — 디스크 쪽 내용으로 탭을 새로 고칩니다.
  • keep your edits(내 편집 유지) — 탭의 내용을 그대로 둡니다.
  • overwrite(덮어쓰기) — 디스크 쪽 내용을 내 편집으로 바꿉니다. 내가 직접 골라야만 일어납니다.

SSH로 접속한 원격 컴퓨터의 파일을 열 때만 해당하는 내용(같은 경로의 파일이라도 컴퓨터마다 편집 내용을 따로 보관)은 아래 접힌 상자에 있습니다.

마크다운 문서 에디터(리치 에디터)

마크다운(#를 붙이면 제목, -를 붙이면 목록이 되는 식으로, 간단한 기호로 서식을 다는 글 문서 형식. 확장자 .md) 파일은 기본으로 리치 에디터로 열립니다. 기호 대신 완성된 모양(제목은 큰 글씨, 목록은 점)을 보면서 바로 고치는 방식이라 워드 프로그램과 비슷합니다. 슬래시 메뉴, 도구 모음, 이미지·코드 미리보기, 내부 링크 자동완성을 갖추고 있습니다.

  • Cmd+Shift+M (macOS) — 기호가 그대로 보이는 원문(raw) 에디터와 리치 에디터를 언제든 오갑니다.
  • 운영체제의 "다음으로 열기" — Orca는 macOS·Windows·Linux에서 마크다운 파일의 Open With(다음으로 열기) 목록에 자신을 등록합니다. 원래 쓰던 기본 편집기를 바꾸지는 않습니다. 리치 에디터로 열고 싶을 때 그 메뉴에서 Orca를 고르면 됩니다.
큰 파일과 특수 문법

  • 리치 에디터가 망가뜨리지 않고 지킬 수 없는 마크다운 문법을 쓴 파일은 원문 에디터에 머뭅니다.

파일 탐색기

파일 탐색기는 각 워크트리 왼쪽에 있으며 디스크의 파일을 실시간으로 따라갑니다. 만들기·이름 바꾸기·삭제·이동이 모두 실제 파일에 그대로 적용되고, 에이전트처럼 바깥에서 생긴 변경도 바로 나타납니다. 정렬은 폴더 먼저, 그다음 파일이며, 이름 속 숫자를 수로 이해하는 순서(9, 99, 100)입니다.

git 상태 색 — 파일 이름 색이 다른 이유

탐색기의 파일 이름은 git(파일의 변경 이력을 기록하는 도구)이 보는 상태에 따라 색이 다릅니다. 색만 봐도 "새로 만든 파일인지, 고친 파일인지"를 알 수 있습니다.

CHAPTER 06

리뷰와 배포 — diff 보기부터 PR·이슈 연동까지

에이전트가 코드를 고쳤다면 이제 사람이 꼼꼼히 확인하고, 저장(커밋)하고, 서버로 올리고(푸시), 동료에게 검토를 부탁(PR)할 차례입니다. 이 장은 그 과정을 Orca 안에서 한 번에 끝내는 방법과, GitHub·GitLab·Bitbucket·Jira·Linear 같은 바깥 서비스와 연결하는 방법을 다룹니다.

먼저 알아 둘 말: diff · 스테이징 · 커밋 · 푸시 · PR · CI

이 장에는 git 용어가 많이 나옵니다. 처음 보는 분도 따라올 수 있게 먼저 하나씩 풀어 보겠습니다. 바탕이 되는 말은 세 가지입니다. git(파일을 언제 누가 어떻게 바꿨는지 기록해 두는 도구), 브랜치(같은 프로젝트에서 갈라져 나온 독립된 작업 줄기 — 다른 작업과 섞이지 않음), 워크트리(브랜치 하나를 위한 별도 작업 폴더. Orca는 작업마다 하나씩 만듭니다).

학교 숙제로 비유하면
  • diff(차이) — 어제 원고와 오늘 원고를 나란히 놓고 빨간 펜(지운 부분)과 초록 펜(새로 쓴 부분)으로 표시한 것입니다.
  • 스테이징(staging) — 고친 것 중 “이번에 낼 부분”만 골라 봉투에 넣어 두는 것입니다. 명령으로는 git add입니다.
  • 커밋(commit) — 봉투를 봉하고 “무엇을 고쳤는지” 메모(커밋 메시지)를 붙여 내 서랍에 보관하는 것입니다. 아직 내 컴퓨터 안에만 있습니다.
  • 푸시(push) — 서랍 속 봉투를 학교 사물함(원격 저장소, 보통 origin이라 부르는 GitHub 같은 서버)에 갖다 넣는 것입니다.
  • PR(풀 리퀘스트) / MR(머지 리퀘스트) — “제 작업 좀 봐 주시고 괜찮으면 본 원고(main 브랜치)에 합쳐 주세요” 하는 검토 요청서입니다. GitHub·Bitbucket은 PR, GitLab은 MR이라고 부릅니다. 이 장에서는 둘을 묶어 호스팅 리뷰(hosted review)라고도 합니다.
  • CI(지속적 통합) / 체크(checks) — 요청서를 내면 자동 채점기가 돌아 테스트·검사를 해 주는 것입니다. GitHub에서는 GitHub Actions, GitLab에서는 파이프라인(pipeline)이 이 일을 합니다.
  • 머지(merge, 병합) — 검토가 끝난 작업을 본 원고에 합치는 것입니다.

여기에 몇 가지 용어를 더 알아 두면 뒤가 편합니다.

용어쉬운 뜻
GitHub · GitLab · Bitbucket코드를 올려 두고 여러 사람이 함께 검토하는 웹사이트. 위 그림의 “원격(학교 사물함)”이 바로 이런 곳입니다. Azure DevOps·Gitea도 같은 종류의 서비스입니다.
이슈(issue)할 일·버그 신고를 적은 카드. 엑셀 할 일 목록의 한 줄이라고 생각하면 됩니다. GitHub·Jira·Linear 모두 이슈를 다룹니다.
칸반(kanban) 보드“할 일 · 하는 중 · 끝남” 같은 칸에 포스트잇을 붙여 두고 칸에서 칸으로 옮기는 보드.
토큰(token)비밀번호 대신 쓰는 출입증 문자열. 서비스 설정 화면에서 만들어 Orca에 붙여 넣으면, Orca가 그 출입증으로 대신 들어갑니다. 필요 없어지면 언제든 폐기할 수 있습니다.
ref / start-from ref“어느 시점의 코드”를 가리키는 이름표(브랜치 이름, 커밋 번호 등). start-from ref는 워크트리를 만들 때 출발점으로 삼은 지점입니다.
base 브랜치PR이 최종적으로 합쳐질 대상 브랜치(보통 main).
hunk(헝크)diff 안에서 붙어 있는 변경 덩어리 하나. 파일 하나에 여러 hunk가 있을 수 있습니다.
upstream내 로컬 브랜치와 짝을 이루는 원격 브랜치. 처음 푸시할 때 정해집니다.
merge base(분기점)내 브랜치와 base 브랜치가 갈라진 지점.
rebase · amend · squash이미 만든 커밋 기록을 다시 쓰는 방법들(다른 지점 위로 옮기기 / 마지막 커밋 고치기 / 여러 커밋 합치기). 기록이 바뀌므로 원격과 어긋날 수 있습니다.
병합 충돌(merge conflict)두 쪽이 같은 줄을 다르게 고쳐서 git이 어느 쪽을 택할지 모르는 상태.
pre-commit hook커밋 직전에 저장소가 자동으로 돌리는 검사(코드 모양·실수 자동 검사). 실패하면 커밋이 막힙니다.

Diff viewer — AI가 만든 코드를 제대로 읽는 화면

무엇인가. Orca의 Diff viewer(차이 보기 화면)는 AI가 만든 코드를 “슬쩍 훑어보는” 용도가 아니라 진지하게 리뷰하도록 설계되었습니다. 모든 워크트리에는 자기 start-from ref와 비교한 diff가 기본으로 들어 있습니다.

왜 필요한가. 에이전트는 빠르게 많은 줄을 바꿉니다. 무엇이 바뀌었는지 정확히 보지 않고 커밋하면 버그도 함께 배포됩니다.

Annotate AI Diff — 코멘트를 모아 한 번에 돌려보내기

무엇인가. Annotate AI Diff는 에이전트가 만든 코드를 위한 Orca의 줄 단위 리뷰 순환입니다. AI가 만든 hunk의 아무 줄에나 코멘트를 남긴 뒤, 그 코멘트들을 한 묶음(batch)으로 에이전트에게 보내 고치게 합니다. 줄 번호를 복사해 붙이거나 다른 창으로 오갈 필요가 없습니다.

코멘트 남기기

  1. 줄 위에 마우스를 올립니다거터(줄 번호 옆 여백)에 +가 나타납니다. 여러 줄에 달고 싶으면 이웃한 줄들을 끌어서 고르거나, Shift를 누른 채 선택을 넓힙니다. Orca는 선택 범위를 그 hunk 안으로 제한하고, 고른 줄 범위를 라벨로 붙입니다.
  2. +를 클릭합니다또는 커서를 그 줄에 두고 c를 누릅니다.
  3. 의견을 씁니다마크다운(제목·목록·코드 표시 같은 간단한 서식 문법)을 쓸 수 있습니다.

묶음 보내기 (Send the batch)

리뷰를 다 했으면 diff 맨 위의 Send to agent(에이전트에게 보내기)를 누릅니다. Orca가 모든 코멘트를 줄 위치와 함께 하나의 프롬프트로 엮은 뒤, 그 워크트리에서 쓸 수 있는 에이전트 목록이 담긴 Send notes to 메뉴를 엽니다. 수정을 맡길 에이전트를 고르거나, 같은 메뉴에서 새 에이전트를 시작할 수 있습니다.

단축키를 직접 정해야 합니다Send Review Notes to Agent 동작은 다른 단축키 조합과 부딪치지 않도록 기본으로 단축키가 비어 있습니다. Settings → Shortcuts(설정 → 단축키)에서 지정하면 키보드로 보내기 메뉴를 열 수 있고, 에디터에 포커스가 있을 때도 동작합니다.

왜 묶어서 보내나요?

하나씩 보내면에이전트가 코멘트 하나 고치고, 다음 코멘트에 맞춰 또 바꾸고… 이리저리 흔들립니다.
묶어서 보내면피드백이 일관됩니다. 한 번 생각하고, 한 번에 고치므로 원하는 결과가 나올 확률이 훨씬 높습니다.

답하기 · 해결 처리 · 재리뷰

  • 에이전트가 고친 뒤에도 코멘트는 그 자리에 고정되어 남습니다. 고쳐졌는지 확인하는 체크리스트로 쓰면 됩니다.
  • Resolve(해결)를 누르면 그 코멘트 스레드가 접힙니다.
  • 해결하지 않은 코멘트는 Send를 다시 누를 때 다음 묶음에 포함됩니다.

커밋 · 푸시 · PR 만들기 — Orca를 떠나지 않고

Orca 안에서 커밋하고, 푸시하고, 리뷰(PR)까지 열 수 있습니다. 커밋 패널은 Diff viewer 바로 옆에 있으며, 가장 흔한 흐름인 리뷰 → 스테이징 → 커밋 → 푸시 → 다음 일에 맞춰 설계되어 있습니다.

  1. 스테이징diff에서 hunk 단위 또는 파일 단위로 스테이징합니다.
  2. 커밋 메시지 쓰기아래 패널에 직접 쓰거나, 스테이징한 변경을 바탕으로 Orca가 초안을 써 주길 원하면 Generate with AI(AI로 생성)를 누릅니다.
  3. CommitmacOS는 Cmd+Enter, Windows/Linux는 Ctrl+Enter. 단, 포커스가 Source Control에 있고 주 버튼이 Commit일 때 동작합니다.

저장소에 있는 pre-commit hook(커밋 직전에 코드 모양·실수를 자동으로 검사하는 장치)은 평소처럼 실행됩니다. hook이 실패하면 Orca가 그 출력을 그 자리에 보여 줍니다.

Fix with AI — 커밋이 실패했을 때실패 상세 화면에서 Fix with AI(AI로 고치기)를 누르면, 현재 워크트리에서 기본 에이전트가 시작되고 hook 출력·시도한 커밋 메시지·스테이징된 파일 목록을 넘겨받습니다. 에이전트는 고치라는 프롬프트만 받습니다. hook을 우회하거나, 커밋·푸시하거나, 리뷰를 열라는 요청은 받지 않습니다.

Push는 워크트리의 브랜치를 origin(원격, 학교 사물함)으로 올립니다. 처음 푸시할 때는 upstream(내 브랜치와 짝을 이루는 원격 브랜치)도 함께 정합니다. 브랜치가 원격보다 뒤처져 있으면 Orca는 몰래 강제 푸시하지 않습니다.

봉투·사물함 비유로 이어 보면일반 Push는 사물함에 이미 들어 있는 봉투 줄의 맨 끝에 새 봉투를 이어 붙이는 일입니다. 그런데 rebase·amend·squash로 이미 낸 봉투를 뜯어 고쳐 다시 봉하면, 사물함에는 옛날 사본이 남아 있어 내 서랍과 끝이 맞지 않습니다. 이어 붙일 자리가 없으니 일반 Push로는 올라가지 않고, 사물함 내용을 바꿔 끼우는 강제 푸시가 필요해집니다. 아래 단계를 넘겨 보세요.

정리하면, rebase·amend·squash로 기록을 다시 써서 원격에는 내 로컬 커밋의 옛날 사본만 있는 상황이면 Source Control 패널이 Force push with lease(조건부 강제 푸시)를 따로 떨어진 버튼으로 보여 줍니다. 일반 Push가 실패했을 때 대신 쓰이는 일은 절대 없습니다.

  • 버튼 라벨에 바뀌게 될 커밋 개수와 upstream 브랜치 이름이 표시되어, 무엇이 바뀌는지 정확히 알 수 있습니다.
  • --force-with-lease를 쓰므로, 내가 알고 있는 원격 상태가 오래된 것이면 푸시가 중단됩니다. 그 사이 다른 사람이 올린 커밋을 덮어쓰지 않습니다.

브랜치를 푸시한 뒤에는 Source Control 패널의 호스팅 리뷰 동작으로 PR(또는 MR)을 만듭니다. 만들기 전에 base 브랜치·제목·설명·초안(draft) 여부를 확인하세요.

  • Bitbucket Cloud도 같은 작성 화면에서 PR을 만들 수 있습니다. Bitbucket Cloud에는 초안 PR이 없어서 Draft 항목이 숨겨집니다.
  • GitHub에서 고른 base에 이미 열린 PR이 있으면 Stack this PR above #N(#N 위에 이 PR 쌓기)을 고를 수 있습니다(아래 스택 PR 참고).

PR 제목·설명은 AI가 초안을 써 줄 수 있고, 만드는 도중 문제가 생기면 이유와 Fix with AI 버튼이 담긴 안내가 나옵니다.

Amend(마지막 커밋 고치기)는 명시적으로만 합니다: Commit → Amend. 이미 푸시된 커밋은 사용자가 확인하지 않으면 Orca가 amend하지 않습니다.

왜 확인을 받나요?푸시된 커밋을 고치면 원격과 기록이 어긋나서, 나중에 강제 푸시가 필요해집니다.

Source Control 패널

사이드바의 Source Control(소스 관리) 패널은 지금 보고 있는 화면을 떠나지 않고 같은 동작을 할 수 있게 해 줍니다. 파일을 스테이징하거나 변경을 버리고(discard), 커밋 메시지를 쓰고, Commit · Push · Pull · Sync를 한 번 클릭으로 실행합니다.

Push · Pull · Sync를 봉투·사물함으로
  • Push(푸시) — 내 서랍의 봉투를 학교 사물함(원격)으로 갖다 넣기.
  • Pull(풀) — 사물함에 있는 봉투(다른 사람이나 다른 컴퓨터가 넣은 것)를 내 서랍으로 가져오기.
  • Sync(싱크) — 가져오기와 올리기를 함께 하기. 양쪽에 다 새 봉투가 있을 때 씁니다.
  • upstream — 내 서랍과 짝으로 정해진 사물함 칸. 처음 Push할 때 정해집니다.

충돌이 났을 때

병합 충돌(두 쪽이 같은 줄을 다르게 고쳐서 git이 어느 쪽을 택할지 모르는 상태)이 생기면 Diff viewer가 3방향 보기로 보여 주고 그 자리에서 해결할 수 있습니다.

CHAPTER 07

Orca CLI와 자동화 — 명령, 예약 작업, 오케스트레이션, Computer Use, 스킬

마우스로 하던 Orca 조작을 글자 명령으로 할 수 있게 해 주는 orca 명령줄 도구를 배웁니다. 사람이 스크립트로 쓸 수도 있고, AI 에이전트가 직접 Orca를 움직이는 데도 씁니다.

CLI란 무엇이고, 왜 에이전트가 Orca를 조작하나

쉽게 말하면

Orca 앱은 보통 버튼과 메뉴로 씁니다. 그런데 같은 일을 글자로 된 명령으로 시킬 수도 있습니다. 예를 들어 “새 작업 공간 만들어 줘”를 버튼 대신 orca worktree create --name my-task라고 타이핑하는 식입니다. 이렇게 글자 명령을 입력하는 창을 터미널(글자로 명령을 입력하고 결과를 글자로 돌려받는 창. 맥의 ‘터미널’ 앱, 윈도우의 PowerShell 등)이라 하고, 그 안에서 쓰는 조작 방식을 CLI(Command-Line Interface, 명령줄 인터페이스 — 버튼 대신 명령어로 프로그램을 조작하는 방식)라고 부릅니다.

글자 명령의 큰 장점은 사람이 아니어도 칠 수 있다는 것입니다. Claude·Codex 같은 AI 에이전트는 화면의 버튼을 누르기는 어렵지만 터미널에 명령을 치는 건 아주 잘합니다. 그래서 에이전트가 orca 명령을 치면, 에이전트가 직접 Orca를 움직여 새 워크트리를 만들고, 다른 에이전트에게 일을 시키고, 브라우저를 클릭하고, 진행 상황을 남길 수 있습니다. 이것이 “에이전트가 Orca를 조작한다”는 뜻입니다.

이 장에 자주 나오는 낱말 세 개
  • 런타임(지금 켜져서 일하고 있는 Orca 프로그램 본체) — orca 명령은 혼자 일하지 않고, 이 런타임에게 “이것 좀 해 줘” 하고 말을 전합니다. 그래서 Orca가 켜져 있어야 대부분의 명령이 동작합니다.
  • 셸(shell — 터미널 창 속에서 명령을 받아 실행하는 프로그램. zsh, bash, PowerShell 등) — “셸에서 실행한다” = “터미널에 쳐서 실행한다”로 읽으면 됩니다.
  • 스크립트(명령 여러 개를 적어 둔 작업 순서표. 엑셀 매크로와 비슷합니다) — 사람이 한 줄씩 치지 않아도 순서대로 자동 실행됩니다.

명령 한 줄 읽는 법 — 해부도

정리하면 Orca CLI는 “아무 셸에서나, 실행 중인 Orca를 스크립트로 조작하는 orca 명령”입니다. 할 수 있는 일은 다음과 같습니다.

워크트리

워크트리(작업마다 따로 꺼내 놓은 프로젝트 폴더)를 만들고, 목록을 보고, 상태를 기록합니다.

에이전트 터미널

에이전트가 돌고 있는 터미널을 읽고, 글자를 보내고, 끝날 때까지 기다립니다.

파일·diff

파일과 diff(무엇이 바뀌었는지 이전과 비교해 보여 주는 화면)를 Orca 탭으로 엽니다.

내장 브라우저

Orca 안 브라우저 탭을 이동·클릭·입력·스크린샷합니다.

예약 자동화

정해진 시간에 프롬프트를 실행합니다.

아티팩트 공유

HTML·Markdown을 공개 링크로 공유합니다.

Orca 고유 도구

오케스트레이션, Computer use, 에뮬레이터, Linear 등을 스크립트나 AI 에이전트가 제어합니다.

설치·등록과 동작 확인

CLI는 데스크톱 앱에 함께 들어 있습니다. 따로 내려받는 게 아니라, 앱 설정에서 “터미널에서 orca를 쓸 수 있게 등록”만 하면 됩니다.

  1. CLI 등록앱 설정에서 Orca CLI를 등록합니다. 버전에 따라 Settings → General → Orca CLI(설정 → 일반) 또는 Settings → Experimental → CLI(설정 → 실험 기능)에 있습니다.
  2. 명령이 보이는지 확인command -v orca — orca 명령의 위치가 출력되면 등록된 것입니다. 성공: 경로가 한 줄 나옵니다. 실패: 아무것도 나오지 않으면 ①(설정에서 등록)로 돌아갑니다.
  3. Orca와 연결되는지 확인orca status --json — CLI가 실행 중인 Orca 런타임에 닿는지 확인합니다.
  4. Orca가 꺼져 있다면orca open --json으로 연 뒤 다시 orca status --json을 실행합니다.
command -v orca
orca status --json
# Orca가 실행 중이 아니라면
orca open --json
orca status --json

코드 속 #로 시작하는 줄은 설명 메모입니다. 실행되지 않습니다.

--json을 붙이는 이유

다른 도구(스크립트·에이전트)가 결과를 읽어야 할 때는 --json을 붙이세요. 사람이 읽기 좋은 출력은 터미널에서 빠르게 확인할 때만 씁니다.

에이전트에게 CLI 사용법 가르치기 — 에이전트가 이 명령들을 정확히 쓰도록, 앱 버전과 맞는 orca-cli 스킬(에이전트용 사용 설명서)을 설치할 수 있습니다. 스킬은 뒤의 스킬 레지스트리에서 다룹니다.

명령 레퍼런스 — 분야별

이 절은 사전입니다 — 건너뛰어도 됩니다

여기는 에이전트·스크립트가 정확한 명령을 찾아보는 사전입니다. 처음 읽는다면 아래 지도와 탭마다 맨 위 한 문장(“이걸로 할 수 있는 일”)만 훑고 다음 절로 넘어가세요. 명령 목록은 탭 안의 🔧 접힌 상자에 있습니다. 모든 명령 끝의 --json은 “기계가 읽을 결과로 달라”는 뜻입니다.

이걸로 할 수 있는 일 — Orca를 켜고(open), 연결을 확인하고(status), 화면 없는 컴퓨터에서 Orca를 서버로 계속 돌려 둘(serve) 수 있습니다.

이걸로 할 수 있는 일 — Orca에 저장소(프로젝트 폴더)를 추가·확인하고, 지난 에이전트 대화 기록에서 “rate limit” 같은 낱말을 검색할 수 있습니다.

이걸로 할 수 있는 일 — 예: “fix-login이라는 워크트리를 만들고 Codex에게 ‘로그인 테스트를 조사해 줘’라고 바로 시켜라” — 이런 일을 한 줄로 시킬 수 있습니다.

이걸로 할 수 있는 일 — 이미 있는 워크트리에서 에이전트를 하나 더 띄우거나, 워크트리에 PR·Linear 이슈 링크를 여러 개 붙여 두고 나중에 이슈 번호로 그 작업과 담당 에이전트를 찾을 수 있습니다.

이걸로 할 수 있는 일 — 에이전트가 돌고 있는 터미널 화면을 읽고, “continue”를 입력해 주고, 일이 끝날 때까지 기다릴 수 있습니다.

이걸로 할 수 있는 일 — 바뀐 파일이나 그 변경 내용(diff)을 Orca 화면의 탭으로 열어 줍니다.

이걸로 할 수 있는 일 — 사람이 웹 화면을 확인하듯, Orca 안의 내장 브라우저에서 주소로 이동하고, 입력칸을 채우고, 버튼을 누르고, 스크린샷을 찍을 수 있습니다.

이걸로 할 수 있는 일 — Orca 밖의 데스크톱 앱을 누르거나, iOS 시뮬레이터(컴퓨터 속 가상 아이폰)를 탭·회전할 수 있습니다.

이걸로 할 수 있는 일 — 에이전트가 Linear(팀 업무 티켓 관리 서비스)의 티켓을 읽고, 상태를 “진행 중”으로 바꾸고, 댓글을 다는 등 티켓을 관리합니다.

이걸로 할 수 있는 일 — 에이전트용 설명서(스킬)를 설치하고, 원격 컴퓨터에 Claude/Codex 계정을 추가하고, 보고서 HTML·Markdown 파일을 공개 링크로 공유할 수 있습니다.

이걸로 할 수 있는 일 — 예약 프롬프트를 만들고, 관리하는 원격 Orca 서버를 업데이트·복구하고, 에이전트 상태 훅을 켜고 끌 수 있습니다.

에이전트 습관(Agent habits) — 권장 사항
  • 결과를 프로그램이 읽어야 하면 --json을 붙인다(기계가 읽기 쉬운 형식).
  • 화면에 보이는 글자로 대상을 짐작하지 말고, id: 같은 정확한 선택자(대상을 가리키는 이름표)로 고른다.
  • 다음에 무엇을 입력할지 분명하지 않으면, 보내기 전에 터미널 화면을 먼저 읽어 본다.
  • 진행 상황은 워크트리 카드의 코멘트로 남긴다(체크포인트).
  • 누가 무엇을 맡았고 끝났는지 따라가야 하는 여러 에이전트 작업은, 터미널에 그때그때 지시를 넣는 대신 오케스트레이션을 쓴다.

오케스트레이션 — 여러 에이전트를 감독하며 일 나누기 Experimental

쉽게 말하면

팀장(코디네이터 에이전트)이 할 일 목록(Task)을 만들고, 팀원(워커 에이전트)에게 하나씩 맡긴 뒤(Dispatch), 우편함(Inbox)으로 “다 했어요”(worker_done)나 “질문 있어요”(question) 편지를 받는 구조입니다. 중요한 결정은 팀장이 “결정 관문”(Decision gate)을 세워, 답이 나올 때까지 그 일을 멈춰 둡니다.

언제 쓰나 — 누가 맡았는지(소유), 끝났는지(완료 추적), 작업 간 순서(DAG(“A가 끝나야 B 시작” 같은 순서 관계를 화살표로 이은 그림))가 필요할 때 씁니다. 한 번 던지는 프롬프트라면 orca terminal send, 감독 없이 일을 통째로 넘기려면 orca-cli 스킬의 worktree/terminal 명령을 쓰세요.

먼저 확인할 것
  • 이 명령을 쓰기 전에 Settings → Experimental(설정 → 실험 기능)에서 orchestration을 켜야 합니다.
  • 실험적 Orchestration 패널은 성능 문제로 v1.4.247에서 꺼져 있지만, 명령은 여전히 동작합니다.
  • CLI는 실행 중인 Orca 런타임과 대화하므로 orca status --json이 먼저 성공해야 합니다.

핵심 낱말 다섯 가지 — 비유로

Run = 프로젝트 폴더

이번 일 전체를 담는 폴더이자 팀장의 우편함입니다. 폴더가 일을 직접 나눠 주지는 않습니다 — 나눠 주는 건 팀장입니다.

Task = 할 일 카드

카드 한 장에 무엇을 할지, 먼저 끝나야 할 카드, 지금 상태(대기·준비·배정됨·완료·실패·막힘)가 적혀 있습니다.

Dispatch = 1회 배정

카드 한 장을 팀원 한 명(터미널 하나)에게 한 번 맡기는 것. 다시 맡기면 새 Dispatch(시도 2)가 됩니다. “다 했어요” 보고는 지금 맡은 배정으로만 받아 줍니다.

Message = 우편함 편지

“다 했어요”(worker_done), “질문 있어요”(question), “아직 일하는 중이에요”(heartbeat) 같은 편지입니다.

Decision gate = 자물쇠

팀장이 답해야 풀리는 자물쇠. 답이 정해질 때까지 그 카드를 잠가 둡니다.

그래서 워커가 “다 했어요”나 “아직 일하는 중이에요”를 보낼 때는 카드 번호(taskId)와 배정 번호(dispatchId)를 둘 다 적습니다. 예전 시도가 엉뚱하게 지금 카드를 완료 처리하지 못하게 하려는 것입니다.

권장 감독 루프 — 단계별

이 명령은 누가 치나요?

아래 ①~⑥ 명령은 보통 코디네이터(팀장 역할 에이전트)와 워커 에이전트가 스스로 칩니다. 사람이 할 일은 코디네이터에게 목표를 말해 주고, 질문·결정이 올라오면 답하고, 결과를 확인하는 것입니다.

① Run 만들기

orca orchestration run-create --objective "Split checkout QA and summarize blockers" --json

목표(objective)를 가진 이름 공간과 코디네이터 우편함이 생깁니다.

② Task 만들기

orca orchestration task-create --spec "Audit billing settings for mobile layout" --task-title "Billing audit" --json

③ 워커 시작(= Dispatch 생성)

할 일 카드를 팀원(에이전트)에게 맡깁니다. 이 순간 Dispatch(1회 배정)가 하나 생깁니다.

orca orchestration worker-start --task <taskId> --worktree current --agent codex --json

④ 우편함 확인하며 기다리기(다 읽으면 ack = 받았음 도장)

orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 900000 --json
orca orchestration check --ack <deliveryId> --wait --types worker_done,escalation,question --timeout-ms 900000 --json

--timeout-ms 900000 = 900,000밀리초 = 15분까지 기다린다는 뜻입니다.

팀장은 편지가 올 때까지 기다렸다가, 한 번에 배달된 편지 묶음을 모두 처리한 뒤 --ack로 “받았음” 도장을 찍습니다. 기다리는 동안에도 CLI는 주기적으로 “살아 있어요” 신호(heartbeat)를 냅니다.

⑤ 워커가 완료 보고(워커 창에서)

orca orchestration send \
  --type worker_done \
  --subject "Completed mobile audit" \
  --body "Fixed footer overlap; no follow-ups." \
  --task-id <taskId> \
  --dispatch-id <dispatchId> \
  --outcome succeeded \
  --files-modified "src/app/settings/Billing.tsx" \
  --json

worker_done은 --outcome succeeded|failed가 필수입니다. ID는 워커에게 주입된 값을 씁니다.

⑥ 정리 — release 또는 retain

orca orchestration worker-release --dispatch <dispatchId> --json
orca orchestration worker-retain --dispatch <dispatchId> --json

받아들여진 worker_done 뒤에는 같은 터미널을 다음 Dispatch에 재사용하거나, release로 내보냅니다(살펴볼 출력은 보관하고 코디네이터 소유 에이전트 터미널만 닫음). 사용자가 남겨 달라고 했다면 디버깅용으로 retain.

코디네이터 ↔ 워커 메시지 흐름

더 깊은 운영 — 접어 둔 부분

워커마다 다른 모델 고르기, 멈춘 워커 살펴보기·복구, 다른 컴퓨터에서 워커 띄우기(연합), 직접 조립하는 저수준 배정, 여러 에이전트에게 한꺼번에 보내는 그룹 주소는 아래 접힌 상자에 있습니다.

워커 계약(Worker contract)

일을 배정받은 워커는 팀장과 연락하는 법이 적힌 안내문(preamble)을 함께 받습니다. 약속은 다섯 가지입니다.

  1. worker_done은 정확히 한 번실패해도 보내고, --outcome을 붙입니다.
  2. 짧은 --body 요약한 일, 찾은 것, 남은 것.
  3. task ID와 dispatch ID 둘 다오래된 재시도가 엉뚱한 Dispatch를 완료 처리하지 못하게 합니다.
  4. heartbeat배정 안내문이 요구하면, 오래 걸리는 작업 중에 “살아 있어요” 신호를 보냅니다.
  5. 막히는 질문은 ask로자기 터미널 화면에서 사용자에게 묻지 말고 orca orchestration ask로 팀장에게 묻습니다.

결정 관문(Decision gates)

ask — 워커 → 코디네이터 질문.

gate — 코디네이터가 Task DAG를 만들어 두고, 결정이 기록될 때까지 특정 Task를 막고 싶을 때.

CHAPTER 08

원격과 모바일 — SSH, 원격 Orca 서버, 폰 앱

노트북이 아닌 다른 컴퓨터(성능 좋은 개발 서버, GPU 장비, 집에 둔 Mac mini)에서 에이전트를 돌리고, 그 모습을 노트북이나 휴대폰으로 지켜보고 조종하는 방법을 다룹니다.

먼저 알아 둘 말: SSH · 원격 서버 · 페어링

쉽게 비유하면 노트북은 리모컨, 원격 컴퓨터는 TV라고 생각해 보세요. 리모컨(노트북)으로 버튼을 누르면 실제 화면과 소리(빌드·에이전트 실행)는 TV(원격 컴퓨터)에서 나옵니다. 리모컨 전원이 꺼져도 TV는 계속 켜져 있지요. 휴대폰 앱은 두 번째 리모컨입니다. "페어링"은 리모컨과 TV를 처음 한 번 짝지어 주는 일입니다.

SSH

SSH(Secure Shell — 다른 컴퓨터에 암호화된 통로로 접속해 명령을 실행하게 해 주는 표준 방법)는 인터넷이나 사내망 너머의 다른 컴퓨터에 안전하게 접속하는 통로입니다. 접속할 컴퓨터를 호스트(host — 접속해 들어갈 그 컴퓨터), Orca에 저장한 접속 정보를 SSH 대상(target — 주소·사용자 이름을 적어 둔 즐겨찾기)이라고 부릅니다. 로그인은 보통 비밀번호 대신 키 파일(identity file — 내 컴퓨터에 보관하는 비밀 파일. 이 파일을 가진 사람만 로그인할 수 있음)로 합니다.

원격 Orca 서버

다른 컴퓨터에서 Orca 전체를 계속 실행해 두고, 노트북·휴대폰·브라우저는 화면만 보여 주는 방식입니다. 프로젝트·워크트리(작업마다 따로 쓰는 작업 폴더)·터미널·탭·계정·에이전트 세션이 모두 서버 쪽에 있습니다.

페어링(pairing)

클라이언트(화면을 보여 주는 쪽 — 노트북·폰)와 서버를 한 번 짝지어 서로 믿게 만드는 절차입니다. 서버가 만든 접속 링크나 코드·QR을 클라이언트에 넣으면, 그 기기 전용 토큰(출입증 같은 비밀 문자열. 서버가 이 출입증만 취소하면 그 기기만 내보낼 수 있음)이 생깁니다.

LAN

LAN(Local Area Network — 근거리 네트워크)은 같은 사무실이나 집의 공유기 안에 묶인 네트워크입니다. 같은 Wi‑Fi·공유기에 붙은 기기끼리 바로 통하는 길이라고 보면 됩니다. 이 장에서 "믿을 수 있는 LAN", "집 LAN"이라고 할 때 이 뜻입니다.

Orca Relay

Relay(중계)는 이름 그대로 Orca가 중간에서 폰과 데스크톱 사이를 전달해 주는 중계소입니다. 모바일 페어링에서 쓸 수 있으면 권장되는 길이며, 이 길을 쓸 때만 데스크톱과 폰 두 기기 모두 같은 Orca 계정 로그인이 필요합니다. Relay로 짝지은 폰은 데스크톱의 Relay 연결을 따라갑니다.

Tailscale·tailnet

Tailscale(여러 기기를 하나의 사설 네트워크로 묶어 주는 VPN 서비스)은 내 기기들끼리만 쓰는 비공개 네트워크를 만들어 주는 도구입니다. 그 네트워크를 tailnet이라 하고, 각 기기는 보통 100.으로 시작하는 사설 주소를 받습니다.

헤드리스(headless)

모니터·창 없이 돌아가는 컴퓨터나 프로그램. 클라우드 리눅스 서버, VM(가상 머신 — 한 컴퓨터 안에 소프트웨어로 만든 또 하나의 컴퓨터)이 대표적입니다. orca serve가 Orca를 창 없이 실행합니다.

포트 포워딩

포트(한 컴퓨터 안의 프로그램마다 붙은 문 번호) 포워딩은 원격에서 띄운 개발 서버(예: 3000번 포트)를 내 노트북 브라우저에서 localhost(내 컴퓨터 자신을 가리키는 주소)처럼 열게 해 주는 연결입니다.

어떤 방식을 고를까: SSH 워크트리 vs 원격 Orca 서버

Orca를 실행하는 방법은 네 가지(로컬, SSH, 자체 호스팅 서버, 일회용 VM)이며, 이 장은 그중 SSH와 원격 Orca 서버를 다룹니다. 둘 다 "다른 컴퓨터에서 일을 시킨다"는 점은 같지만, 누가 Orca의 두뇌(런타임 — 실제로 판단하고 기억하는 Orca 본체)를 가지느냐가 다릅니다. 아래 그림에서 초록 상자(두뇌)가 어디 있는지만 보세요.

노트북의 Orca가 주인입니다. 다른 컴퓨터는 고른 워크트리와 터미널만 실행하는 "작업장"으로 씁니다. 편집기와 diff는 노트북에 있고, 에이전트는 원격 호스트에서 돕니다.

  • 좋은 경우: 오래 걸리는 빌드, GPU 장비, 노트북이 적합하지 않은 환경
  • 설정: Settings → SSH에 호스트 추가

다른 컴퓨터의 Orca가 주인입니다. 그 컴퓨터가 Orca 런타임 전체를 갖고, 데스크톱·브라우저·모바일·자동화 클라이언트가 같은 세션을 공유합니다.

  • 좋은 경우: 늘 켜 둘 Mac mini·데스크톱·헤드리스 리눅스 서버, 여러 기기에서 같은 세션 보기
  • 설정: Settings → Remote Orca Servers 또는 orca serve
  • Beta 베타 기능입니다.

호스트 키 확인 — "이 서버가 진짜 그 서버인가?"

호스트 키란?서버마다 가진 고유한 "지문"입니다. 한 번 접속한 서버의 지문을 기억해 두었다가, 다음에 지문이 달라지면 "누군가 서버인 척하는 것 아닐까?" 하고 접속을 막습니다. 이 기억 목록이 known_hosts 파일입니다.

Orca의 내장 SSH 연결은 내 컴퓨터에서 실제로 적용되는 OpenSSH(컴퓨터에 깔린 표준 SSH 프로그램) known_hosts 파일들과, Orca가 예전에 저장해 둔 키를 기준으로 확인합니다.

고급 연결 옵션과 인증(암호 · MFA · Kerberos · 보안키)

회사 IT가 이 방식을 요구할 때만보통은 앞의 "SSH 대상 추가하기"만으로 충분합니다. 회사 IT 담당자가 프록시·점프 호스트·Kerberos·USB 보안키 같은 방식을 쓰라고 안내했을 때만 아래 상자를 펼치세요.

한 줄 요약: 키 암호는 Orca가 켜져 있는 동안만 기억하고, 인증 코드(OTP·MFA)를 묻는 서버는 Orca가 질문을 화면에 띄워 줍니다. 회사 로그인(Kerberos)이나 USB 보안키처럼 특별한 방식은 Orca가 알아서 컴퓨터에 깔린 표준 SSH 프로그램으로 넘겨 처리합니다.

원격 Orca 서버 Beta

한 컴퓨터가 일을 하고, 다른 컴퓨터는 화면만 제공합니다. 서버가 프로젝트·워크트리·터미널·탭·제공자 계정·에이전트 세션을 가지고, 노트북은 실행 중인 그 Orca에 접속합니다. 가장 쉬운 방법은 양쪽 모두 Orca 데스크톱 앱 + Tailscale이며, 이 경우 orca serve는 필요 없습니다.

베타 · 사설 경로에서만원격 Orca 서버는 베타입니다. 서버와 클라이언트는 같은 Tailscale tailnet이나 LAN(같은 사무실·집 공유기 안의 네트워크)처럼 내가 통제하는 사설 네트워크 경로에 두세요.
에이전트 도구는 서버에 설치Codex, Claude Code, OpenCode, git, 그 밖의 제공자 CLI는 서버 컴퓨터에 설치하고 로그인해야 합니다. 노트북에서 로그인한 상태가 서버로 자동으로 넘어가지 않습니다.

권장: 데스크톱 앱 + Tailscale

준비 0단계 — 먼저 두 컴퓨터를 같은 Tailscale에 묶어 둡니다.

  1. 두 컴퓨터 모두에 Tailscale 설치 — 설치 방법은 Tailscale 공식 안내를 따릅니다. 두 컴퓨터 모두 최신 Orca도 설치해 둡니다.
  2. 두 컴퓨터 모두 같은 Tailscale 계정으로 로그인 — 그래야 같은 tailnet(내 기기끼리만 쓰는 비공개 네트워크)에 들어갑니다.
  3. 서버 컴퓨터는 켜 두기 — 깨어 있고, 인터넷에 연결돼 있고, Orca가 실행 중이어야 합니다.
  4. 준비 완료 확인 — 서버 컴퓨터의 Orca 연결 주소 목록(아래 서버 ③단계)에 100.으로 시작하는 주소가 보이면 준비 완료입니다. Orca는 이 주소를 목록 맨 위에 둡니다.

링크는 비밀번호처럼페어링 URL은 이 Orca 런타임에 들어갈 권한 그 자체입니다. 짝지을 클라이언트에게만 보내세요.
클라이언트 ① · 서버 추가

노트북에서 Settings → Remote Orca Servers → Add Server를 누르고, 알아보기 쉬운 이름(예: Remote Server)을 넣고, 서버에서 받은 링크를 붙여 넣은 뒤 Add Server를 누릅니다.

클라이언트 ② · 연결

저장된 서버가 Disconnected로 보이면 Connect를 누릅니다. 서버를 추가해도 새 프로젝트가 모두 그 서버로 가지는 않습니다. 새로 여는 프로젝트(와 그 터미널·브라우저·모바일 연결)를 기본으로 이 서버에서 열고 싶으면 Advanced → Active Server를 켜세요.

서버 사용하기

서버가 Connected가 되면 서버나 그 프로젝트를 골라 평소처럼 Orca를 씁니다. 터미널·에이전트 프로세스·파일·워크트리·세션 상태는 모두 서버 컴퓨터에 있습니다. 그래서:

  • 클라이언트 노트북이 잠들거나 끊겨도 에이전트는 계속 돕니다.
  • 서버에는 에이전트가 쓰는 저장소·도구·자격 증명(로그인 정보)이 있어야 합니다.
  • 서버는 깨어 있고 tailnet에 연결된 상태여야 합니다.

접근 권한과 보안

Orca는 페어링한 클라이언트마다 따로따로, 취소 가능한 토큰을 만들고, 서버의 Shared Server Access에 목록으로 보여 줍니다. 지킬 일은 세 가지입니다.

🗑 필요 없어진 기기는 바로 내보내기

Shared Server Access에서 그 기기 옆 휴지통 버튼을 누르면 취소되고, 그 권한을 쓰던 클라이언트는 즉시 끊깁니다.

🎯 닿을 수 있는 기기를 최소로

Tailscale 관리 화면에서 이 서버에 닿을 수 있는 기기를 꼭 필요한 것만 남기세요.

🚫 인터넷에 직접 열지 않기

Orca 서버는 Tailscale이나 믿을 수 있는 LAN 같은 사설 경로로만 쓰세요.

대안: orca serve (헤드리스 서버)

데스크톱 창 없이 돌려야 할 때 — 예를 들어 헤드리스 리눅스 서버나 서비스로 관리되는 VM — orca serve를 씁니다. 로그인한 채 둘 수 있는 MacBook·데스크톱이라면 위의 앱 안 설정이 더 간단합니다. 서버에 Orca와 함께 들어 있는 CLI를 설치하고 실행합니다.

orca serve --pairing-address <server-tailscale-ip-or-hostname>
# 예
orca serve --pairing-address 100.64.1.20
# 방화벽·터널·서비스 정의가 고정 포트를 요구할 때
orca serve --port 6768 --pairing-address 100.64.1.20

실행하면 터미널에 페어링 URL이 찍힙니다. 이 URL을 클라이언트의 Settings → Remote Orca Servers → Add Server에 붙여 넣으면 됩니다.

한 번에 한 가지 호스트 모드만그 컴퓨터를 이미 Orca 데스크톱 앱이 공유하고 있다면, 같은 설정에 두 번째 orca serve 프로세스를 띄우지 마세요.

헤드리스 서버에 폰 연결하기

모바일 앱용으로는 모바일 범위의 QR 코드와 링크를 요청합니다.

orca serve --pairing-address 100.64.1.20 --mobile-pairing

폰을 같은 tailnet에 두고, Orca Mobile에서 Pair를 고른 뒤 터미널에 뜬 QR 코드를 찍거나 출력된 링크를 붙여 넣습니다.

서비스로 계속 돌리기

한 줄 요약: 컴퓨터가 켜지면 자동으로 Orca 서버를 띄워 두는 등록입니다. 등록·상태 확인·해제 명령 세 개만 기억하면 됩니다(아직 Windows에서는 쓸 수 없음).

orca serve service install --port 6768
orca serve service status
orca serve service uninstall

원격 서버 문제 해결

Tailscale 주소가 목록에 없음

서버에서 Tailscale이 연결됐는지 확인하고 Connection address 옆 새로고침을 누르세요. 두 컴퓨터가 같은 tailnet에 로그인해야 합니다. Tailscale IPv4 주소는 보통 100.으로 시작합니다.

서버가 Disconnected

서버 컴퓨터가 깨어 있는지, Orca가 실행 중인지, Tailscale에서 두 기기가 온라인인지 확인하세요. 한쪽이 닿지 않으면 Tailscale 관리 화면에서 두 기기가 서로 닿도록 허용돼 있는지(ACL·grant — 어느 기기가 어느 기기에 닿을 수 있는지 정하는 규칙) 확인하세요. 서버 줄에 호환되지 않는 프로토콜 버전이 보이면 두 컴퓨터 모두 Orca를 업데이트하세요.

접근 링크를 엉뚱한 사람에게 보냈음

서버에서 Settings → Remote Orca Servers → Shared Server Access를 열고 그 권한을 취소한 뒤, 원래 클라이언트용 새 링크를 만드세요.

서버가 에이전트 CLI를 찾지 못함

그 CLI를 서버 컴퓨터에 설치하고 로그인하세요. 원격 세션은 클라이언트가 아니라 서버의 PATH·홈 디렉터리·자격 증명을 씁니다.

orca serve가 잘못된 주소를 알림

명령을 멈추고 클라이언트가 닿을 수 있는 주소로 다시 시작하세요: orca serve --pairing-address <reachable-tailscale-ip-or-hostname>. 원격 클라이언트용으로 와일드카드 주소(특정 주소 대신 "아무 주소나"를 뜻하는 값)나 127.0.0.1을 쓰지 마세요.

페어링하기

1 · 데스크톱에서 코드 만들기

데스크톱 Orca의 계정 / 상태 메뉴(account / status menu)에서 페어링 흐름을 엽니다. Orca가 일회용 페어링 코드를 보여 줍니다.

2 · 폰에서 Pair

Orca 모바일 앱에서 Pair를 고르고 코드를 붙여 넣습니다. 데스크톱의 딥 링크를 눌러 모바일 페어링 화면으로 바로 갈 수도 있습니다.

3 · 경로 고르기

가능하면 Orca Relay(Orca가 중간에서 전달해 주는 중계소)로 페어링하세요. Relay를 쓸 때만 데스크톱과 폰 두 기기 모두 같은 Orca 계정으로 로그인해야 합니다(LAN·Tailscale로 짝지을 때는 로그인이 필요 없습니다). Relay에서는 로컬 네트워크 주소 선택이 선택 사항이며(같은 공유기 안의 LAN으로 빠르게 가고 싶을 때 펼침), LAN 페어링에는 주소가 꼭 필요합니다.

4 · 토큰 발급

페어링 교환으로 그 폰 전용 기기 토큰이 생깁니다. 고른 경로로 데스크톱에 계속 닿을 수 있게 두세요.

5 · 호스트 이름 표시

페어링 후 폰은 데스크톱의 기기 이름으로 호스트를 부르고 운영체제를 보여 줍니다. 기기 이름은 데스크톱 Settings → Remote Orca Servers에서 바꿀 수 있으며, 폰은 다시 연결될 때 바뀐 이름을 가져옵니다.

데스크톱을 닫으면직접/LAN 세션은 데스크톱 앱을 닫는 순간 끊기고, 다시 열어야 이어집니다. Relay 기반 페어링은 데스크톱의 Relay 연결을 따르므로, 호스트가 오프라인이 되면 데스크톱을 다시 여세요. 창 없는 서버라면 앞의 orca serve --mobile-pairing을 쓰세요.

Chat UI · Quick Commands · 세션 탭

한 줄 요약: 지원되는 에이전트(Claude, Codex 등)는 폰에서 메신저 같은 대화 화면(Chat UI)으로 열 수 있고, 데스크톱에 저장해 둔 명령 목록(Quick Commands)을 폰에서 그대로 실행할 수 있습니다. 세션 탭을 길게 누르면 닫기·화면 바꾸기 메뉴가 나옵니다.

모바일 문제 해결

워크트리에서 스피너가 계속 돎

폰은 데스크톱 에이전트 프로세스의 하트비트(살아 있다는 신호)를 따라갑니다. 데스크톱은 idle인데 폰은 working이면 그 워크트리 줄을 강제로 새로 고쳐 상태를 맞추세요.

페어링 실패

Relay로 페어링한다면 데스크톱과 폰 두 기기 모두 같은 Orca 계정에 로그인했는지 확인하세요. 페어링 코드는 몇 분 뒤 만료되므로, 화면에 오래 떠 있었다면 새로 만드세요.

Authentication failed / pairing invalid

데스크톱이 이 기기 토큰을 더 이상 받지 않는 상태입니다(예: 데스크톱이 페어링된 기기를 지웠을 때). 먼저 배너의 Retry를 눌러 보세요(일시적 거부는 다시 페어링하지 않아도 회복될 수 있음). 계속 실패하면 Re-pair from desktop을 쓰거나, 호스트를 Remove하고 다시 페어링하세요.

Update Orca Mobile / Update Orca on your computer

폰과 데스크톱은 버전이 있는 모바일 프로토콜로 대화합니다. 어느 한쪽이 너무 오래되면 모바일이 그 호스트를 막고 App Store(iOS)나 GitHub Releases(Android APK 또는 데스크톱)로 안내한 뒤 호스트 목록으로 돌아갑니다. 업데이트 후 연결을 새로 고치고, 메시지가 남아 있으면 호스트를 지우고 다시 페어링하세요.

Quick Commands를 쓸 수 없음

페어링된 데스크톱을 업데이트해 quick-commands 기능을 알리게 하세요.

데스크톱에 닿지 않음

폰과 데스크톱이 같은 네트워크 경로(LAN, Tailscale, 또는 페어링에 쓴 경로)를 공유해야 합니다. 데스크톱 앱을 닫으면 연결이 끊기며, 다시 열면 폰이 자동으로 재연결합니다.

함께 보면 좋은 것: 에이전트 완료 알림이 알맞은 기기로 가도록 모바일 알림과 데스크톱 알림을 짝지으세요. 창 없는 기계는 원격 Orca 서버의 모바일 페어링을, 제공자 사용량은 사용량·한도 추적 장을 참고하세요.

한눈에 정리
  • 다른 컴퓨터(서버)가 없다면 SSH·원격 서버는 건너뛰고 모바일 앱만 보면 됩니다.
  • SSH 워크트리: 노트북 Orca가 주인, 원격 호스트는 작업장. Settings → SSH에서 대상 추가(host·user·port는 IT 담당자에게) → Test → Save, 워크트리 위치로 SSH 대상 선택.
  • 호스트 키(서버 지문)가 바뀌었다는 경고가 뜨면 직접 처리하지 말고 서버 관리자에게 문의합니다.
  • 끊겨도 원격 에이전트는 계속 돌고, 끊기면 워크트리 카드의 재연결 버튼으로 다시 붙습니다.
  • 관리형 Orca 서버는 자동으로 설치·업데이트되므로 오류가 날 때만 Settings → Managed servers를 봅니다.
  • Ports 탭(Cmd+Shift+I — macOS)으로 원격 포트를 감지해 한 번 클릭으로 내 브라우저에 연결합니다.
  • 원격 Orca 서버(베타): 서버가 Orca 전체를 가짐. 두 컴퓨터를 같은 Tailscale에 묶고(100. 주소 확인) → 서버에서 New Link → Generate Access Link → 노트북에서 Add Server → Connect. 접근 링크는 비밀번호처럼, 필요 없어진 기기는 바로 취소.
  • 모바일 앱(베타): 상태 보기·짧은 답장·푸시 알림·워크트리 만들기. 데스크톱 계정/상태 메뉴에서 코드를 만들어 폰에서 Pair. Relay를 쓸 때만 두 기기 모두 같은 Orca 계정 로그인.
