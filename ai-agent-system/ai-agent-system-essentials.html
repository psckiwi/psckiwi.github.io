CHAPTER 01

LLM과 에이전트의 기본 구조

AI 에이전트의 두뇌는 LLM(대규모 언어 모델)입니다. 그런데 LLM 은 혼자서는 글을 읽고 글을 써 낼 뿐, 파일을 열거나 메일을 보내지 못하고, 방금 나눈 대화도 다음 호출에서는 기억하지 못합니다. 이 장은 LLM 한 번 호출에 무엇이 들어가고 무엇이 나오는지(역할별 메시지 · 컨텍스트 창 · 토큰 · 추론 · 구조화 출력)를 먼저 보고, 여기에 도구와 반복 고리(루프)를 붙이면 왜 에이전트가 되는지를 설명합니다.

LLM 은 무엇을 하나 — 글을 읽고, 이어질 글을 만든다

LLM(Large Language Model, 대규모 언어 모델 — 아주 많은 글로 학습한 AI 모델)은 입력한 글(프롬프트)을 읽고 그에 맞는 글을 만들어 냅니다. 만들어 내는 글의 종류는 거의 제한이 없어서, 사람 말투의 문장뿐 아니라 코드 · 수식 · JSON(이름과 값을 짝지어 적는 데이터 형식) 같은 구조화된 데이터도 만들 수 있습니다. [OpenAI Text generation] LLM 은 다음에 올 토큰(낱말 조각)을 예측하도록 학습되며, 그래서 학습 때 많이 본 형식에서 더 잘 동작하는 경향이 있습니다. [Writing effective tools for agents]

쉽게 말하면 LLM 은 세상의 글을 어마어마하게 많이 읽은 글 잘 쓰는 사람과 비슷합니다. 질문을 적어 건네면 그럴듯한 답을 적어 돌려줍니다. 하지만 이 사람은 방에 갇혀 있어서 바깥을 볼 수도, 무언가를 직접 할 수도 없습니다. 건네받은 쪽지에 적힌 것과 예전에 읽은 것만으로 답을 씁니다.

실제로는, 모델이 참고하는 정보는 두 가지뿐입니다. 하나는 학습 때 본 대량의 데이터이고, 다른 하나는 이번 요청에 담아 보낸 글인 컨텍스트입니다. Anthropic 문서는 컨텍스트 창을 학습 데이터와 구별해 모델의 “작업 기억(working memory)”이라고 부릅니다. [Claude Context windows] 그래서 오늘의 가격, 회사 데이터베이스의 내용처럼 학습 데이터 밖에 있거나 우리 시스템에만 있는 정보는 모델이 스스로 알 수 없고, 메일 보내기 · 파일 쓰기 같은 실제 행동도 모델이 설명은 해도 직접 하지는 못합니다. 이런 일은 도구를 통해야 합니다. [How tool use works]

또 하나 중요한 성질은 비결정성입니다. 모델이 만드는 내용은 같은 입력에도 달라질 수 있어서, 원하는 결과를 꾸준히 얻으려면 지시를 잘 쓰는 기술(프롬프트 엔지니어링)과 측정이 함께 필요합니다. 같은 계열 모델이라도 스냅숏(특정 날짜에 고정한 모델 판)이 바뀌면 결과가 달라질 수 있으므로, OpenAI 문서는 운영 중인 앱을 특정 스냅숏에 고정하고, 프롬프트 동작을 재는 테스트 · 평가 묶음을 만들어 두라고 권합니다. [OpenAI Text generation] Google ADK 문서도 LLM 기반 에이전트는 모델이 어떻게 진행할지를 그때그때 정하므로 동작이 비결정적이며, 이 점을 전제로 만들고 평가해야 한다고 말합니다. [ADK LlmAgent]

토큰과 컨텍스트 창 — 모델이 한 번에 보는 글 전체

모델은 글을 글자 단위가 아니라 토큰(모델이 글을 쪼개 읽는 단위 — 낱말이나 낱말 조각) 단위로 읽고 씁니다. 모델의 입력과 출력은 모두 토큰 수로 셉니다. 그리고 한 번의 요청에서 쓸 수 있는 토큰 수에는 한도가 있습니다. [OpenAI Conversation state] 이 한도가 컨텍스트 창(context window — 모델이 답을 만들 때 참고할 수 있는 글 전체의 최대 크기)입니다. OpenAI 문서는 컨텍스트 창을 “요청 하나에 쓸 수 있는 최대 토큰 수로, 입력 · 출력 · 추론 토큰을 모두 포함한다”고 정의하고, Anthropic 문서는 “모델이 답을 만들 때 참고할 수 있는 모든 글, 만들어지는 답 자신까지”라고 정의합니다. [OpenAI Conversation state] [Claude Context windows]

설계에서 놓치기 쉬운 점은 사람이 쓴 메시지만 들어가는 것이 아니라는 것입니다. 요청 안의 모든 것이 컨텍스트 창을 차지합니다.

왜 중요한가. 컨텍스트 창은 클수록 길고 복잡한 입력을 다룰 수 있지만, Anthropic 문서는 “컨텍스트가 많을수록 자동으로 좋아지지는 않는다”고 경고합니다. 토큰 수가 늘면 정확도와 회상(앞에 있던 정보를 정확히 떠올리는 능력)이 떨어지는 현상, 이른바 컨텍스트 부패(context rot)가 생기므로 무엇을 넣을지 고르는 일이 공간의 크기만큼 중요합니다. [Claude Context windows] 이 “고르는 일”이 4장의 컨텍스트 엔지니어링입니다.

  • 대화가 진행되면 사용자 메시지와 모델 답이 차례로 쌓이고, 앞 턴은 그대로 보존됩니다(API 기본 동작). 각 턴은 “지난 기록 전체 + 이번 메시지”를 입력으로 받고, 그 답이 다음 턴의 입력이 됩니다. [Claude Context windows]
  • claude.ai 같은 대화 화면은 컨텍스트 창을 “먼저 들어온 것부터 내보내는” 방식으로 관리하기도 합니다 — API 를 직접 쓸 때와 다를 수 있다는 뜻입니다. [Claude Context windows]
  • 에이전트가 도구를 쓸 때마다 도구 결과가 쌓이므로, 에이전트는 일반 대화보다 훨씬 빨리 창을 채웁니다. LangChain 문서도 에이전트가 돌수록 누적 기록 · 도구 결과 · 중간 단계로 창이 찬다고 설명합니다. [LangChain Agents]
  • Anthropic 모델에 따라 최대 100만(1M) 토큰. 최근 여러 Claude 모델이 1M 컨텍스트 창을 갖고, 요청 하나에서 최대 128k(k 는 천. 128k = 12만 8천) 출력 토큰을 만들 수 있습니다. 그 밖의 모델은 200k 토큰입니다. 요청 하나에 이미지 · PDF 쪽을 최대 600개(200k 모델은 100개)까지 넣을 수 있어, 토큰 한도보다 요청 크기 한도에 먼저 닿을 수도 있습니다. [Claude Context windows]
  • OpenAI 모델과 스냅숏마다 다르며 모델 안내 쪽에 적혀 있습니다. 문서의 예: gpt-4o-2024-08-06 은 컨텍스트 창 128k, 출력 최대 16,384 토큰. [OpenAI Conversation state]
  • 토큰 수는 미리 잴 수 있습니다 — OpenAI 의 토크나이저 도구, Anthropic 의 토큰 세기 API. 응답의 usage 필드는 실제로 쓴 양을 알려 줍니다. [OpenAI Conversation state] [Claude Context windows]
  • Anthropic 입력만으로 창을 넘으면 모든 모델에서 400 오류(요청이 잘못되어 받아 줄 수 없다는 응답)(“prompt is too long”). Claude 4.5 이후 모델은 “입력 + 출력 한도”가 창을 넘는 요청도 받아 주되, 생성 중 창 끝에 닿으면 stop_reason: "model_context_window_exceeded" 로 멈춥니다. [Claude Context windows]
  • OpenAI 창을 넘어 만들어진 토큰은 응답에서 잘릴 수 있습니다. 추론 모델에서 창이나 max_output_tokens 한도에 닿으면 status: "incomplete" 로 끝나며, 보이는 답이 나오기 전에 끝나 답 없이 비용만 드는 경우도 있습니다. [OpenAI Conversation state] [OpenAI Reasoning models]
  • 공통 교훈: 앱은 “답이 정상적으로 끝났는지”를 늘 확인해야 합니다(stop_reason · status).

LLM vs 에이전트 — 다음 단계를 누가 정하나

“LLM 을 쓰는 앱”과 “에이전트”는 같은 말이 아닙니다. 둘을 가르는 기준은 모델의 똑똑함이 아니라 일의 진행을 누가 이끄느냐입니다. Anthropic 문서는 LLM 을 쓰는 시스템을 통틀어 에이전트형 시스템이라 부르면서, 그 안을 둘로 나눕니다. [Building effective agents]

워크플로 (workflows) LLM 과 도구가 미리 정해 둔 코드 경로를 따라 엮인 시스템. 예: “요약 → 번역 → 저장”을 코드가 순서대로 부른다. 다음 단계는 개발자가 미리 정했습니다.
에이전트 (agents) LLM 이 자기 진행 과정과 도구 사용을 스스로 이끌며, 일을 어떻게 해낼지에 대한 통제권을 쥔 시스템. 다음 단계는 모델이 결과를 보고 그때그때 정합니다.

그리고 이 둘의 바닥에는 공통 부품인 보강된 LLM(augmented LLM) — 검색 · 도구 · 메모리를 붙인 LLM — 이 있습니다. 최신 모델은 스스로 검색어를 만들고, 알맞은 도구를 고르고, 무엇을 기억할지 정할 수 있습니다. [Building effective agents] 즉 “LLM → 보강된 LLM → 워크플로 → 에이전트” 순서로 자율성과 복잡도가 커집니다.

정의의 말은 다르지만 공통 뼈대는 같습니다. 모델 + 지시 + 도구 + 반복 고리입니다. 차이는 범위에 있습니다. OpenAI 는 다른 에이전트와의 협업을 정의에 넣고, ADK 는 “자율적 실행 단위”라는 소프트웨어 구조로 보며, Anthropic 은 워크플로와의 대비로 정의합니다.

에이전트 루프 — 호출, 실행, 결과, 다시 호출

에이전트 루프는 에이전트가 일하는 반복 고리입니다. 모델은 앱의 코드를 실행할 수 없으므로, 도구 호출 하나하나가 왕복입니다 — 모델이 요청하고, 앱이 실행하고, 결과를 알려 주고, 모델이 이어 갑니다. Anthropic 문서는 이 고리의 기본 모양을 “stop_reason 을 기준으로 도는 while 반복문(조건이 맞는 동안 같은 일을 되풀이하는 코드)”으로 설명합니다. [How tool use works]

① 요청 보내기 — 앱이 도구 목록과 사용자 메시지를 담아 모델을 부릅니다.
1번째 요청
tools: get_weather(city) — 도시의 현재 날씨 user: 서울 날씨 어때? 우산 챙겨야 해?
② 모델 응답 — 도구를 써야겠다고 판단 — 모델은 답 대신 도구 사용 요청을 돌려주고, 멈춘 이유를 tool_use 로 알립니다.
1번째 응답
assistant: tool_use → get_weather {"city": "서울"} stop_reason: tool_use
③ 앱이 도구를 실행 — 모델이 아니라 앱의 코드가 실제 날씨 API 를 부르고, 결과를 tool_result 로 만듭니다.
앱 내부
날씨 API 호출 … tool_result: {"상태": "비", "기온": 17, "강수확률": 80}
④ 결과를 붙여 다시 보내기 — 새 요청에는 원래 메시지, 모델의 앞 응답, 그리고 도구 결과를 담은 사용자 메시지가 모두 들어갑니다. 모델은 앞 요청을 기억하지 않기 때문입니다.
2번째 요청
user: 서울 날씨 어때? 우산 챙겨야 해? assistant: tool_use → get_weather {"city": "서울"} user: tool_result {"상태": "비", "기온": 17, "강수확률": 80}
⑤ 모델 응답 — 이번엔 최종 답 — 더 부를 도구가 없으면 end_turn 으로 끝나고 루프를 빠져나옵니다. 더 필요하면 ② 로 돌아가 다시 도구를 요청합니다.
2번째 응답
assistant: 서울은 지금 비가 오고 17도예요. 강수확률이 80%라 우산을 챙기세요. stop_reason: end_turn → 루프 종료

위 대화는 흐름을 보이기 위한 예시입니다. 실제 필드 이름과 형식은 벤더 API 마다 다릅니다.

루프는 어떻게 끝나나. Claude 의 경우 stop_reason 이 "tool_use" 가 아닌 값("end_turn" · "max_tokens" · "stop_sequence" · "refusal")이면 루프를 나오는데, 이는 최종 답이 나왔거나 앱이 따로 처리해야 할 다른 이유로 멈췄다는 뜻입니다. [How tool use works] Anthropic 의 에이전트 설명은 여기에 더해, 일은 보통 완료될 때 끝나지만 통제를 위해 최대 반복 횟수 같은 멈춤 조건을 두는 것이 흔하고, 확인 지점이나 막혔을 때 사람의 피드백을 위해 멈출 수 있다고 말합니다. [Building effective agents] 멈춤 조건 · 재시도 · 사람 승인은 6장에서 설계합니다.

CHAPTER 02

도구와 함수 호출 — 모델에게 “손발”을 주는 방법

LLM(대규모 언어 모델)은 글을 읽고 글을 쓸 뿐, 메일을 보내거나 데이터베이스를 들여다볼 수는 없습니다. 이 일을 가능하게 하는 것이 도구(Tool)와 함수 호출(Function Calling)입니다. 이 장에서는 도구가 무엇이고 일반 API와 무엇이 다른지, 벤더마다 다르게 부르는 “함수 호출 · 도구 호출 · tool use”가 사실 같은 메커니즘이라는 점, 그리고 호출이 실제로 오가는 흐름과 도구를 잘 정의하고 고르게 하고 오류를 처리하는 방법을 다룹니다.

1. 도구(Tool)란 무엇인가

무엇인가. OpenAI 문서는 도구를 “모델에게 쓸 수 있다고 알려 준 기능 한 조각”이라고 정의합니다. 예를 들면 “어느 지역의 오늘 날씨 가져오기”, “사용자 ID로 계정 정보 보기”, “분실된 주문 환불하기” 같은 것입니다. [OpenAI · Function calling] Anthropic 문서는 같은 것을 앱과 모델 사이의 계약으로 설명합니다. 앱은 “어떤 작업이 가능하고 입력·출력이 어떤 모양인지”를 정해 주고, 모델은 “언제, 어떻게 부를지”를 정합니다. [Claude · How tool use works]

가장 중요한 사실은 모델은 아무것도 직접 실행하지 않는다는 점입니다. 모델은 “이 도구를 이 값으로 불러 주세요”라는 구조화된 요청(정해진 칸에 값을 채운 요청서)을 내놓을 뿐이고, 실제 실행은 내 프로그램(또는 벤더의 서버)이 하며, 그 결과가 다시 대화에 들어갑니다.

비유로 보면 모델은 사무실 책상에 앉아 전화도 컴퓨터도 쓸 수 없는 아주 똑똑한 상담원입니다. 대신 “창고에 재고 확인 요청”, “고객에게 메일 발송 요청” 같은 요청서 양식을 받아 두었고, 필요할 때 양식을 채워 창구에 내밉니다. 창구 직원(내 프로그램)이 실제 일을 하고 결과를 쪽지로 돌려줍니다.
실제로는 요청서 양식 = 도구 정의(이름·설명·입력 스키마), 채운 요청서 = 도구 호출(tool call), 쪽지 = 도구 실행 결과입니다. 모델은 프로그램 코드를 받지 않고, 정의와 결과만 봅니다.

왜 등장했고 어떤 문제를 푸나. 모델이 글만으로 할 수 없는 일이 있기 때문입니다. Anthropic 문서는 도구가 맞는 경우를 네 가지로 꼽습니다.

언제 쓰지 않는가. 반대로 도구가 맞지 않는 경우도 문서에 분명히 적혀 있습니다.

3. 함수 호출(Function Calling)과 도구 호출(Tool Calling)의 관계

결론부터: 같은 메커니즘을 가리키는 다른 이름입니다. OpenAI 문서 제목은 “Function calling”이고 첫 문장에서 “tool calling이라고도 한다”고 밝힙니다. Anthropic 문서 제목은 “Tool use”이고 “function calling이라고도 한다”고 밝힙니다. [OpenAI · Function calling] [Claude · Tool use overview] 이 교재는 두 말을 섞지 않도록 메커니즘 전체를 함수 호출(Function Calling) · 도구 호출(Tool Calling)로 쓰고, 이후에는 주로 “도구 호출”이라 부릅니다.

그럼 “함수”와 “도구”는 같은 말인가? 메커니즘 이름으로는 같지만, OpenAI 문서는 범위를 한 번 더 나눕니다. “도구”는 모델에게 준 기능 전체를 가리키는 넓은 말이고, “함수”는 그중 JSON 스키마(입력 칸의 이름·종류·필수 여부를 적은 형식 명세)로 정의한 도구라는 한 종류입니다. 그 밖에 자유 텍스트를 주고받는 사용자 지정 도구, OpenAI가 직접 제공하는 내장 도구가 있습니다. [OpenAI · Function calling]

4. 도구 호출의 왕복 흐름

도구 호출은 한 번의 질문-답이 아니라 앱과 모델이 여러 번 주고받는 대화입니다. OpenAI 문서는 이를 다섯 단계로, Anthropic 문서는 같은 내용을 stop_reason(모델이 응답을 멈춘 이유)을 기준으로 한 반복문으로 설명합니다. 아래 그림은 “파리 날씨 어때?”라는 질문 하나가 처리되는 전 과정입니다.

같은 흐름을 한 단계씩 넘겨 보며 두 벤더가 각 단계에서 무엇을 주고받는지 확인해 보세요.

1단계 — 도구 목록과 함께 요청

앱이 사용자 메시지와 함께 “쓸 수 있는 도구 목록”을 보냅니다. 두 벤더 모두 요청의 tools 칸에 넣습니다. 이 목록(이름·설명·스키마)은 모델의 컨텍스트에 들어가 입력 토큰으로 계산됩니다.

2단계 — 모델이 도구 호출을 냄

모델이 도구가 필요하다고 판단하면 일반 답 대신 도구 호출을 돌려줍니다. OpenAI 구현 응답에 function_call 항목. Anthropic 구현 stop_reason: "tool_use" 와 tool_use 블록. 한 번에 0개, 1개, 여러 개가 올 수 있으니 여러 개를 가정하고 처리하라고 OpenAI 문서는 권합니다.

3단계 — 앱이 실제로 실행

앱은 호출에서 도구 이름과 인자를 꺼내, 그 이름에 해당하는 내 코드를 실행합니다(데이터베이스 조회, HTTP 호출(인터넷 주소로 다른 서버에 요청 보내기), 파일 쓰기 등). 모델은 내 코드 내용을 결코 받지 않습니다 — 받는 것은 내가 준 스키마와 내가 돌려준 결과뿐입니다.

4단계 — 결과를 붙여 다시 요청

실행 결과를 호출 ID와 짝지어 다시 보냅니다. OpenAI 구현 function_call_output + call_id. Anthropic 구현 user 역할 메시지 안의 tool_result + tool_use_id. 이전 대화와 모델의 호출도 함께 보내야 합니다.

5단계 — 최종 답, 또는 또 호출

모델이 결과를 읽고 최종 답을 쓰거나, 더 필요한 도구를 다시 요청합니다. Anthropic 문서의 기본 모양은 “stop_reason 이 tool_use 인 동안 도구를 실행하고 대화를 이어 간다”는 while 반복문입니다. 그 밖의 멈춤 이유가 오면 루프를 빠져나옵니다.

잘못된 호출필수 인자 location 누락개발 중에는 설명을 더 자세히 고쳐 다시 시도하는 것이 최선. 운영 중에는 오류를 is_error 결과로 돌려주면 모델이 빠진 값을 채워 다시 부릅니다 — 2~3회 고쳐 시도한 뒤 사용자에게 사과합니다. 아예 없애려면 엄격 모드
서버 도구 오류웹 검색의 too_many_requests, max_uses_exceeded, unavailable 등Claude 가 알아서 처리하고 대안 답이나 설명을 줌. 앱이 is_error 를 다룰 필요 없음

잘라낸 결과도 안내를 붙인다. 결과를 자를 때는 “더 좁은 검색을 여러 번 하라”처럼 토큰을 아끼는 방법으로 모델을 이끄는 안내를 덧붙이라고 Anthropic 글은 권합니다. 잘림 안내와 오류 응답은 모델을 필터·페이지 나누기 쪽으로 이끌거나 올바른 입력 형식의 예를 보여 주는 통로가 됩니다.

도구 결과는 믿을 수 없는 입력이다 도구 결과에는 내가 통제하지 못하는 곳의 내용(웹 페이지, 받은 메일, 사용자가 올린 파일, 외부 API)이 자주 섞입니다. 공격자가 그 안에 모델을 딴 데로 이끄는 지시를 숨길 수 있습니다(간접 프롬프트 인젝션). Anthropic 문서는 이런 내용을 시스템 프롬프트나 일반 사용자 글이 아니라 tool_result 블록 안에 두라고 합니다. 자세한 방어는 9장에서 다룹니다. [Claude · Handle tool calls]

재시도는 어디서. 모델이 스스로 고치는 재시도(위 고리)와 달리, 일시적인 네트워크 오류·요청 한도·시간 초과 같은 실패는 기반 계층에서 처리할 수 있습니다. LangChain 문서는 운영 환경에서 개발 때 드물던 실패가 생긴다며, 도구와 업무 로직마다 오류 처리 코드를 두지 않도록 결함 허용 미들웨어(실패해도 다시 시도해 버티게 하는, 실행 중간에 끼어드는 부품)(ToolRetryMiddleware, ModelRetryMiddleware)를 둡니다. [LangChain · Agents] 재시도·시간 초과·대체 경로·멈춤 조건의 전체 설계는 6장에서 다룹니다.

한눈에 정리
  • 도구는 앱과 모델 사이의 계약입니다. 모델은 “이 도구를 이 값으로” 요청만 하고, 실행은 앱(또는 벤더 서버)이 합니다.
  • API는 코드가 정해진 대로 부르고, 도구는 모델이 상황을 보고 골라 부릅니다. 그래서 도구는 API를 감싸되 업무 흐름 단위로, 적은 수로, 신호가 큰 결과를 돌려주게 설계합니다.
  • 함수 호출(OpenAI)과 tool use(Anthropic)는 같은 메커니즘이며 필드 이름만 다릅니다.
  • 흐름은 도구 목록 → 호출 요청 → 실행 → 결과를 붙여 재요청 → 답 또는 또 호출의 루프입니다.
  • 도구 설명이 성능을 가장 크게 좌우하고, 도구가 많으면 이름 공간과 도구 검색으로 필요한 것만 보이게 합니다.
  • 실패는 무엇이 틀렸고 무엇을 해 볼지 담아 돌려주면 모델이 스스로 고칩니다. 도구 결과는 믿을 수 없는 입력으로 다룹니다.

CHAPTER 03

MCP 아키텍처

2장에서 본 도구(Tool)는 "이 프로그램 안에서 모델에게 쥐여 주는 기능"이었습니다. 그런데 회사에 시스템이 수십 개 있고, AI 앱도 여러 개라면 같은 연결을 앱마다 다시 만들어야 합니다. MCP(Model Context Protocol)는 이 연결을 공통 규격으로 만든 공개 명세입니다. 이 장에서는 MCP 를 이루는 세 참여자(호스트·클라이언트·서버), 서버가 내놓는 세 가지 기본 요소(도구·리소스·프롬프트), 메시지를 실어 나르는 두 가지 전송 방식(STDIO·Streamable HTTP), 한 번의 도구 호출이 오가는 순서, 그리고 여러 MCP 서버를 함께 다루는 법을 차례로 봅니다. 기준은 MCP 명세 2026-07-28 판입니다.

MCP 는 무엇이고 왜 생겼나 — Tool vs MCP

MCP 는 AI 애플리케이션을 바깥 시스템에 연결하기 위한 오픈소스 표준(설계도가 공개되어 누구나 보고 쓸 수 있는 규격)입니다 [MCP 소개]. 여기서 바깥 시스템은 세 종류로 소개됩니다 — 파일·데이터베이스 같은 데이터, 검색 엔진·계산기 같은 도구, 미리 짜 둔 프롬프트 같은 작업 흐름. Claude·ChatGPT 같은 AI 비서, Visual Studio Code·Cursor 같은 개발 도구가 MCP 를 지원하므로 "한 번 만들어 여러 곳에 붙이는" 것이 가능해집니다.

비유로 먼저 공식 문서는 MCP 를 AI 애플리케이션용 USB-C 단자에 빗댑니다. 기기마다 다른 충전기를 쓰던 시절에서, 단자 규격 하나로 여러 기기를 꽂게 된 것처럼, AI 앱과 바깥 시스템 사이에도 공통 단자를 두자는 뜻입니다.

실제로는 MCP 는 "어떤 메시지를 어떤 모양으로 주고받는가"를 정한 통신 규약(프로토콜 — 두 프로그램이 대화하는 약속)입니다. 메시지는 JSON-RPC 2.0(JSON 이라는 글자 형식으로 "이 기능을 이 값으로 실행해 줘"와 그 답을 주고받는 규칙)으로 씁니다 [MCP 명세 개요]. 명세는 프로그래밍 언어 지원 방식을 표준화한 Language Server Protocol 에서 영감을 받았다고 밝힙니다 — 그것이 개발 도구 생태계에 언어 지원을 붙이는 방식을 통일했듯, MCP 는 AI 애플리케이션 생태계에 맥락과 도구를 붙이는 방식을 통일하려는 것입니다.

MCP 가 각자에게 주는 이점을 공식 소개는 이렇게 정리합니다.

누구에게무엇이 좋아지나 [MCP 소개]
개발자AI 앱·에이전트를 만들거나 연동할 때 개발 시간과 복잡도가 줄어듭니다.
AI 앱 · 에이전트데이터 소스·도구·앱의 생태계에 접근해 할 수 있는 일이 늘어납니다.
최종 사용자필요하면 내 데이터에 접근하고 나를 대신해 행동하는, 더 능력 있는 AI 앱을 쓰게 됩니다.

도구(Tool)와 MCP 는 다른 층이다

가장 헷갈리는 지점은 "MCP 도구"와 2장의 "도구"가 같은 것이냐입니다. 둘은 층이 다릅니다. MCP 공식 아키텍처 문서는 이렇게 설명합니다 — AI 애플리케이션은 연결된 모든 MCP 서버에서 도구 목록을 받아 하나의 도구 목록으로 합쳐 LLM 에게 보여 주고, LLM 이 도구를 쓰기로 하면 애플리케이션이 그 호출을 가로채 알맞은 MCP 서버로 보내 실행하고 결과를 대화에 돌려줍니다 [MCP 아키텍처 개요]. 즉 모델은 MCP 를 직접 말하지 않습니다. 모델 쪽은 2장의 함수 호출 그대로이고, MCP 는 "그 도구의 정의를 어디서 가져오고 실제 실행을 누구에게 맡기나"를 정합니다. 명세도 "MCP 는 맥락 교환 규약에만 집중하며, AI 애플리케이션이 LLM 을 어떻게 쓰는지는 정하지 않는다"고 못 박습니다.

비교도구(Tool)MCP
무엇인가모델이 부를 수 있는 기능 하나 — 이름 · 설명 · 입력 형식으로 정의도구(와 리소스·프롬프트)를 다른 프로그램에서 가져와 실행하는 공통 규약
누가 다루나모델이 고르고, 애플리케이션이 실행애플리케이션(호스트·클라이언트)과 MCP 서버가 주고받음 — 모델은 직접 쓰지 않음
범위기능 하나도구 + 리소스 + 프롬프트 + 사용자에게 묻기(elicitation) + 변경 알림 + 전송 방식 + 인증
표준인가정의 형식은 벤더 API 마다 다름(2장)공개 명세 — 버전 2026-07-28
예"날씨 조회" 함수 하나를 내 코드에 직접 정의날씨 MCP 서버 하나를 만들어 Claude · VS Code · 사내 에이전트가 모두 연결

언제 적절한가 · 한계. 같은 기능을 여러 AI 앱이 써야 하거나, 남이 만든 서버(예: 서비스 회사가 직접 운영하는 공식 MCP 서버)를 붙이고 싶을 때 MCP 가 힘을 씁니다. 반대로 MCP 는 보안을 대신 지켜 주지 않습니다 — 명세 스스로 "MCP 자체는 이 보안 원칙들을 프로토콜 수준에서 강제할 수 없다"고 적고, 동의 절차와 권한 관리를 구현하는 쪽의 몫으로 둡니다 [MCP 명세 개요]. 보안 요약은 이 장 끝, 자세한 내용은 9장에서 다룹니다.

호스트 · 클라이언트 · 서버 — MCP 전체 구조

MCP 에는 참여자가 셋 있습니다. 이름이 비슷해 헷갈리니 "사람이 보는 것 / 연결 담당 / 기능 제공" 으로 나눠 기억하면 쉽습니다.

MCP 호스트(Host)
사용자가 실제로 쓰는 AI 애플리케이션입니다. 예: Claude Code, Claude Desktop, Visual Studio Code. 클라이언트를 여럿 만들고 관리하며, 연결 허용과 사용자 동의를 결정하고, LLM 연동과 여러 서버에서 모은 맥락을 조정합니다.
MCP 클라이언트(Client)
호스트 안에 있는 연결 담당 부품입니다. 서버 하나와만 전용 연결을 유지합니다(1:1). 요청마다 프로토콜 버전과 자기 기능 목록을 붙여 보내고, 알림 구독을 관리하며, 서버끼리의 경계를 지킵니다.
MCP 서버(Server)
맥락과 기능을 제공하는 프로그램입니다. 도구·리소스·프롬프트를 내놓고, 필요하면 클라이언트에게 사용자 입력을 요청합니다. 내 컴퓨터에서 도는 "로컬" 서버일 수도, 인터넷 너머의 "원격" 서버일 수도 있습니다.

예를 들어 Visual Studio Code(호스트)가 Sentry MCP 서버에 연결하면 그 안에 클라이언트 객체가 하나 생기고, 이어서 로컬 파일 시스템 서버에 연결하면 클라이언트가 하나 더 생깁니다 [MCP 아키텍처 개요]. 서버 수만큼 클라이언트가 있다는 점이 핵심입니다.

설계 원칙 네 가지 — 왜 이렇게 나눴나

명세는 이 구조가 다음 원칙에서 나왔다고 설명합니다 [MCP 명세 아키텍처]. 결국 "복잡한 일은 호스트가, 서버는 작고 단순하게"입니다.

원칙뜻
서버는 아주 만들기 쉬워야 한다복잡한 조정은 호스트가 맡고, 서버는 잘 정의된 기능 하나에 집중합니다.
서버는 조합하기 쉬워야 한다서버마다 자기 기능만 독립적으로 제공하고, 여러 서버를 자연스럽게 함께 씁니다.
서버는 대화 전체를 읽거나 다른 서버를 "들여다볼" 수 없어야 한다서버는 필요한 맥락만 받고, 전체 대화 기록은 호스트에 남습니다. 서버 사이 상호작용은 호스트가 통제합니다.
기능은 점진적으로 더할 수 있어야 한다핵심 규약은 최소한만 정하고, 추가 기능은 필요할 때 협상합니다. 서버와 클라이언트가 따로 발전해도 하위 호환(새 판이 옛 판과도 계속 함께 동작하는 것)을 유지합니다.

두 개의 층 — 데이터 층과 전송 층

MCP 는 안쪽의 데이터 층과 바깥쪽의 전송 층으로 나뉩니다 [MCP 아키텍처 개요]. 데이터 층은 "무슨 말을 하나"(기능 확인, 도구·리소스·프롬프트, 알림)를, 전송 층은 "어떤 통로로 실어 나르나"(연결 맺기, 메시지 구분, 인증)를 정합니다. 전송 방식이 달라도 데이터 층의 메시지는 똑같습니다 — 그래서 아래 기본 요소와 전송 방식을 따로 볼 수 있습니다.

프롬프트 (Prompts)사용자가 정함미리 만든 지시 템플릿. 사용자가 골라서 실행"휴가 계획 세우기", "회의 요약" 슬래시 명령prompts/list · prompts/get

데이터베이스 서버 하나를 예로 들면, 질의를 실행하는 도구, DB 구조를 담은 리소스, 그 도구를 잘 쓰는 예시가 든 프롬프트를 함께 내놓을 수 있습니다 [MCP 아키텍처 개요]. 각 요소에는 목록을 얻는 */list 와 내용을 얻는 메시지가 있고, 도구에만 실행 메시지(tools/call)가 있습니다. 목록은 그때그때 바뀔 수 있어서, 클라이언트는 먼저 목록을 받은 뒤 씁니다.

무엇: 모델이 자동으로 발견하고 부르는 함수입니다. 각 도구는 이름·설명·입력 형식(JSON Schema(데이터 모양을 적는 표준 형식 — "이 칸은 글자, 이 칸은 필수"))으로 정의되고, 출력 형식(outputSchema)을 선택적으로 적을 수 있습니다.

사람의 통제: 명세는 "신뢰와 안전을 위해 도구 호출을 거부할 수 있는 사람이 늘 있어야 한다(SHOULD(명세의 ‘권장’ 표시. ‘반드시’는 MUST, ‘하면 안 됨’은 MUST NOT))"고 하고, 어떤 도구가 모델에 노출되는지 보여 주는 화면, 호출 시 눈에 띄는 표시, 확인 창을 권합니다 [MCP 명세 Tools]. 사용자 승인 창, 안전한 작업의 사전 승인 설정, 실행 기록 화면도 예로 듭니다 [MCP 서버 개념].

결과: 글·이미지·오디오·리소스 링크·내장 리소스를 여러 개 담는 content, 또는 정해진 형식의 데이터를 담는 structuredContent 로 돌려줍니다.

무엇: 파일·API·DB 등에서 꺼낸 맥락 데이터입니다. 주소(URI(자원을 가리키는 주소 문자열 — 예: file:///문서/a.md))마다 하나씩 있고, 데이터 종류(MIME 타입(글·이미지 같은 데이터 종류를 나타내는 표준 표시))를 밝힙니다.

애플리케이션이 정한다는 뜻: 리소스를 받은 뒤 어떻게 쓸지는 애플리케이션 몫입니다 — 일부만 고르거나, 임베딩으로 검색하거나, 통째로 모델에 넘깁니다. 화면에서는 폴더처럼 펼쳐 보이거나, 검색·필터, 자동 포함, 직접 선택 같은 방식을 씁니다 [MCP 서버 개념].

두 가지 발견 방식: 고정 주소를 가리키는 직접 리소스(calendar://events/2024)와, 값을 끼워 넣는 리소스 템플릿(travel://activities/{city}/{category}). 템플릿은 입력 중 자동 완성("Par" → "Paris")을 지원합니다.

무엇: 서버가 제공하는 재사용 지시 템플릿입니다. 인자(예: 도시·기간·예산)를 받아 메시지 묶음을 만들어 줍니다.

사용자가 정한다는 뜻: 명세는 "누가 언제 쓰는지를 정한다는 뜻이지, 누가 내용을 쓰는지가 아니다 — 내용은 서버가 정한다"고 짚습니다 [MCP 명세 Prompts]. 보통 / 를 쳐서 고르는 슬래시 명령, 명령 팔레트, 전용 버튼으로 노출됩니다.

장점: 자유 문장 대신 "템플릿 선택 → 정해진 칸 입력 → 같은 흐름으로 실행"이 되어 결과가 일정해집니다.

한 번의 도구 호출이 오가는 과정 — 수명 주기와 "상태 없음"

2026-07-28 판의 MCP 는 상태 없는(stateless) 프로토콜입니다. 뜻은 "요청 하나에 처리에 필요한 정보가 모두 들어 있어서, 서버는 이전 요청에서 아무것도 추측하지 않는다"입니다 [MCP 명세 기본 프로토콜]. 그래서 예전처럼 연결을 맺자마자 initialize 로 인사하고 기능을 맞추는 단계가 없어졌고, 모든 요청이 _meta 칸에 프로토콜 버전과 클라이언트 기능 목록을 직접 싣습니다(필수). 클라이언트 이름·버전도 매번 붙이기를 권합니다.

비유로 먼저 옛 방식은 단골 가게였습니다 — 처음 들어갈 때 "저 누구고 이런 거 됩니다" 하고 인사하면, 그다음 주문부터는 가게가 나를 기억했습니다. 새 방식은 무인 주문기입니다 — 주문할 때마다 "버전 · 내가 할 수 있는 것"을 주문서에 같이 적어 냅니다.

실제로는 서버가 같은 연결·같은 프로세스에서 온 이전 요청에 기대어 맥락(기능·버전·클라이언트 정체)을 정하면 안 되고(MUST NOT), 여러 요청에 걸친 상태는 클라이언트가 매번 넘기는 명시적 식별자로만 이어야 합니다(MUST). 열린 STDIO 프로세스도 "대화"나 "세션"이 아닙니다 — 한 통로에 서로 관계없는 요청이 섞여 올 수 있습니다.

① ~ ② 발견(선택) — 클라이언트는 다른 요청보다 먼저 server/discover 를 보내 서버가 지원하는 버전·기능·이름을 한 번에 받을 수 있습니다. 모든 서버는 이것을 구현해야 하지만(MUST), 부르는 것은 선택입니다 — 바로 다른 요청을 보내고 버전 오류가 오면 고쳐도 됩니다. 답에는 "이 서버를 잘 쓰는 법"을 LLM 에게 알려 주는 instructions 가 들어갈 수 있습니다 [MCP 명세 Discovery].
③ ~ ④ 도구 목록 — tools/list 로 도구 정의를 받습니다. 답에는 ttlMs(몇 밀리초 동안 믿어도 되는지)와 cacheScope(공용 중간 장비가 캐시(저장해 두고 다시 쓰기)해도 되는지)가 붙어, 매번 다시 묻지 않아도 됩니다. 호스트는 여러 서버의 목록을 합쳐 모델에 줄 도구 목록을 만듭니다.
⑤ ~ ⑥ 모델의 선택 — 여기부터는 2장의 함수 호출입니다. 모델이 도구 이름과 인자를 내놓으면, 호스트가 그 도구가 어느 서버 것인지 찾아 해당 클라이언트에 넘깁니다. 명세는 민감한 작업이면 사용자 확인을, 서버로 보내기 전 입력 값을 사용자에게 보여 주기를 권합니다(데이터 유출 방지).
⑦ ~ ⑩ 실행과 추가 입력 — 클라이언트가 tools/call 을 보냅니다. 서버가 사용자 확인이나 정보가 더 필요하면 InputRequiredResult 를 돌려주고, 클라이언트는 사용자 답을 붙여 새 요청 번호로 같은 요청을 다시 보냅니다. 오래 걸리는 작업은 같은 응답 스트림으로 진행 알림을 받을 수 있습니다.
⑪ ~ ⑫ 결과 — 모든 결과에는 resultType 이 붙습니다("complete" 또는 "input_required"). 도구가 실패했으면 isError: true 와 고칠 수 있는 설명이 오고, 클라이언트는 이를 모델에 넘겨 스스로 고치게 합니다. 명세는 도구 호출에 시간 제한과 감사용 기록(누가 무엇을 했는지 남기는 기록)을 두라고 권합니다.
⑬ ~ ⑮ 변경 알림 — 서버 도구가 바뀌는 것을 알고 싶으면 클라이언트가 subscriptions/listen 으로 오래 열린 스트림을 엽니다. 서버가 listChanged 를 지원한다고 밝혔다면, 목록이 바뀔 때 알림이 오고 클라이언트는 목록을 다시 받습니다. 알림은 "최선 노력"이라 놓칠 수 있으므로 주기적으로 다시 묻는 것도 병행하라고 합니다 [MCP 아키텍처 개요].

한계·주의. 상태가 없다는 것은 장점(서버를 여러 대로 늘리거나 재시작해도 요청을 다시 보내면 됨)이자 설계 부담입니다. 장바구니처럼 이어지는 작업은 서버가 핸들을 만들어 도구 인자로 주고받게 설계해야 합니다(세부 규칙 참고). 또 응답 스트림이 끊기면 진행 중이던 요청은 사라지므로, 클라이언트는 새 번호로 다시 보내야 합니다(MUST) [MCP 명세 변경 이력].

CHAPTER 04

프롬프트 · 스킬 · 컨텍스트 — 에이전트에게 “무엇을, 언제” 보여 줄 것인가

에이전트가 얼마나 일을 잘하느냐는 모델이 똑똑한지만으로 정해지지 않습니다. 모델이 그 순간 무엇을 보고 있느냐가 결과를 크게 좌우합니다. 이 장에서는 모델에게 주는 글인 프롬프트와 에이전트 지시문, 필요할 때만 꺼내 읽는 업무 설명서인 스킬, 그리고 이 모든 것을 한정된 공간에 어떻게 골라 담을지 정하는 컨텍스트 엔지니어링을 차례로 다룹니다. 스킬·도구·MCP 가 서로 어떻게 다르고 어떻게 함께 쓰이는지도 정리합니다.

1. 프롬프트와 프롬프트 엔지니어링

프롬프트(모델에게 주는 입력 글)는 모델에게 건네는 모든 입력이고, 프롬프트 엔지니어링은 모델이 요구 사항에 맞는 결과를 꾸준히 내도록 지시를 잘 쓰는 일입니다. OpenAI 문서는 “출력의 품질은 프롬프트를 얼마나 잘 쓰느냐에 달려 있다”고 하고, 모델의 출력이 매번 똑같지 않기(비결정적) 때문에 프롬프트 작성은 “기술이자 과학”이라고 설명합니다 [OpenAI Prompting · Text generation]. Anthropic 은 프롬프트 엔지니어링을 “LLM 지시문을 가장 좋은 결과가 나오게 쓰고 정리하는 방법”이라고 정의합니다 [Effective context engineering].

왜 필요할까요? 같은 모델이라도 무엇을, 어떤 순서로, 어떤 예시와 함께 말하느냐에 따라 결과가 달라집니다. 게다가 모델마다, 같은 계열의 다른 판(스냅숏)마다 같은 프롬프트에 다르게 반응할 수 있습니다. 그래서 OpenAI 는 실제 서비스에서는 모델 판을 고정하고, 프롬프트 동작을 재는 시험·평가 묶음을 만들어 두라고 권합니다 [OpenAI Text generation].

언제 프롬프트로 고치는 게 맞을까요? 모든 실패가 프롬프트 문제는 아닙니다. Anthropic 문서는 “응답 속도나 비용은 프롬프트보다 다른 모델을 고르는 것으로 더 쉽게 나아질 때가 있다”고 짚습니다 [Prompt engineering overview]. 즉 프롬프트 엔지니어링은 지시로 바꿀 수 있는 성공 기준(말투, 형식, 빠뜨리는 항목, 규칙 지키기 등)에 쓰는 도구입니다.

벤더프롬프트를 다루는 관점 (원문 요지)
Anthropic기법(명확하게 쓰기·예시, XML(<태그>…</태그> 로 글 구역을 감싸는 표시법) 로 구조 나누기, 역할 부여, 생각하게 하기, 프롬프트 연결)은 “Prompting best practices” 문서 한 곳에 계속 갱신한다. 시작 전에 성공 기준과 평가를 먼저 세운다.
OpenAI전체적인 말투·역할은 시스템(개발자) 메시지에, 그 일에만 필요한 세부와 예시는 사용자 메시지에 둔다. 예시(few-shot)는 짧은 목록으로 묶어 팀이 훑어보고 고치기 쉽게 한다. 프롬프트를 애플리케이션 코드처럼 다룬다.

프롬프트는 “코드처럼” 관리합니다. OpenAI 는 프롬프트를 이름 붙인 코드 모듈에 두고, 바뀌는 값은 입력 형식이 정해진 함수 인자로 받으며, 프롬프트 변경을 그 변경이 지원하는 제품 동작과 같은 검토 요청(PR)에서 함께 검토하라고 권합니다. 실제 사용 예로는 “고객 응대 답장” 프롬프트를 prompts/supportReply.ts 같은 파일에 버전 관리하고, git 이력·검토·릴리스 태그(배포한 판마다 붙이는 이름표)·기능 플래그(코드를 고치지 않고 기능을 켜고 끄는 스위치)로 비교하고 되돌리는 방식을 듭니다 [OpenAI Prompting].

주의할 점 프롬프트를 고쳐 한 사례가 좋아져도 다른 사례가 나빠질 수 있습니다. 그래서 “대표 사례 묶음으로 반복 측정”이 빠지면 프롬프트 엔지니어링은 감에 의존하게 됩니다. 또 모델 판이 바뀌면 같은 프롬프트의 결과도 바뀔 수 있으니, 모델을 올릴 때도 평가를 다시 돌립니다 [OpenAI Text generation]. 평가는 8장 평가에서 자세히 다룹니다.

스킬(Skill)은 에이전트에게 특정 분야의 업무 방법을 가르치는 재사용 가능한 꾸러미입니다. Anthropic 문서의 정의로는 “지시문, 메타데이터(이름·설명), 그리고 필요하면 스크립트·템플릿 같은 자료를 한 폴더에 묶은 것”이며, 관련 있을 때 Claude 가 알아서 꺼내 씁니다. 문서는 이를 “새 팀원을 위해 만드는 온보딩 안내서처럼 정리된 폴더”에 빗댑니다 [Agent Skills].

5. 스킬 · 도구 · MCP 의 관계 (비교 — 스킬 vs 도구)

세 가지는 이름이 비슷하게 “에이전트의 능력을 넓힌다”고 소개되지만, 하는 일의 층이 다릅니다. 한 줄로 정리하면 — 스킬은 “어떻게 하는지”(지식·절차), 도구는 “실제로 하는 손”(행동), MCP 는 “도구와 자료를 에이전트에 꽂는 표준 규격”(연결)입니다.

  • 도구(2장): 모델이 부를 수 있는 기능. 모델은 “이 도구를 이 입력으로 불러 달라”고 요청만 하고, 실제 실행은 애플리케이션이 하고 결과를 돌려줍니다. 도구는 이름·설명·인자 이름·인자 설명이 있어야 하며, 이것들은 단순한 정보가 아니라 모델이 언제·어떻게 쓸지 판단하는 근거입니다 [LangChain Context engineering].
  • 스킬: 업무 절차와 지식 꾸러미. 스킬 자체는 아무것도 실행하지 못하고, Claude 가 bash·코드 실행이라는 도구를 써서 스킬 파일을 읽고 스크립트를 돌립니다. 그래서 Claude API 에서 스킬을 쓰려면 코드 실행 도구가 반드시 필요합니다 [Agent Skills].

6. 컨텍스트 엔지니어링 — 한정된 책상 위에 무엇을 올릴까

컨텍스트(모델이 한 번에 보는 글 전체)는 LLM 이 답을 만들 때 함께 들어가는 토큰의 묶음입니다. 컨텍스트 엔지니어링은 Anthropic 의 정의로 “추론하는 동안 가장 알맞은 토큰(정보)의 묶음을 고르고 유지하는 전략들 — 프롬프트 밖에서 들어오는 모든 정보까지 포함해서”입니다. LangChain 은 “LLM 이 일을 해낼 수 있게 알맞은 정보와 도구를 알맞은 형식으로 주는 것”이라고 하고, 이것이 AI 엔지니어의 첫째 일이라고 말합니다 [Effective context engineering · LangChain Context engineering].

왜 등장했나요? 초기 LLM 활용은 한 번에 분류하거나 글을 만드는 일이 많아 “프롬프트를 잘 쓰는 법”이 핵심이었습니다. 그런데 에이전트는 루프를 돌며 여러 번 추론하고 오래 일합니다. 그 사이 시스템 지시문·도구·MCP·외부 데이터·대화 기록이 계속 쌓이기 때문에 전체 컨텍스트 상태를 관리할 전략이 필요해졌습니다. Anthropic 은 컨텍스트 엔지니어링을 프롬프트 엔지니어링의 “자연스러운 다음 단계”로 봅니다. 프롬프트 작성이 한 번 하는 일이라면, 컨텍스트 엔지니어링은 모델에 무엇을 넘길지 정할 때마다 되풀이되는 일입니다 [Effective context engineering].

컨텍스트는 왜 “아껴 써야 하는 자원”인가

Anthropic 은 LLM 도 사람처럼 어느 지점을 넘으면 집중을 잃는다고 설명합니다. 긴 글 속에서 한 조각을 찾게 하는 시험(needle-in-a-haystack)에서 컨텍스트 부패(context rot: 컨텍스트 창 속 토큰이 늘수록 그 안의 정보를 정확히 떠올리는 능력이 떨어지는 현상)가 관찰되었고, 정도의 차이는 있어도 모든 모델에서 나타납니다. 그래서 컨텍스트는 “한계 효용이 줄어드는 유한한 자원”(더 넣을수록 하나당 얻는 이득이 작아진다는 뜻)이고, 모델에는 “주의력 예산”이 있어 새 토큰 하나하나가 그 예산을 조금씩 씁니다 [Effective context engineering].

구조적 이유
LLM 의 기반인 트랜스포머(오늘날 LLM 이 쓰는 신경망 구조)는 모든 토큰이 다른 모든 토큰을 봅니다. 토큰이 n 개면 관계는 n² 개 — 길어질수록 주의가 얇게 퍼집니다.
학습 데이터
모델은 짧은 글을 더 많이 보며 학습했기 때문에, 컨텍스트 전체에 걸친 관계를 다룬 경험이 상대적으로 적습니다.
절벽이 아닌 기울기
긴 컨텍스트에서도 모델은 여전히 유능하지만, 정보 찾기와 먼 거리 추론의 정밀도가 조금씩 떨어집니다.

LangChain 도 같은 결론에 닿습니다 — 에이전트가 실패하는 이유는 ① 모델 능력이 모자라거나 ② 알맞은 컨텍스트가 전달되지 않았거나 둘 중 하나인데, 대개는 ②라는 것입니다 [LangChain Context engineering]. 지도 원칙은 하나입니다: 원하는 결과가 나올 가능성을 가장 높이는, 가장 작은 고신호 토큰 묶음을 찾아라(‘고신호’는 쓸모 있는 정보가 촘촘하다는 뜻) [Effective context engineering].

필요한 정보를 언제 가져오나 — 미리 vs 그때그때

Anthropic 은 많은 AI 앱이 추론 전에 임베딩 기반 검색으로 중요한 컨텍스트를 미리 찾아 넣는다고 설명하고(→ 5장 RAG), 점점 많은 팀이 여기에 “그때그때”(just in time) 전략을 더한다고 말합니다. 모든 데이터를 미리 처리하는 대신 파일 경로·저장된 쿼리(데이터베이스에 보내는 조회 명령)·웹 링크 같은 가벼운 식별자만 들고 있다가, 실행 중에 도구로 필요한 부분만 불러오는 방식입니다. Claude Code 는 큰 데이터베이스를 분석할 때 표적 쿼리를 쓰고 head·tail(파일의 앞·뒤 몇 줄만 보는 명령) 같은 명령으로 데이터 전체를 컨텍스트에 싣지 않고 다룹니다. 폴더 구조·이름 규칙·시각 같은 메타데이터도 “이 파일이 무엇에 쓰이는지” 알려 주는 신호가 됩니다 [Effective context engineering].

Anthropic 의 결론은 “작동하는 가장 단순한 것을 하라”입니다 [Effective context engineering]. 이 장의 스킬(설명만 먼저, 본문은 필요할 때)도 같은 “점진적 공개” 원리입니다.

오래 걸리는 일 — 컨텍스트 창보다 긴 작업

수십 분에서 몇 시간 걸리는 일(큰 코드 이전(많은 코드를 새 구조·새 도구로 옮기는 작업), 폭넓은 조사)은 토큰 양이 컨텍스트 창을 넘습니다. 원문은 “더 큰 컨텍스트 창을 기다리는 것”도 답이 아니라고 봅니다 — 어떤 크기든 컨텍스트 오염과 관련성 문제는 남기 때문입니다. 대신 세 가지 기법을 제시합니다.

압축: 컨텍스트 창 한계에 가까워진 대화를 요약해, 그 요약으로 새 컨텍스트 창을 시작합니다. 보통 가장 먼저 쓰는 수단입니다. Claude Code 는 대화 기록을 모델에 넘겨 핵심(설계 결정, 풀리지 않은 버그, 구현 세부)은 남기고 중복된 도구 출력·메시지는 버린 뒤, 그 요약과 최근에 연 파일 5개로 이어 갑니다. 어려운 점은 무엇을 남기고 버릴지 — 너무 공격적으로 줄이면 나중에야 중요해지는 미묘한 맥락을 잃습니다. 원문은 먼저 빠짐없이 담게(재현율) 만들고, 그다음 군더더기를 줄이라고(정밀도) 권합니다. 가장 가볍고 안전한 압축은 오래된 도구 결과 지우기(tool result clearing)입니다.

구조화된 메모(에이전트 메모리): 에이전트가 컨텍스트 창 밖에 메모를 정기적으로 써 두고 나중에 다시 불러옵니다. 할 일 목록이나 NOTES.md 같은 단순한 방식으로 수십 번의 도구 호출 동안 진행 상황과 의존 관계를 놓치지 않습니다. 원문의 사례로, 포켓몬 게임을 하는 Claude 는 수천 단계에 걸친 정확한 집계·지도·전투 전략 메모를 남기고, 컨텍스트가 초기화된 뒤 자기 메모를 읽고 몇 시간짜리 훈련을 이어 갔습니다. 이 기법을 제품으로 만든 것이 메모리 도구입니다(→ 5장).

하위 에이전트 구조: 한 에이전트가 프로젝트 전체 상태를 붙들지 않고, 전문 하위 에이전트가 깨끗한 컨텍스트 창으로 좁은 일을 맡습니다. 하위 에이전트는 수만 토큰 넘게 탐색해도 압축된 요약(보통 1,000~2,000 토큰)만 돌려주고, 주 에이전트는 결과를 종합하는 데 집중합니다. 원문은 복잡한 조사 과제에서 단일 에이전트보다 크게 나았다고 보고합니다(→ 7장).

한계와 주의 컨텍스트를 줄이는 기법은 모두 “무엇을 버릴지” 판단을 포함합니다. 압축은 나중에 중요해질 정보를 잃을 수 있고, 그때그때 탐색은 느리고 길잡이가 없으면 헤맵니다. 원문은 모델이 좋아질수록 덜 규범적인(덜 손으로 짜는) 설계가 가능해진다고 보지만, 컨텍스트를 귀하고 유한한 자원으로 다루는 원칙은 계속 중심에 남는다고 맺습니다 [Effective context engineering].

CHAPTER 05

메모리와 RAG — 컨텍스트 창 밖에 지식을 두고 꺼내 쓰기

4장에서 컨텍스트 창은 좁고 귀하다는 것을 봤습니다. 그렇다면 대화가 끝난 뒤에도 남아야 할 정보, 처음부터 창에 다 넣기엔 너무 많은 회사 문서는 어디에 둘까요? 이 장은 그 두 가지 답 — 에이전트가 스스로 겪은 것을 기억하는 메모리와 문서 더미에서 관련 조각을 찾아 읽는 RAG — 를 다루고, 그 밑바탕인 임베딩·벡터 저장소를 설명합니다. 마지막에는 지시문·스킬·도구·MCP·메모리·RAG 가 한 에이전트 안에서 어떻게 함께 쓰이는지 한 그림으로 묶습니다.

1. 메모리의 개념과 종류 — 단기 메모리와 장기 메모리

메모리(Memory)는 LangChain 문서의 정의로 “이전 상호작용에 대한 정보를 기억하는 시스템”입니다. 에이전트에게 메모리가 중요한 이유는 세 가지 — 이전 대화를 기억하고, 피드백에서 배우고, 사용자 선호에 맞추기 위해서입니다. 사용자와 여러 번 주고받는 복잡한 일일수록 효율과 만족도 모두에 꼭 필요해집니다 [LangChain Short-term memory].

LLM 은 원래 호출마다 새로 시작합니다(1장). 그래서 “기억”은 모델 안이 아니라 모델 바깥의 저장소에 있고, 필요할 때 컨텍스트로 다시 넣어 주는 방식으로 동작합니다. 범위에 따라 두 가지로 나눕니다.

단기 메모리 — 한 대화 안의 기억

단기 메모리는 하나의 스레드(thread: 이메일이 한 대화로 묶이듯 여러 번의 주고받음을 묶은 단위) 안에서 이전 상호작용을 기억합니다. 가장 흔한 형태는 대화 기록입니다 [LangChain Short-term memory]. 문제는 대화가 길어질 때입니다. 기록 전체가 컨텍스트 창에 다 안 들어가 맥락을 잃거나 오류가 날 수 있고, 들어가더라도 대부분의 LLM 은 오래되거나 주제를 벗어난 내용에 “정신이 팔려” 성능이 떨어지고 응답도 느리고 비싸집니다. 그래서 오래된 정보를 지우거나 “잊는” 기법이 필요합니다.

잘라내기 (trim)
앞이나 뒤의 메시지 N 개를 LLM 호출 전에 뺍니다. 토큰 수를 세어 한도에 가까워지면 자릅니다.
지우기 (delete)
상태에서 특정 메시지나 전체 기록을 영구히 지웁니다.
요약하기 (summarize)
앞의 메시지를 요약으로 바꿉니다. 잘라내기·지우기는 정보를 잃을 수 있어서 요약이 더 정교한 방법입니다.
직접 만든 전략
메시지 걸러 내기 등 상황에 맞는 방식.

LangChain 구현 단기 메모리는 에이전트 상태(state)의 일부로 관리되고, 체크포인터(checkpointer: 상태를 데이터베이스나 메모리에 저장해 두는 장치)로 저장되어 언제든 그 스레드를 다시 이어 갈 수 있습니다. 에이전트가 호출되거나 한 단계(예: 도구 호출)가 끝날 때 갱신되고, 각 단계 시작 때 읽힙니다. 실제 서비스에서는 데이터베이스 기반 체크포인터를 씁니다 [LangChain Short-term memory]. 체크포인트는 6장에서 실행 제어 관점으로 다시 봅니다.

Google ADK 구현 ADK 는 Session(지금 진행 중인 대화 한 줄기, 메시지와 행동을 시간순으로 담은 Events), State(session.state — 그 대화 동안만 필요한 데이터를 적는 “메모장”, 예: 이번 대화의 장바구니), Memory(여러 세션에 걸쳐 검색할 수 있는 정보)를 구분합니다. Session·State 가 “한 대화 동안의 단기 메모리”이고, Memory 가 “장기 지식”입니다 [ADK Sessions · ADK Memory].

ADK 는 같은 session.state 안에서도 접두어로 범위를 나눕니다. 그래서 user: 키는 “상태”이면서 사실상 사용자 단위로 오래 남는 정보가 됩니다. 저장이 실제로 남는지는 고른 저장 서비스에 달려 있습니다(메모리 안 구현은 앱을 다시 켜면 사라짐) [ADK State].

장기 메모리 — 대화를 넘어 남는 기억

장기 메모리는 여러 대화·세션에 걸쳐 정보를 저장하고 언제든 다시 불러옵니다. 한 스레드에 묶인 단기 메모리와 달리 스레드를 넘어 남습니다 [LangChain Long-term memory]. 벤더별로 구현 모양이 꽤 다릅니다.

LangChain 구현 장기 메모리는 LangGraph 저장소(store)에 JSON 문서로 저장됩니다. 각 기억은 namespace(폴더 같은 것 — 보통 사용자·조직 ID 를 넣음)와 key(파일 이름 같은 것)로 정리되어 계층적으로 관리되고, 내용 필터로 namespace 를 가로질러 찾을 수도 있습니다. 저장소에 임베딩 색인을 붙이면 “언어 선호” 같은 질의로 벡터 유사도 순 검색도 됩니다. 도구가 실행 중에 저장소를 읽고 씁니다. 원문은 기억의 종류(semantic·episodic·procedural)와 기억을 쓰는 전략을 별도 개념 문서로 안내하지만, 그 문서는 이 교재의 수집 범위 밖입니다 [LangChain Long-term memory].

Google ADK 구현 MemoryService 가 “검색할 수 있는 장기 지식 저장소”를 관리합니다. 넣기: 끝난 세션 전체를 넣는 add_session_to_memory, 일부 이벤트만 넣는 add_events_to_memory, 특정 사실을 직접 넣는 add_memory. 찾기: search_memory 로 질의해 관련 조각을 받습니다(보통 도구를 통해). 미리 만든 도구 두 개 — 매 턴 시작에 자동으로 기억을 불러오는 Preload memory, 에이전트가 필요하다고 판단할 때 부르는 Load memory [ADK Memory].

Anthropic 구현 메모리 도구(memory tool)는 기억을 파일 디렉터리(폴더)로 다룹니다. Claude 는 /memories 아래에 파일을 만들고·읽고·고치고·지우며, 세션 사이에 남는 지식을 쌓습니다. 이 도구는 클라이언트 쪽에서 동작합니다 — Claude 는 파일 작업을 요청만 하고, 실제 실행은 내 애플리케이션이 내 저장소(사용자별 디렉터리, 데이터베이스 키 등)에 대해 합니다. 그래서 데이터를 어디에 어떻게 둘지 내가 통제합니다 [Claude Memory tool].

Microsoft 구현 AgentSession 으로 호출과 호출 사이에 대화 맥락을 유지합니다. 세션을 만들어 매 실행에 넘기고, 직렬화(저장하거나 보낼 수 있는 글·바이트 형태로 바꾸기)해 저장했다가 나중에 되살리거나 서비스 쪽 대화 ID 로 이어 갑니다. 관련 기능으로 컨텍스트 제공자(Context Providers), 컨텍스트 압축(Context Compaction), 저장(Storage), 대화 기록 메모리 제공자(Chat History Memory Provider)를 둡니다 [MSAF Conversations & Memory].

메모리 도구는 실제로 어떻게 움직이나 (Anthropic 예)

메모리 도구가 켜져 있으면 Claude 는 일을 시작하기 전에 먼저 메모리 디렉터리를 확인하고, 일하면서 알게 된 것을 파일에 적고, 다음 대화에서 다시 읽어 이전 일을 이어 갑니다. API 는 이 도구가 있으면 시스템 프롬프트에 아래와 같은 지시를 자동으로 넣습니다 [Claude Memory tool].

자동으로 들어가는 지시 (원문 요지를 우리말로)
중요: 무엇보다 먼저 메모리 디렉터리를 확인하라.
메모리 규칙: ① memory 도구의 view 로 이전 진행을 확인한다. ② 일을 하면서 상태·진행·생각을 메모리에 기록한다.
중단을 가정하라: 컨텍스트 창은 언제든 초기화될 수 있으므로, 메모리에 기록하지 않은 진행은 잃을 수 있다.
메모리의 한계와 주의 — 보안은 내 책임 메모리 도구의 파일 작업은 내 애플리케이션이 실행하므로 안전장치도 내 몫입니다 [Claude Memory tool]. ① 민감 정보: Claude 는 보통 민감 정보를 메모리에 쓰기를 거절하지만, 더 확실히 하려면 쓰기 전에 민감 데이터를 걸러 내는 검증을 둡니다. ② 크기: 파일 크기에 상한을 두고, view 가 돌려주는 글자 수도 제한합니다. ③ 만료: 오래 쓰지 않은 기억 파일은 주기적으로 지웁니다. ④ 경로 조작: /memories/../../secrets.env 같은 경로로 디렉터리 밖 파일에 닿을 수 있으니, 모든 명령의 모든 경로를 검증합니다(/memories 로 시작하는지, 정규화한 경로가 디렉터리 안인지, ../·URL 인코딩된 %2e%2e%2f 거부). 기억이 오래되면 틀린 정보가 될 수 있다는 점도 기억하세요 — 원문이 “완료는 검증 뒤에만 표시”를 강조하는 이유입니다.

3. RAG — 찾아 읽고 답하기

RAG(Retrieval-Augmented Generation, 검색 증강 생성: 질문과 관련된 자료를 먼저 찾아 모델 입력에 덧붙인 뒤 답을 만들게 하는 방식)는 모델이 학습하지 않은 사실을 답에 쓰게 하는 대표적인 방법입니다. OpenAI 문서는 출발점을 이렇게 설명합니다 — 모델이 응답에 필요한 핵심 사실을 학습하지 못한 경우가 많고, 한 가지 해결책은 추가 정보를 컨텍스트 창에 넣는 것인데 이는 많은 경우 효과적이지만 토큰 비용이 커진다. 그래서 임베딩 기반 검색으로 관련 부분만 골라 넣는 방식과 저울질하게 됩니다 [OpenAI Vector embeddings].

OpenAI 의 Retrieval API 는 내 데이터에 대해 의미 검색(semantic search: 키워드가 거의 겹치지 않아도 뜻이 비슷한 결과를 찾는 검색)을 하게 해 주고, “그 자체로도 유용하지만 모델과 결합해 응답을 종합할 때 특히 강력하다”고 설명합니다. 검색 결과와 원래 질문을 모델에 함께 주면 근거 있는(grounded) 응답을 받습니다 [OpenAI Retrieval]. 아래 단계를 넘겨 보세요.

RAG 의 변형 — 한 번 찾기 vs 에이전트가 여러 번 찾기

Anthropic 은 멀티 에이전트 조사 시스템을 설명하며 전통적인 RAG 를 “정적 검색”이라고 부릅니다 — 입력 질문과 가장 비슷한 조각 묶음을 가져와 그것으로 답을 만드는 방식입니다. 이와 달리 자기네 구조는 새로 찾은 내용에 맞춰 검색을 바꾸고 결과를 분석하는 여러 단계의 동적 검색을 쓴다고 대비합니다 [How we built our multi-agent research system]. 4장에서 본 “그때그때(just in time)” 탐색도 같은 흐름입니다. 에이전트에게 검색을 도구로 주면 모델이 “더 찾아볼지”를 스스로 정할 수 있습니다 — ADK 의 Load memory 도구, OpenAI 의 file search 도구가 그런 예입니다.

5. 비교 — 메모리 vs RAG (그리고 두 데이터 흐름)

메모리와 RAG 는 둘 다 “창 밖에 두었다가 필요할 때 꺼내 컨텍스트에 넣는다”는 점이 같고, 기술도 겹칠 수 있습니다 — LangChain 장기 메모리 저장소는 벡터 유사도 검색을 하고, ADK 는 RAG 기반 메모리 서비스(VertexAiRagMemoryService)까지 제공합니다 [LangChain Long-term memory · ADK Memory]. 그래서 둘을 가르는 기준은 검색 기술이 아니라 무엇을 담고, 그 정보가 어디서 생겨 어떻게 바뀌느냐입니다.

ADK 문서는 Memory 를 “여러 과거 세션에 걸치거나 외부 데이터 출처를 포함할 수도 있는 검색 가능한 저장소”라고 정의합니다. 또 기본 메모리 서비스 하나에 더해, 도구 안에서 두 번째 메모리 서비스(예: 문서 말뭉치용 RAG 서비스)를 따로 만들어 “별도 지식 기반”으로 쓸 수 있다고 안내합니다 [ADK Sessions · ADK Memory]. 즉 ADK 에서는 문서 검색도 “메모리 서비스”라는 같은 틀로 다룰 수 있어서, 이 교재의 메모리/RAG 구분은 데이터의 출처와 수명에 따른 개념 구분이라는 점을 기억하세요.

4장과 5장에서 본 여섯 가지 — 지시문, 스킬, 도구, MCP, 메모리, RAG — 는 따로 노는 기능이 아니라 모두 컨텍스트 창이라는 한 자리를 두고 “언제, 얼마나” 실리느냐가 다른 수단입니다. LangChain 문서는 이를 한 문단으로 요약합니다: 모든 모델 호출에는 고정된 컨텍스트 창이 있고, 에이전트가 돌수록 기록·도구 결과·중간 단계로 창이 찬다. 요약은 넘치기 전에 기록을 줄이고, 메모리는 시작할 때 지속적인 지시를 불러와 지식이 세션을 넘어 이어지게 하며, 스킬은 모든 것을 미리 싣지 않고 분야 지식을 필요할 때 드러낸다 [LangChain Agents — Context management].

④ RAG — 제품 문서 근거

보안 인증 관련 제품 문서 조각을 의미 검색으로 찾아 근거로 붙입니다. 가격표는 승인된 문서에서만 가져옵니다.

⑤ 도구·MCP — 실제 행동

CRM(고객·거래 관리 시스템) 의 MCP 서버 도구로 A 고객사 담당자 정보를 조회하고, 문서 저장 도구로 초안을 만듭니다. 실행은 앱·서버가 하고 결과만 돌아옵니다.

⑥ 기록 — 다음을 위해

“A 고객사 제안서 v1 작성, 검토 대기”를 장기 메모리에 적습니다. 대화가 길어지면 압축으로 컨텍스트를 줄이되, 이 기록은 메모리에 남습니다.

설계 관행 (공식 근거 없음 · 의견) 무엇을 어디에 둘지 고를 때 이렇게 물어보면 정리가 쉽습니다 — “매번 필요한가?”(예 → 지시문), “특정 일에만 필요한 절차인가?”(→ 스킬), “실제로 무언가를 바꾸거나 가져와야 하나?”(→ 도구, 여러 앱이 쓰면 MCP), “사용자·대화에서 생긴 정보인가?”(→ 메모리), “미리 있는 문서인가?”(→ RAG). 실습 pb4 컨텍스트 배치표와 pb5 기억할 것과 검색할 것에서 직접 해 봅니다.
한눈에 정리
  • 메모리는 모델 밖 저장소에 둔 “이전 상호작용의 기억”입니다. 단기 메모리는 한 스레드 안(대화 기록·상태, 길면 잘라내기·지우기·요약), 장기 메모리는 스레드를 넘어(저장소·MemoryService·메모리 파일) 남습니다.
  • 컨텍스트는 이번 호출에 실린 일시적인 글이고, 메모리는 창 밖에 지속되다가 도구·콜백으로 불러와야 컨텍스트가 됩니다.
  • RAG 는 문서를 조각·임베딩·색인해 두고, 질문과 뜻이 가까운 조각을 찾아 모델 입력에 붙여 근거 있는 답을 만드는 방식입니다. 정적 검색과 에이전트형 검색이 있습니다.
  • 임베딩은 글을 벡터로 바꿔 거리로 관련도를 재며, 키워드가 안 겹쳐도 뜻이 비슷한 글을 찾게 합니다. 많을 때는 벡터 저장소(벡터 DB)로 빠르게 찾습니다.
  • 메모리와 RAG 는 기술이 겹칠 수 있지만 데이터의 출처·수명·범위가 다릅니다. 지시문·스킬·메모리·RAG 는 “언제 실리나”가, 도구·MCP 는 “행동 경로”가 다른 수단으로 한 에이전트 안에서 함께 쓰입니다.

CHAPTER 06

에이전트 실행과 제어

앞 장까지는 에이전트가 무엇으로 일하는지(LLM·도구·MCP·프롬프트·메모리)를 봤습니다. 이 장은 에이전트가 어떤 순서로 일하고, 어디서 멈추고, 누가 브레이크를 잡는지를 다룹니다. 계획 세우기와 실행 고리, 정해진 길을 따르는 워크플로와 스스로 길을 찾는 에이전트의 차이, 중간 저장(체크포인트)과 재개, 사람 승인, 실패했을 때의 재시도·대체, 그리고 “언제 멈추게 할 것인가”까지가 이 장의 범위입니다.

계획과 실행의 고리 — 목표를 쪼개고, 하고, 확인하고, 다시

무엇인가. 에이전트의 계획(Planning)은 받은 목표를 한 번에 할 수 있는 작은 단계로 나누고(작업 분해, Task Decomposition) 그 순서를 정하는 일입니다. 실행(Execution)은 그 단계를 실제로 하는 일 — 대부분 도구를 부르는 일 — 입니다. 에이전트는 이 둘을 한 번만 하지 않고 고리(loop)로 반복합니다. Anthropic 문서는 에이전트를 이렇게 설명합니다. 사람의 지시나 대화로 일을 받고, 할 일이 분명해지면 스스로 계획하고 움직이며, 필요하면 사람에게 돌아와 정보나 판단을 구합니다 [Building effective agents].

쉽게 말하면 처음 가 보는 동네에서 심부름을 하는 사람을 떠올려 보세요. “빵 사 오기”를 받으면 ① 빵집 위치 찾기 → ② 가기 → ③ 사기로 나눕니다. 가다가 길이 막혀 있으면 지도를 다시 보고 길을 바꿉니다. 계속 “지금 어디까지 왔지?”를 확인하는 것이 핵심입니다.

실제로는 이렇습니다. 사람이 지도를 보는 일에 해당하는 것이 도구 호출 결과입니다. Anthropic 문서는 실행 중 매 단계에서 환경으로부터 실제 결과(ground truth)(추측이 아니라 실제로 일어난 일 — 도구가 돌려준 값, 코드를 실행한 결과 등)를 받아 진행 상황을 판단하는 것이 중요하다고 강조합니다. 그리고 에이전트는 체크포인트에서, 또는 막혔을 때 멈춰 사람의 피드백을 받을 수 있고, 일은 보통 완료되면 끝나지만 최대 반복 횟수 같은 멈춤 조건을 함께 두는 것이 흔하다고 적습니다 [Building effective agents].

왜 등장했나 · 무엇을 푸나. 한 번의 LLM 호출로 끝나는 일은 계획이 필요 없습니다. 하지만 “여러 파일을 고쳐 버그를 잡아라”처럼 몇 단계가 필요할지 미리 알 수 없는 일은, 단계를 나누고 결과를 보며 계획을 고쳐 가야 합니다. Anthropic 문서는 에이전트가 쓸모 있어진 배경으로 LLM 이 복잡한 입력 이해, 추론과 계획, 믿을 만한 도구 사용, 오류에서의 회복을 잘하게 된 점을 듭니다 [Building effective agents].

코드(사람)가 미리단계를 사람이 코드로 미리 나눠 두면 그것이 워크플로입니다(아래 워크플로 vs 에이전트). 예: Anthropic 의 프롬프트 체이닝은 “작업을 단계의 연속으로 분해”합니다 [Building effective agents].

관계 · 언제 쓰나 · 주의. 작업 분해를 누가 하느냐가 곧 워크플로와 에이전트를 가르는 기준입니다 — 코드가 미리 하면 워크플로, LLM 이 실행 중에 하면 에이전트입니다. Anthropic 은 에이전트 설계 원칙 세 가지 중 하나로 “에이전트의 계획 단계를 명시적으로 보여 줘 투명성을 높일 것”을 꼽습니다 [Building effective agents]. 계획이 보이면 사람이 중간에 잘못된 방향을 잡아낼 수 있습니다. 한계도 분명합니다. 자율적으로 여러 바퀴를 도는 만큼 비용이 커지고 오류가 쌓일 수 있으므로, 격리된 환경에서 충분히 시험하고 가드레일(실행 중 입력·출력·행동을 자동으로 검사해 막는 장치 — 8장에서 자세히)을 두라고 권합니다 [Building effective agents].

워크플로 vs 에이전트 — 길을 누가 정하나

무엇인가. 이 장에서 가장 중요한 비교입니다. Anthropic 은 LLM 과 도구를 쓰는 시스템 전체를 에이전트형 시스템(agentic systems)이라 묶고, 그 안을 둘로 나눕니다 [Building effective agents].

워크플로(Workflow)

LLM 과 도구가 미리 정해 둔 코드 경로를 따라 움직이는 시스템. 어떤 순서로 무엇을 할지 개발자가 코드로 정합니다.

에이전트(Agent)

LLM 이 자기 과정과 도구 사용을 스스로 동적으로 지휘하며, 일을 어떻게 해낼지에 대한 통제권을 쥐는 시스템.

LangGraph 문서도 같은 선을 긋습니다. 워크플로는 “미리 정해진 코드 경로가 있고 특정 순서로 동작하도록 설계된 것”, 에이전트는 “동적이며 자기 과정과 도구 사용을 스스로 정하는 것”입니다 [lg-workflows-agents]. 요청서의 결정적 워크플로(Deterministic Workflow) vs 동적 에이전트(Dynamic Agent)도 같은 구분입니다. 결정적이란 “같은 입력이면 같은 경로를 탄다”는 뜻입니다.

왜 이 구분이 중요한가. Anthropic 은 가능한 가장 단순한 해법을 찾고, 필요할 때만 복잡도를 높이라고 권합니다. 에이전트형 시스템은 보통 지연과 비용을 내주고 성능을 얻는 거래이며, 많은 경우 검색과 예시를 곁들인 LLM 호출 한 번을 잘 다듬는 것으로 충분하다고 말합니다. 복잡도를 높일 때도 잘 정의된 일에는 워크플로, 유연성이 필요할 때 에이전트를 고르라는 순서입니다 [Building effective agents].

실제 업무에서 고르는 예 매주 같은 양식의 주간 보고서 만들기(데이터 모으기 → 요약 → 양식에 채우기)는 단계가 늘 같으니 워크플로가 맞습니다. “이 고객 문의를 해결해 줘”는 주문 조회가 필요한지, 환불이 필요한지, 기술 문서를 찾아야 하는지 문의마다 달라 에이전트가 어울립니다. Anthropic 은 고객 지원과 코딩을 에이전트가 특히 가치를 낸 두 분야로 꼽으며, 공통점으로 대화와 행동이 함께 필요하고, 성공 기준이 분명하고, 피드백 고리가 있고, 사람의 감독이 들어간다는 점을 듭니다 [Building effective agents].

벤더마다 “워크플로”가 가리키는 것. 같은 말이 제품마다 조금씩 다른 범위를 가리킵니다. 공통점은 “실행 경로를 명시적으로 정한다”는 것입니다.

사람 승인 단계 — 위험한 행동 앞에서 멈추고 묻기

무엇인가. 사람 승인 단계(Human-in-the-loop, HITL)는 실행을 특정 지점에서 멈추고 사람(또는 정책)의 입력을 기다렸다가 이어 가는 구조입니다. Microsoft Agent Framework 문서는 에이전트가 함수 호출 승인 같은 사용자 입력을 필요로 하면 이를 human-in-the-loop 패턴이라 부르며, 이때 실행은 최종 답 대신 “어떤 입력이 필요한지”를 알리는 응답으로 끝난다고 설명합니다 [msaf-tool-approval].

왜 필요한가. LangChain 문서는 “완전한 자율이 언제나 적절하지는 않다”며, 파괴적인 쓰기, 비싼 API 호출, 판단이 필요한 모든 일 앞에 사람을 둘 수 있게 한다고 말합니다 [lc-agents]. OpenAI 문서는 취소·편집·셸 명령·민감한 MCP 동작 같은 부작용(되돌리기 어려운 바깥 세상의 변화 — 메일 발송, 결제, 삭제 등) 앞에서 멈추라고 권합니다 [openai-guardrails-approvals]. LangGraph 는 대표 쓰임으로 API 호출·데이터베이스 변경·금융 거래 같은 중요한 행동 앞의 승인을 듭니다 [lg-interrupts].

어떻게 동작하나 — 벤더별 이름. 모든 벤더가 “멈추고 → 상태를 저장하고 → 사람 결정을 받아 → 같은 실행을 이어 간다”는 같은 뼈대를 쓰지만, 부르는 이름이 다릅니다.

벤더부르는 이름뜻
LangGraphinterrupt (중단)노드 안 어디서든 interrupt() 를 부르면 상태를 저장하고 재개될 때까지 무기한 기다립니다. 같은 thread_id 로 Command(resume=…) 를 보내면 그 값이 interrupt() 의 반환값이 됩니다. 정해진 노드 앞뒤에서 멈추는 정적 중단점과 달리 동적입니다 [lg-interrupts].
OpenAI Agents SDKapproval · interruptions도구 호출에 대한 사람 승인 경로. 모델은 행동이 필요하다고 판단할 수 있지만, 승인·거절할 때까지 실행이 멈춥니다. 핸드오프 뒤나 도구로 감싼 에이전트 안쪽에서도 같은 방식입니다 [openai-guardrails-approvals].
Microsoft Agent Frameworktool approval (도구 승인)도구마다 승인 필요 여부를 표시(.NET ApprovalRequiredAIFunction, Python approval_mode="always_require"). 응답에 승인 요청이 있으면 사용자에게 보여 주고, 승인/거절 응답을 같은 세션으로 보냅니다. 워크플로에서는 request_info 로 사람 입력을 받습니다 [msaf-tool-approval · msaf-workflows].
Claude Managed Agentspermission policy · confirmationalways_ask 정책인 도구를 부르면 세션이 requires_action 으로 멈추고 무기한 기다립니다. 막힌 이벤트마다 user.tool_confirmation(allow/deny)을 보내면 다시 실행됩니다 [claude-managed-permissions].
LangChainsteering (조종) · HumanInTheLoopMiddleware정해진 결정 지점에서 에이전트가 멈추고, 사람이 승인·수정·거절하면 실행이 계속됩니다 [lc-agents].

사람이 할 수 있는 일 ① 승인 또는 거절. 가장 흔한 쓰임입니다. 중요한 행동 직전에 멈추고 예/아니오를 받아 다음 경로를 고릅니다. 예: “500달러 송금을 승인하시겠습니까?” → 예면 진행, 아니오면 취소 [lg-interrupts]. Microsoft·OpenAI 문서는 거절도 결과로 돌려줘야 모델이 사용자에게 그 결정에 맞게 답할 수 있다고 설명합니다 [msaf-tool-approval].

② 검토하고 고치기. LLM 이 만든 초안이나 상태 일부를 사람이 직접 고쳐서 돌려줍니다. LLM 의 실수를 바로잡거나 빠진 정보를 채울 때 씁니다. 도구 호출이라면 실행 전에 인자(예: 메일 제목)를 바꿔 승인할 수 있습니다 [lg-interrupts].

③ 도구 안에 승인 넣기. 승인 로직을 도구 자체에 넣으면, LLM 이 그 도구를 부를 때마다 자동으로 멈춥니다. 그래프의 여러 곳에서 같은 도구를 써도 승인 규칙이 따라다닙니다 [lg-interrupts].

④ 사람 입력 검증하기. 사람이 잘못된 값을 넣으면(예: 나이에 “서른”) 다시 묻습니다. LangGraph 는 한 노드 안에서 while 반복으로 계속 묻지 말고, 한 번 묻고 → 오류 메시지를 상태에 남기고 → 조건부 연결로 그 노드로 돌아가게 하라고 권합니다 [lg-interrupts].

주의 — 재개하면 그 단계가 처음부터 다시 실행됩니다 LangGraph 에서 재개는 interrupt() 가 있던 줄이 아니라 그 노드의 처음부터 다시 실행됩니다. 그래서 interrupt() 앞에 둔 부작용(레코드 생성, API 호출)은 재개할 때마다 반복될 수 있습니다. 문서는 그런 동작을 멱등(여러 번 해도 결과가 한 번 한 것과 같은 성질)하게 만들거나, interrupt() 뒤나 별도 노드로 옮기라고 권합니다 [lg-interrupts].

멈춤 조건 — 에이전트가 끝없이 돌지 않게

무엇인가. 실행 제어(Execution Control)의 마지막 조각은 “언제 멈추는가”입니다. 워크플로는 마지막 칸에 닿으면 끝나지만, 에이전트는 스스로 다음 행동을 정하므로 끝나는 조건을 따로 정해 두지 않으면 같은 일을 되풀이하거나 비용을 계속 쓸 수 있습니다. Anthropic 문서는 일은 보통 완료되면 끝나지만, 통제를 유지하기 위해 최대 반복 횟수 같은 멈춤 조건을 두는 것이 흔하다고 말합니다 [Building effective agents].

① 일이 끝났다

Claude 앱이 도는 고리는 stop_reason(모델이 응답을 멈춘 이유를 알려 주는 값) 이 "tool_use"(도구를 불러 달라는 뜻) 인 동안 도구를 실행하고 계속하며, 다른 이유(end_turn·max_tokens·stop_sequence·refusal)가 오면 빠져나갑니다. 최종 답을 냈거나 다른 이유로 멈춘 것입니다 [claude-how-tool-use-works].

② 반복 상한에 닿았다

서버 쪽 도구 고리에는 반복 한도가 있어, 넘으면 pause_turn 으로 돌아옵니다 — 끝난 것이 아니므로 대화를 다시 보내 이어 가게 합니다 [claude-how-tool-use-works]. SDK 도구 실행기 예시에는 max_iterations: 10 이 나옵니다 [claude-memory-tool]. LangChain 은 호출 한도를 장애 허용 기능에 둡니다 [lc-agents].

③ 정한 조건을 만족했다

Google ADK 반복(Loop) 워크플로 에이전트는 하위 에이전트를 특정 종료 조건을 만족할 때까지 되풀이합니다 [adk-workflow-agents]. 평가자-최적화는 받아들일 만한 답이 나오면 끝납니다 [lg-workflows-agents].

④ 규칙이 막았다

Microsoft 미들웨어로 멈춤 조건·내용 정책·대화 길이 제한을 구현합니다. 실행 전에 금지된 내용을 막는 사전 종료, 실행 후 응답을 검증하거나 응답 수 상한에서 끝내는 사후 종료가 있습니다 [msaf-termination]. OpenAI 입력 가드레일도 본 에이전트가 돌기 전에 요청을 막습니다 [openai-guardrails-approvals].

⑤ 사람이 멈추게 했다

승인 요청에서 사람이 거절하면 그 도구는 실행되지 않습니다. 대기 자체는 LangGraph·Claude Managed Agents 모두 무기한이므로, 얼마나 기다릴지는 앱이 정합니다 [lg-interrupts · claude-managed-permissions].

⑥ 콜백이 건너뛰었다

Google ADK 에이전트 실행 전 콜백(정해진 시점에 자동으로 불리도록 걸어 둔 개발자 함수)이 값을 돌려주면 에이전트 본 실행을 건너뛰고 그 값을 최종 출력으로, 모델 호출 전 콜백은 LLM 호출을, 도구 실행 전 콜백은 도구 실행을 건너뜁니다 [adk-callbacks].

한눈에 정리
  • 에이전트는 계획 → 도구로 행동 → 실제 결과 관찰 → 판단의 고리를 돌며, 매 바퀴 LLM 이 다음 행동을 정합니다. 계획 단계를 드러내면 투명성이 높아집니다.
  • 워크플로는 코드가 경로를 미리 정하고(예측 가능·일관), 에이전트는 LLM 이 실행 중에 정합니다(유연·비용과 오류 누적). 가장 단순한 해법부터 시작해 나아질 때만 복잡도를 더합니다.
  • 그 사이에 체이닝·라우팅·병렬화·오케스트레이터-워커·평가자-최적화 다섯 패턴이 있고, 평가자-최적화가 반성·자기 수정의 대표 형태입니다.
  • 오래 걸리는 일은 상태와 체크포인트로 저장 지점에서 재개하고, 부작용 앞에서는 사람 승인으로 멈춘 뒤 같은 실행을 이어 갑니다. 도구마다 권한 정책(자동·항상 묻기·판단)을 정합니다.
  • 실패는 층별로 재시도·대체·재개로 다루되 부작용이 두 번 일어나지 않게 하고, 완료·반복 상한·규칙 차단·사람 거절 같은 멈춤 조건을 미리 둡니다.

CHAPTER 07

멀티 에이전트 시스템

에이전트 하나로 감당하기 어려운 일을 여러 에이전트에게 나눠 맡기는 구조를 다룹니다. 언제 나누는 것이 이득인지, 나눌 때 어떤 모양(패턴)이 있는지, 에이전트끼리 무엇을 어떻게 주고받는지, 그리고 그 대가로 얼마나 많은 비용을 치르는지를 6개 벤더 문서를 나란히 놓고 살펴봅니다.

단일 에이전트 vs 멀티 에이전트

멀티 에이전트가 성능을 올려 준다고 해서 언제나 좋은 것은 아닙니다. 여러 벤더 문서가 같은 권고를 합니다 — 할 수 있으면 에이전트 하나로 시작하라는 것입니다.

  • OpenAI "가능하면 에이전트 하나로 시작하고, 능력 분리·정책 분리·프롬프트 명확성·추적 가독성이 실질적으로 좋아질 때만 전문 에이전트를 추가하라. 너무 일찍 나누면 프롬프트·추적·승인 지점만 늘고 워크플로가 꼭 나아지지는 않는다." [Orchestration and handoffs]
  • LangChain "모든 복잡한 작업에 멀티 에이전트가 필요한 것은 아니다. 알맞은(때로는 동적으로 바뀌는) 도구와 프롬프트를 가진 에이전트 하나로도 비슷한 결과를 얻을 때가 많다." [Multi-agent]
  • Google ADK 단일 에이전트에서 여러 에이전트 구조로 옮기는 데 정해진 요건은 없고, 지시 수행 성능·컨텍스트 한계·코드 모듈화 같은 한계를 발견했을 때 옮기면 된다고 설명합니다. [ADK Agents]
  • Microsoft "함수 하나로 처리할 수 있으면 AI 에이전트 대신 그 함수를 써라." [Microsoft Agent Framework overview]
비교 항목단일 에이전트멀티 에이전트
구조모델 하나가 지시문·도구·대화 기록 전부를 한 컨텍스트에서 다룸리드(또는 첫 담당)가 일을 나눠 다른 에이전트에게 맡기고, 각자 별도 컨텍스트에서 일함
잘 맞는 일단계가 분명하고 도구 수가 적당한 일, 대부분의 일상 업무독립적으로 나눌 수 있는 넓은 조사, 한 컨텍스트에 다 안 들어가는 정보, 복잡한 도구가 많은 일 (Anthropic)
비용 · 지연적음. 모델 호출 수가 적음토큰 사용이 크게 늘어남 — 채팅 대비 약 15배 (Anthropic 측정)
디버깅한 흐름만 보면 됨에이전트 사이의 상호작용까지 봐야 함. 리드의 작은 변화가 하위 에이전트 행동을 예측 못 하게 바꿈(창발적 행동)
잘 안 맞는 일한 컨텍스트에 다 넣기엔 너무 넓은 조사모든 에이전트가 같은 컨텍스트를 공유해야 하거나 에이전트 사이 의존이 많은 일 — 원문은 대부분의 코딩 작업을 예로 듦 (Anthropic)
실제 사례로 비교하기 사내 규정 Q&A 봇: 질문 하나에 규정 문서 검색 도구 하나면 충분합니다 → 단일 에이전트. 경쟁사 20곳의 공개 자료 비교 보고서: 회사마다 독립적으로 조사할 수 있고 자료가 한 컨텍스트에 다 들어가지 않습니다 → 회사별 하위 에이전트로 나누면 이득. 코드 저장소 하나의 버그 수정: 파일끼리 얽혀 있어 모두가 같은 맥락을 알아야 합니다 → Anthropic 은 이런 일이 멀티 에이전트에 아직 잘 맞지 않는다고 봅니다.

여러 에이전트를 엮는 모양은 몇 가지로 정리됩니다. 요청서가 든 다섯 이름 가운데 순차(Sequential)·병렬(Parallel)은 Google ADK·Microsoft Agent Framework 문서에 그대로 나오는 이름이지만, 감독자(Supervisor)·계층(Hierarchical)·스웜(Swarm)은 이 교재가 받은 6개 벤더 원문 어디에도 나오지 않습니다. 이 세 가지는 업계에서 흔히 부르는 이름으로 소개하고, 벤더 문서의 어떤 개념과 대응되는지는 아래 설계 관행 상자에 따로 적습니다.

중앙의 에이전트가 계속 주도권을 쥐고 전문 에이전트를 필요할 때 불러 씁니다. OpenAI 문서는 이를 agents as tools(에이전트를 도구로 쓰기)라 부르고 "관리자가 최종 답을 종합해야 하거나, 전문가가 요약·분류처럼 범위가 정해진 일을 할 때" 알맞다고 합니다. LangChain 의 Subagents 패턴도 "메인 에이전트가 하위 에이전트를 도구로 조정하고 모든 경로가 메인을 지난다"고 설명합니다.

감독자형을 여러 층으로 쌓은 것입니다. 원문에 "계층형"이라는 패턴 이름은 없지만, 얼마나 깊이 중첩할 수 있는지에 대한 규칙은 있습니다. Claude Managed Agents는 위임이 한 단계까지만 가능하고, 이미 하위 에이전트를 가진 에이전트를 하위로 넣으면 요청이 거부됩니다. Google ADK는 task 모드(맡은 일을 끝내면 자동으로 부모 에이전트에게 돌아가는 방식) 에이전트가 맨 끝(잎) 에이전트여야 하며 하위 에이전트를 가질 수 없다고 적습니다. 반대로 Microsoft는 워크플로를 더 큰 그래프의 한 실행 단위로 넣는 하위 워크플로(Sub-Workflows)를, LangChain은 패턴끼리 섞어 쓰는 것을 허용합니다.

Google ADK의 SequentialAgent는 하위 에이전트를 차례로 실행하고, ADK 문서는 이런 워크플로 에이전트가 "AI 모델에게 묻지 않고" 정해진 논리로 순서를 정하므로 실행이 결정적이고 예측 가능하다고 설명합니다. Microsoft의 Sequential 오케스트레이션도 "정해진 순서로 하나씩 실행"입니다.

Google ADK ParallelAgent, Microsoft Concurrent, Anthropic Parallelization 이 같은 모양입니다. Anthropic 은 병렬화를 두 가지로 나눕니다 — 구획 나누기(Sectioning): 독립 하위 작업을 동시에 실행, 투표(Voting): 같은 작업을 여러 번 실행해 다양한 결과를 얻음(예: 여러 프롬프트가 코드의 보안 취약점을 각각 검토).

대화 주도권 자체가 넘어갑니다. OpenAI는 이를 handoffs(핸드오프 — 대화 주도권을 다른 에이전트에게 넘김)라 부르며 "전문 에이전트가 그 갈래의 다음 응답을 맡아야 할 때" 쓰라고 합니다. LangChain Handoffs 는 "도구 호출이 상태 변수를 바꾸고, 그 값에 따라 담당 에이전트나 도구·프롬프트가 바뀐다"는 방식이고, Microsoft Handoff 는 "맥락에 따라 에이전트끼리 제어를 넘긴다", Google ADK는 기본(chat) 모드 하위 에이전트가 transfer_to_agent 로 직접 넘겨 줄 때까지 사용자와 계속 대화하는 방식입니다.

장단점과 비용 · 병렬 실행과 의존성

멀티 에이전트가 잘 되는 이유와 비싼 이유는 같은 데 있습니다. Anthropic 분석에 따르면 조사 능력 평가(BrowseComp)에서 성능 차이의 95%를 세 요인이 설명했고, 그중 토큰 사용량 하나가 80%를 설명했습니다(나머지는 도구 호출 수와 모델 선택). 즉 멀티 에이전트는 "문제를 풀기에 충분한 토큰을 쓰게 해 주기 때문에" 잘 됩니다. 그리고 그만큼 비쌉니다.

패턴마다 비용 모양도 다릅니다. LangChain 문서는 같은 요청을 패턴별로 돌렸을 때의 모델 호출 수와 토큰을 비교합니다.

오케스트레이션 vs 에이전트 간 통신

두 말은 자주 섞여 쓰이지만 서로 다른 질문에 답합니다. 오케스트레이션(Orchestration — 여러 에이전트와 단계의 실행 순서·흐름을 정하고 관리하는 일)은 "누가 · 언제 · 어떤 순서로 일하나"를, 에이전트 간 통신은 "무엇을 · 어떤 형식과 통로로 주고받나"를 다룹니다.

한눈에 정리
  • 멀티 에이전트 = 각자 컨텍스트를 가진 에이전트 여럿이 일을 나눠 하는 구조. 이득은 컨텍스트 분리·병렬화·분산 개발에서 나온다.
  • 벤더 공통 권고: 먼저 에이전트 하나로 시작하고, 나눠서 실질적으로 나아질 때만 나눈다.
  • 패턴은 "최종 답을 누가 소유하나"로 가른다 — 감독자형(agents as tools·subagents·orchestrator-workers) vs 핸드오프형(handoffs). 순차·병렬은 코드가 흐름을 정하는 워크플로다. 감독자·계층·스웜은 원문에 없는 업계 이름이다.
  • 통신은 대부분 도구 호출의 형태를 빌리고, 원격 에이전트에는 ADK 가 소개하는 A2A 가 있다. 위임 지시서에는 목표·출력 형식·도구·경계를 담는다.
  • 멀티 에이전트는 채팅 대비 약 15배 토큰을 쓴다. 공유/독립 컨텍스트, 검증 에이전트, 실패 보고, 예산 상한을 함께 설계한다.

이 장의 나머지 소절과 🔧 세부는 완전 가이드 7장에 있습니다.

CHAPTER 08

시스템 아키텍처와 프레임워크

지금까지 배운 부품 — 모델, 도구, MCP, 메모리, 워크플로, 여러 에이전트 — 을 실제로 돌리려면 그 아래를 받치는 바탕 구조가 필요합니다. 이 장은 오케스트레이터·런타임·세션 저장소·추적·평가·가드레일이 어떻게 맞물리는지 보고, LangGraph·LangChain·Microsoft Agent Framework·Google ADK·OpenAI Agents SDK·Anthropic 기술이 같은 개념을 각각 무엇이라 부르는지 비교합니다. 프레임워크 사용법은 다루지 않습니다.

에이전트 프레임워크(Agent Framework — 에이전트를 만드는 데 쓰는 부품과 추상화(복잡한 세부를 감추고 쓰기 쉽게 만든 틀)의 묶음)와 에이전트 런타임(Agent Runtime — 만든 에이전트를 실제로 실행하고 상태를 유지하는 실행 환경)은 자주 섞여 쓰입니다. 이 구분을 가장 분명하게 적은 곳은 LangChain 문서입니다.

오케스트레이터의 전체 구조

오케스트레이터(Orchestrator — 요청을 받아 어떤 에이전트·단계를 어떤 순서로 실행할지 관리하는 부분)는 시스템의 지휘자입니다. 6장에서 본 워크플로(코드가 순서를 정함)와 에이전트(LLM 이 순서를 정함), 7장의 협업 패턴이 모두 이 자리에서 실행됩니다. 아래 그림은 원문들이 다루는 구성 요소 — 가드레일, 위임, 사람 승인, 체크포인트, 추적 — 를 한 장에 모은 것입니다.

요청 하나가 이 구조를 지나는 과정을 단계로 보면 다음과 같습니다.

① 입력 검사 — 요청이 들어오면 비싸거나 부작용이 있는 일을 시작하기 전에 입력 가드레일이 허용되지 않는 요청을 막습니다. OpenAI 문서는 막는(blocking) 실행과, 지연을 줄이려 본 작업과 동시에 돌리는 병렬 실행을 구분합니다.
② 세션 불러오기 — 같은 대화라면 세션(대화 기록·상태)을 불러옵니다. LangGraph 는 thread_id 로, Microsoft 는 AgentSession 으로, ADK 는 SessionService 로 이 일을 합니다.
③ 실행 흐름 정하기 — 오케스트레이터가 정해진 그래프를 따르거나(워크플로), 리드 에이전트가 위임·핸드오프를 판단합니다(에이전트).
④ 에이전트 루프 — 각 에이전트 런타임이 모델 호출 → 도구 실행 → 결과 반영을 반복합니다. 도구 중 일부는 MCP 서버나 원격 에이전트를 거칩니다.
⑤ 승인과 저장 — 위험한 도구 호출은 실행 대신 승인 대기로 기록되고, 실행은 재개 가능한 상태로 멈춥니다. 승인되면 처음부터가 아니라 같은 실행을 그 상태에서 이어 갑니다(OpenAI 승인 생애 주기). Microsoft 워크플로는 슈퍼스텝이 끝날 때마다 체크포인트를 남깁니다.
⑥ 출력 검사와 기록 — 최종 답은 출력 가드레일로 검증·가림 처리된 뒤 나가고, 이 모든 과정은 추적(트레이스)으로 남아 나중에 평가에 쓰입니다.

각 프레임워크는 이 "오케스트레이터" 자리를 다른 이름으로 부릅니다.

CHAPTER 09

보안과 운영

에이전트는 말만 하는 프로그램이 아니라 도구를 호출해 실제로 무언가를 바꾸는 프로그램입니다. 그래서 "무엇을 할 수 있게 둘 것인가(권한)", "누구 이름으로 할 것인가(인증·인가)", "남이 몰래 지시를 끼워 넣으면 어떻게 되는가(인젝션)", "무엇을 기록해 두고 얼마를 쓰는가(감사·비용)", "고장 나면 어떻게 되살리는가(장애 대응)"를 설계 단계에서 정해야 합니다. 이 장은 MCP 명세와 5개 벤더 문서가 공통으로 말하는 보안 원칙을 먼저 세우고, 운영에서 챙길 비용·성능·품질·장애 대응을 이어서 다룹니다.

도구 실행 권한과 최소 권한 원칙

무엇인가. 최소 권한 원칙(principle of least privilege — 일에 꼭 필요한 만큼만 권한을 주는 원칙)은 에이전트에게 지금 맡긴 일에 필요한 도구와 권한만 주라는 원칙입니다. 에이전트는 모델이 스스로 어떤 도구를 부를지 고르기 때문에, "모델이 잘 판단하겠지"에 기대는 대신 애초에 할 수 없는 일을 만들어 두는 것이 가장 확실한 안전장치입니다.

왜 필요한가. Google ADK 문서는 에이전트의 위험 원천으로 모호한 지시, 모델의 환각(사실이 아닌 내용을 그럴듯하게 지어내는 것), 악의적 사용자의 탈옥(모델의 안전 규칙을 우회하도록 꾸민 입력)·프롬프트 인젝션, 도구를 통한 간접 인젝션을 꼽고, 위험 종류로 "시스템을 망가뜨리는 명령 실행, 허가 없는 구매·금융 거래, 개인정보 유출, 데이터 유출" 같은 안전하지 않은 행동을 듭니다 [adk-safety]. Anthropic 문서는 인젝션 대책의 하나로 "인젝션이 성공해도 피해가 최소가 되도록 최소 권한을 적용하라 — 필요 없는 비밀은 주지 말고, 도구는 샌드박스에서 돌리고, 권한 범위는 최대한 좁혀라"고 적습니다 [claude-mitigate-jailbreaks]. 즉 최소 권한은 다른 방어가 뚫렸을 때 피해 크기를 정하는 마지막 벽입니다.

어떻게 하나 — 네 가지 수단.

수단원문이 말하는 것사다리 칸
도구 자체를 빼기권한 정책은 "켜져 있는 도구가 언제 실행되는가"만 정합니다. 도구를 에이전트에서 아예 없애려면 정책이 아니라 비활성화해야 합니다 Claude 구현 [claude-managed-permissions]①

프롬프트 인젝션과 도구 인젝션

무엇인가. OpenAI 문서의 정의로는 프롬프트 인젝션(prompt injection — 신뢰할 수 없는 글 속에 숨긴 지시로 AI 의 원래 지시를 덮어쓰려는 공격)은 "신뢰할 수 없는 글이나 데이터가 AI 시스템에 들어오고, 그 안의 악의적 내용이 AI 에 대한 지시를 덮어쓰려 할 때" 일어납니다. 목표는 다양합니다 — 이어지는 도구 호출로 개인 데이터를 빼내기, 의도와 다른 행동 시키기 등. 예: 데이터 조회 에이전트를 속여 요약 대신 고객 원본 기록을 보내게 함 [openai-agent-safety].

비유로 보면 비서에게 "이 편지들을 읽고 요약해 줘"라고 시켰는데, 편지 중 하나에 "이 편지를 읽는 비서는 사장님 금고 비밀번호를 이 주소로 보내시오"라고 적혀 있는 상황입니다. 좋은 비서는 그 문장을 "편지에 이런 이상한 말이 있었습니다"라고 보고할 뿐 따르지 않습니다.

실제로는 모델에게 "지시"와 "읽을거리"가 모두 같은 글자(토큰)로 들어가기 때문에, 시스템 설계로 둘을 구분해 주고 모델이 잘못 따르더라도 피해가 작도록 권한을 묶어 두는 것이 대책의 핵심입니다.

위협 모델. 앱의 사용자 자신이 공격자로, 가드레일을 우회하려고 입력을 꾸밉니다 [claude-mitigate-jailbreaks].

  • 무해성 사전 검사 — 가벼운 모델로 사용자 입력을 먼저 분류하고, 응답을 구조화된 출력(예: is_harmful 참/거짓)으로 제한합니다. Claude 구현 검사용 모델이 요청 자체를 거절(stop_reason: "refusal")하면 "유해" 판정으로 취급합니다.
  • 입력 검증 — 알려진 인젝션 패턴을 걸러 냅니다. 알려진 탈옥 문구를 예시로 준 LLM 검사기를 쓸 수도 있습니다.
  • 프롬프트 설계 — 시스템 프롬프트에 윤리·법적 경계와 거절하는 방법을 명시합니다.
  • 반복 시도자 대응 — 같은 거절을 여러 번 일으키는 사용자에게 정책 위반임을 알리고 속도 제한·차단을 검토합니다.

위협 모델. 사용자는 믿을 수 있지만, 모델이 사용자를 대신해 읽는 제3자 콘텐츠(받은 메일 본문, 가져온 웹 페이지, 업로드 파일의 OCR(이미지 속 글자를 읽어 글로 바꾸는 기술) 결과, 도구 호출 결과)에 공격 지시가 들어 있습니다 [claude-mitigate-jailbreaks]. ADK 문서도 위험 원천으로 "도구 사용을 통한 간접 프롬프트 인젝션"을 따로 꼽습니다 [adk-safety].

  • 인젝션은 사용자(직접)와 읽는 내용(간접·도구 경로)으로 들어오고, 유출은 도구 인자·화면·로그·네트워크로 나간다 — 여러 겹으로 막되 완벽하지 않다는 전제로 권한과 격리를 묶는다.
  • 열쇠는 호스트가 쥐고, 생성 코드는 네트워크 없는 샌드박스에서 돌리며, 누가·무엇을·어떤 판단으로 했는지 감사 로그에 남긴다(민감 데이터 기록 기본값은 프레임워크마다 다르다).
  • 운영은 토큰(에이전트 약 4배·멀티 약 15배), 시간, 품질 평가 고리, 그리고 "멈춘 자리에서 재개 + 점진 배포"의 장애 대응으로 관리한다.

⑩실행 과정

아래 단계는 이 교재가 짠 설계 예시입니다. 출처 표시([문서명])가 붙은 부분만 원문이 말하는 사실입니다.

1단계 — 접수와 검사. 질문이 들어오면 가벼운 모델이 유해성·탈옥 여부를 분류합니다. 통과하면 리드에게 넘깁니다.

2단계 — 계획. 리드가 확장 사고로 접근법을 세웁니다 — 질문 복잡도, 하위 에이전트 수, 각자의 역할. 계획을 메모리에 저장합니다 [anthropic-multi-agent-research]. 이 예에서는 회사별로 세 갈래.

3단계 — 병렬 조사. 하위 에이전트 3개가 동시에 출발해 각자 넓은 검색어로 시작해 좁혀 가고, 도구 결과를 받을 때마다 품질과 빈틈을 따져 다음 검색을 고칩니다(도구 결과 사이의 사고). 결과는 산출물 저장소에 파일로 남기고 참조만 리드에게 돌려줍니다.

4단계 — 종합과 추가 판단. 리드가 결과를 종합하고 빠진 측면이 있으면 하위 에이전트를 더 띄우거나 전략을 고칩니다. 충분하면 조사 고리를 빠져나옵니다.

5단계 — 작성과 인용. 보고서 스킬을 불러 양식에 맞춰 개요 → 확인 → 본문을 쓰고, 인용 에이전트가 문서와 보고서를 대조해 주장마다 출처 위치를 붙입니다.

6단계 — 검토와 전달. 평가자 역할의 검토로 빠진 측면·근거 없는 주장을 확인하고, 화면에 안전하게 표시합니다. 공유를 원하면 메일 발송 승인을 요청합니다.

실사용을 대표하는 질문 약 20개로 바로 평가를 시작하고, LLM 판정자가 사실·인용·완결성·출처 품질·도구 효율을 한 번에 0.0~1.0 점수와 통과/실패로 매깁니다. 사람 시험자는 정기적으로 결과를 읽어 출처 편향(검색 최적화 콘텐츠 선호 같은)을 찾습니다 [anthropic-multi-agent-research]. 비용은 질문 종류별 토큰·도구 호출 수로 보고, 멀티 에이전트가 채팅보다 약 15배 토큰을 쓴다는 점을 감안해 단순 질문이 멀티 경로로 가는 비율을 지표로 둡니다(→ 9장 비용).

  • 설계는 12항목을 같은 순서로 — 요구사항이 구조(워크플로/에이전트, 하나/여럿)를 정하고, 구조가 부품(LLM·도구·MCP·스킬·메모리)을 정하며, 권한·실패·운영은 같은 표 안에서 함께 정한다.
  • 조사·보고서는 오케스트레이터-워커와 인용, GitHub 개발은 단일 에이전트 + 테스트 고리 + 사람 병합, 프로젝트 관리는 감독자 + 전문 에이전트(도구로 호출) + 정기 워크플로, 업무 자동화는 결정적 워크플로 + 사람 승인 + 감사가 이 교재의 설계 예시다.
  • "사용 LLM"은 제품이 아니라 능력(추론·도구 호출·컨텍스트·비용)으로 정하고, 역할별로 나눠 라우팅한다.
