웹 서버 — 파일을 맡아 두었다가
요청이 오면 HTTP로 건네주는 컴퓨터와 프로그램

브라우저(크롬·파이어폭스처럼 웹을 보는 프로그램)에 주소를 치면 화면에 페이지가 뜹니다. 그 페이지를 보관하다가 내어 주는 쪽이 웹 서버입니다. 이 한 장은 웹 서버가 무엇이고, 주소·요청과 응답·호스팅·HTTPS가 어떻게 이어지는지를 다룹니다.

1. 웹 서버라는 말의 두 가지 뜻

"웹 서버"는 하드웨어를 가리키기도 하고 소프트웨어를 가리키기도 하며, 둘이 함께 일하는 것을 통틀어 부르기도 합니다.

하드웨어 — 컴퓨터

웹 서버 소프트웨어와 웹사이트를 이루는 파일(HTML 문서, 이미지, CSS(꾸밈 규칙), JavaScript(동작을 넣는 코드))을 보관하는 컴퓨터입니다. 인터넷에 연결되어 다른 기기와 데이터를 주고받습니다.

소프트웨어 — HTTP 서버

보관된 파일에 사람들이 어떻게 접근할지를 다루는 프로그램입니다. 최소한 HTTP 서버가 들어 있는데, 주소(URL)와 HTTP(브라우저와 서버가 대화하는 규칙)를 알아듣고 내용을 사용자 기기로 보내 줍니다.

왜 내 컴퓨터가 아니라 전용 서버인가

파일을 내 컴퓨터에 두고 보여 줄 수도 있지만, 전용 서버는 보통 더 오래 켜져 있고, 인터넷에 늘 연결되어 있으며, IP 주소가 늘 같고, 전문 업체가 관리해 줍니다.

2. 주소를 치면 일어나는 일 — 4단계

  1. 브라우저가 DNS(이름을 IP 주소로 바꿔 주는 체계) 서버에서 그 사이트가 있는 서버의 진짜 주소를 찾습니다.
  2. 브라우저가 서버에 HTTP 요청을 보내 사이트의 사본을 달라고 합니다.
  3. 서버가 요청을 받아들이면 "200 OK"를 보내고, 파일을 패킷이라는 작은 조각으로 나눠 보내기 시작합니다. 조각이 빠지거나 깨지면 그 조각만 다시 받으면 되고, 여러 길로 나눠 보낼 수 있어 효율적입니다.
  4. 브라우저가 조각을 모아 완성된 페이지로 조립해 화면에 보여 줍니다. 페이지에 딸린 꾸밈·그림·코드 파일은 브라우저가 추가로 요청해 받습니다.

3. 주소 읽는 법 — URL, 도메인, DNS

URL(인터넷에 있는 자료 하나하나의 주소)은 여러 부분으로 이루어집니다. 필수인 부분도 있고 생략할 수 있는 부분도 있습니다.

부분뜻기억할 점
방식 (scheme)브라우저가 자료를 요청할 때 쓸 규칙(프로토콜)웹사이트는 보통 HTTPS, 또는 보안이 없는 HTTP입니다
도메인어느 웹 서버에 요청하는지보통 도메인 이름을 쓰고, IP 주소를 직접 쓸 수도 있지만 불편해서 드뭅니다
포트서버의 자료에 접근하는 기술적인 "문"표준 포트(HTTP는 80, HTTPS는 443)를 쓰면 보통 생략합니다
경로웹 서버 안에서 자료가 있는 곳초창기에는 서버의 실제 파일 위치였지만, 요즘은 대개 서버가 해석하는 추상적인 이름입니다
매개변수? 뒤에 붙는 이름=값 쌍(&로 구분)서버가 자료를 돌려주기 전에 추가로 할 일을 정하는 데 씁니다
책갈피 (anchor)# 뒤 — 자료 안의 특정 위치이 부분은 요청과 함께 서버로 보내지지 않습니다. 브라우저가 그 위치로 화면을 옮깁니다

IP 주소와 도메인 이름

인터넷에 연결된 컴퓨터는 공인 IP 주소(예: 192.0.2.172)로 찾아갑니다. 사람이 외우기 어렵고 바뀔 수도 있어서, 읽기 쉬운 도메인 이름을 씁니다.

도메인은 오른쪽부터 읽는다

점으로 나뉜 부분을 오른쪽에서 왼쪽으로 읽습니다. 맨 오른쪽이 최상위 도메인(.com, .org 등)이고, 내가 관리하는 도메인 앞에는 developer.mozilla.org처럼 하위 도메인을 만들 수 있습니다.

도메인은 사지 않고 빌린다

도메인은 살 수 없고, 한 해 이상 쓸 권리에 돈을 냅니다. 등록 대행 업체(registrar)에서 빌리며, 원문 기준 보통 한 해 5~15달러이고 이름과 업체에 따라 달라집니다.

DNS — 인터넷의 전화번호부

사람은 도메인 이름으로, 브라우저는 IP 주소로 찾습니다. DNS가 이름을 IP 주소로 바꿔 줍니다. 한 번 찾은 결과는 잠시 저장(캐시)해 두어 다음 조회가 빨라집니다.

4. 요청과 응답 — HTTP

HTTP에서는 항상 브라우저 쪽이 먼저 요청하고, 서버가 그에 응답합니다. 서버는 모든 요청에 반드시 답해야 하며, 최소한 오류 메시지라도 보냅니다.

요청에 들어 있는 것

메서드(하려는 동작 — 가져오기는 GET, 양식 내용 보내기는 POST), 가져올 자료의 경로, HTTP 버전, 덧붙이는 정보인 헤더, 그리고 POST처럼 보낼 내용이 있을 때의 본문.

응답에 들어 있는 것

HTTP 버전, 성공 여부를 알리는 상태 코드와 짧은 상태 메시지, 헤더, 그리고 가져온 자료가 담긴 본문.

HTTP는 앞 대화를 기억하지 않는다

HTTP만으로는 연달아 온 두 요청 사이에 연결 고리가 없습니다(stateless). 장바구니처럼 앞뒤가 이어져야 하는 기능은 쿠키라는 장치를 더해, 여러 요청이 같은 맥락을 공유하게 해서 만듭니다.

코드뜻흔한 상황
200 OK요청 성공자료를 찾아 응답 본문에 담아 보냄
301자료가 새 주소로 영구히 옮겨짐내용을 옮긴 뒤 새 주소로 안내(리다이렉트)할 때
400서버가 요청을 처리할 수 없음요청 형식이 잘못됐거나 오류가 있을 때
403접근 권한 없음서버가 누구인지는 알지만 그 페이지를 볼 권한이 없을 때
404요청한 자료를 찾을 수 없음주소가 틀렸거나, 내용을 지우고 안내를 걸어 두지 않았을 때 — 가장 흔한 오류
500서버가 처리 방법을 모르는 상황을 만남더 알맞은 500번대 코드가 없을 때 쓰는 일반 오류
503서버가 요청을 처리할 준비가 안 됨점검 중이거나 과부하일 때 — 보통 일시적

5. 정적과 동적 — 그대로 보내기와 그때그때 만들기

정적 (static)동적 (dynamic)
보내는 것보관한 파일을 있는 그대로요청을 받을 때 내용을 가공하거나 그 자리에서 만들어서
구성컴퓨터 + HTTP 서버정적 웹 서버 + 추가 소프트웨어 — 흔히 애플리케이션 서버(내용을 만들어 내는 프로그램)와 데이터베이스(자료 창고)
동작같은 주소에는 누구에게나 같은 내용데이터베이스에서 자료를 꺼내 HTML 틀(템플릿)에 채워 페이지를 만듦
알맞은 경우쪽수가 적고 모두에게 같은 내용을 보여 줄 때. 가장 만들기 쉬워 첫 사이트로 권장쪽수가 수천 개인 사이트 — 틀 몇 개와 큰 데이터베이스로 관리. 더 유연하지만 구성이 훨씬 복잡

동적 사이트도 꾸밈·코드·그림 같은 정적 파일은 정적 사이트와 똑같은 방식으로 내보냅니다.

6. 대표 웹 서버 프로그램 — nginx와 Apache

1절의 "소프트웨어" 자리에 들어가는 프로그램의 대표가 nginx와 Apache HTTP Server입니다. 둘 다 글로 된 설정 파일에 "어느 주소 요청이 오면 어느 폴더의 파일을 보낼지"를 적어 두고, 일어난 일은 로그 파일(기록 파일)에 남깁니다.

nginx·Apache 설정에서 쓰는 이름
nginxApache HTTP Server 2.4
설정 파일nginx.conf — /usr/local/nginx/conf, /etc/nginx, /usr/local/etc/nginx 중 한 곳보통 httpd.conf — 소스에서 설치하면 기본 위치는 /usr/local/apache2/conf. 여러 파일로 나누어 Include로 불러오기도 함
파일을 꺼낼 폴더location 블록 안의 root (예: root /data/www;)DocumentRoot 지시어(설정 항목) (예: /var/www/html)
한 서버에 여러 사이트server 블록을 여러 개 — 듣는 포트와 서버 이름으로 구분가상 호스트(virtual hosts) — 여러 호스트 이름이 같은 IP 주소를 가리킬 수 있음
설정 반영nginx -s reload — 새 설정의 문법이 맞으면 적용하고, 틀리면 이전 설정으로 계속 동작설정 파일에 지시어를 적어 반영. 주 설정 파일을 못 고치는 사람은 내용 폴더의 .htaccess를 씀
로그access.log · error.log (/usr/local/nginx/logs 또는 /var/log/nginx)오류 로그 위치는 ErrorLog 지시어로 지정 — 문제 해결의 가장 중요한 단서

7. 큰 사이트는 서버 앞에 리버스 프록시를 둔다

리버스 프록시는 웹 서버들 앞에 서서 브라우저의 요청을 대신 받아 뒤쪽 서버로 넘겨 주는 서버입니다. 밖에서는 서버가 한 대처럼 보이지만, 실제로는 여러 대가 일을 나눠 맡을 수 있습니다. nginx도 흔히 이런 프록시 서버로 설정해 씁니다.

부하 분산

들어오는 요청을 여러 서버에 고르게 나눠, 한 대가 감당 못 하는 방문량을 처리합니다. 한 대가 멈춰도 다른 서버가 이어받습니다.

공격으로부터 보호

원본 서버의 IP 주소를 드러내지 않아도 되므로, 서버를 직접 겨냥한 공격이 훨씬 어려워집니다.

캐싱

응답을 잠시 저장해 두었다가 같은 요청에 바로 돌려줘 속도를 높입니다.

암호화 대행

요청을 풀고 응답을 암호화하는 일을 프록시가 맡아 원본 서버의 부담을 덜어 줍니다.

8. 사이트를 어디에, 어떻게 올리나

호스팅 + 도메인

웹 호스팅은 호스팅 업체의 웹 서버에 있는 파일 공간을 빌리는 것입니다. 정적 파일 호스팅은 무료인 곳도 있고, 원문 기준 다달이 5~10달러쯤 받는 곳도 있습니다. 내용과 모양을 마음대로 다루려는 전문가·기업이 주로 고릅니다.

온라인 게시 도구

GitHub Pages는 GitHub 저장소(코드를 올려 두는 곳)의 HTML·CSS·JavaScript 파일을 가져와 웹사이트로 게시하는 정적 사이트 호스팅 서비스입니다. Netlify도 GitHub 저장소에서 바로 정적 사이트를 호스팅합니다. 제한된 기능 안에서 대체로 무료입니다.

웹 기반 편집 도구

CodePen 같은 웹 앱에서 코드를 쓰면 결과 페이지에 고유한 주소가 생깁니다. 배우고 공유하기에 좋지만 기능이 제한적이고, 이미지 같은 파일을 둘 공간은 없는 경우가 많습니다.

처음이라면 GitHub Pages

MDN은 처음 시작하는 사람에게 쓰기 쉬운 GitHub Pages를 권합니다. 저장소에 파일을 올리고 게시 설정을 하면 https://username.github.io/repositoryname/ 형태의 주소가 생깁니다. 내 도메인을 연결할 수도 있습니다.

호스팅 서버에 파일을 올리는 방법은 업체마다 여럿입니다. (S)FTP(파일 전송 프로그램으로 내 파일을 서버 쪽으로 끌어다 놓기), rsync(내 컴퓨터와 서버의 파일을 맞춰 주는 도구 — 주로 글자로 명령을 입력해 씀), 또는 GitHub 저장소를 연결해 업체가 가져가 게시하게 하는 방식이 대표적입니다. 호스팅과 도메인을 다른 업체에서 구했다면, 도메인이 올바른 서버를 가리키도록 DNS 레코드(이름과 주소를 잇는 설정)를 직접 설정해야 합니다.

9. HTTPS — 주고받는 내용을 암호화한다

무엇으로 암호화하나

TLS(예전 이름 SSL)라는 암호화 규칙을 씁니다. 누구에게나 공개하는 공개 키로 잠근 내용은, 사이트 주인이 서버에 간직한 개인 키로만 풀 수 있습니다.

인증서

접속하면 사이트가 인증서를 보냅니다. 인증서에는 공개 키가 들어 있고, 그 사이트가 스스로 밝힌 대로의 주인인지 확인해 줍니다. 브라우저는 주소창의 자물쇠로 표시하고, HTTPS가 아닌 사이트는 "안전하지 않음"으로 표시합니다.

무료 인증서 — Let's Encrypt

무료·자동·공개 인증 기관(인증서를 발급하는 곳)입니다. 웹 서버에서 돌아가는 프로그램이 "이 도메인을 내가 관리한다"는 것을 증명하면, 사람 손을 거치지 않고 인증서를 발급·갱신해 줍니다.

호스팅이 대신 해 주기도

github.io 주소를 쓰는 GitHub Pages 사이트(2016년 6월 15일 이후 생성)는 자동으로 HTTPS로 제공됩니다. 내 도메인을 연결한 사이트도 HTTPS를 지원합니다.

GitHub Pages에 민감한 정보를 두지 않습니다

GitHub Pages 사이트는 비밀번호나 카드 번호를 보내는 것 같은 민감한 거래에 쓰면 안 됩니다. 또 저장소가 비공개여도 게시된 사이트는 인터넷에 공개됩니다.
