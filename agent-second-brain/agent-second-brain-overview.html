에이전트 세컨드 브레인 — 팀의 목표와 맥락을
대화가 아니라 모두가 읽는 파일에 두기

“개인 일을 하는 에이전트 팀, 회사 일을 하는 에이전트 팀을 따로 꾸리되, 팀 안의 모든 에이전트가 같은 목표와 맥락을 갖게 하려면?” 이 한 장의 답은 세컨드 브레인, 곧 에이전트들이 일을 시작할 때마다 읽고 일하면서 고쳐 쓰는 공용 기억 파일 묶음입니다. 기준 도구는 Claude Code 이고, 원문을 엮은 설계는 “이 가이드의 제안”이라고 밝혀 둡니다.

1. 문제 — 에이전트는 어제를 모르고, 팀원은 리더의 대화를 모릅니다

사람 팀은 각자 머릿속에 어제 회의와 지난주 결정이 남아 있습니다. 에이전트 팀은 다릅니다. 원문이 분명히 적는 사실 두 가지가 있습니다.

① 세션마다 처음부터

Claude Code 문서: “모든 세션은 새 컨텍스트 창에서 시작한다.” 컨텍스트(에이전트가 한 번에 보고 있는 글 전체)가 비어 있으니, 어제 함께 정한 것도 오늘은 모릅니다.

② 팀원은 대화를 물려받지 않음

에이전트 팀의 팀원은 만들어질 때 프로젝트 맥락(CLAUDE.md · MCP 서버 · 스킬)과 생성 지시문(spawn prompt — 리더가 팀원을 만들 때 주는 첫 지시)만 받습니다. 리더의 대화 기록은 넘어가지 않습니다.

그래서

파일에 적어 두지 않은 목표와 맥락은 팀에 퍼지지 않습니다.

→ 자세히: 0장 문제 · 팀원이 시작 때 받는 것 · 컨텍스트 창

2. 생각 — 기억을 머릿속이 아니라, 모두가 펼쳐 보는 파일에

세컨드 브레인의 원뜻(Forte Labs)은 배운 것을 뇌 바깥 한곳에 모아 둔 한 사람의 디지털 지식 창고입니다. 이 가이드는 그 말을 넓혀 “에이전트 팀이 함께 읽고 쓰는 공용 기억(파일 묶음)”으로 씁니다.

  • 짧게 — 글이 많을수록 정확히 떠올리는 힘이 떨어집니다(컨텍스트 썩음). 좋은 컨텍스트는 “꼭 필요한 정보만 담은 가장 작은 묶음”입니다(원문 표현은 “신호가 강한 토큰의 가장 작은 묶음”).
  • 필요할 때 불러오기 — 자료는 미리 다 넣지 말고 경로·이름 같은 표시만 두고 필요할 때 찾게 합니다.
  • 목표에 묶어 정리 — PARA(Projects 프로젝트 · Areas 영역 · Resources 자원 · Archives 보관)처럼 주제가 아니라 실행 기준으로 나눕니다.
  • AI 가 쓰고 고치는 위키 — 안드레 카파시의 LLM 위키(AI 가 원문을 읽고 마크다운 위키를 직접 쓰고 고쳐 가는 지식 창고 방식)는 질문 때마다 원문 조각을 다시 찾는 대신, AI 가 원문을 읽어 위키 쪽에 엮어 두고 계속 고칩니다. 세 층(고치지 않는 원문 · AI 가 쓰는 위키 · 규칙 문서인 스키마)과 세 작업(넣기 · 묻기 · 점검)으로 굴립니다. 사람은 자료를 고르고 좋은 질문을 하고, 정리·연결·기록은 AI 가 맡습니다. LLM 위키
  • 다음 에이전트를 위한 메모 — “미래의 나를 위한 메모”를 “다음 에이전트를 위한 메모”로. 용어 풀이 · 멈춘 자리 · 관련 링크를 남깁니다.
이 가이드의 제안 — 팀 목표 문서 한 장

팀마다 목표 문서 한 장(예시 이름 GOAL.md)을 짧게 쓰고, 프로젝트 CLAUDE.md 에서 @GOAL.md 로 불러옵니다. 리더·팀원·다음 세션이 시작 때 함께 읽습니다.

→ 자세히: 0장 생각 · 컨텍스트 썩음 · PARA · 팀 목표 문서 · LLM 위키 · 다음 에이전트를 위한 메모

3. 층 구조 — “언제 읽혀야 하나”로 다섯 층

기준은 “이 글이 언제 책상에 올라와야 하나”입니다. 다섯 층은 원문의 세 원리(시작 때 넣기 · 필요할 때 찾기 · 컨텍스트 창 바깥 파일에 적어 두기)를 Claude Code 의 실제 장치에 짝지어 이 가이드가 붙인 이름입니다.

층무엇 (원문 사실)더 보기
① 항상 읽힘사람이 쓴 지침 파일. 매 세션 시작 때 읽히고, 팀원도 만들어질 때 프로젝트의 CLAUDE.md 를 읽습니다. 파일당 200줄 아래 권장. AGENTS.md 는 여러 도구가 함께 읽는 오픈 형식으로, CLAUDE.md 에서 @AGENTS.md(@ 뒤에 적은 파일을 함께 읽게 하는 표기) 로 가져오거나, CLAUDE.md 가 없으면 Claude Code 가 바로 읽습니다.3장 · 잘 쓰는 법 · AGENTS.md
② 필요할 때스킬(절차·지식을 SKILL.md 가 든 폴더로 묶어 필요할 때만 불러오는 것). 평소엔 이름과 설명만, 본문은 쓸 때만 읽힙니다. 프로젝트 .claude/skills/ 에 커밋(git 저장소에 변경을 기록해 팀원과 나누는 일)하면 팀 공유.4장 · 언제 무엇에
③ 스스로 쌓음자동 메모리 — Claude 가 스스로 적는 메모. 시작 때 MEMORY.md 처음 200줄 또는 25KB 까지 읽힙니다. 저장소(프로젝트 파일과 그 변경 이력을 담은 폴더)마다 하나, 이 컴퓨터에만 있습니다. /memory 로 보고 고칩니다.5장 · 점검·편집
④ 인수인계인수인계 노트 — 진행 기록(claude-progress.txt)·기능 목록(feature_list.json)·git 커밋. 매 세션 같은 순서로 읽고 끝날 때 갱신합니다.7장 · 세션 시작 루틴
⑤ 바깥 연결MCP(AI 앱을 외부 도구·데이터에 잇는 표준 연결 방식 — “AI 앱용 USB-C 포트”). 프로젝트 범위 .mcp.json 을 커밋하면 팀이 같은 도구를 씁니다. 코딩 안 하는 팀은 Claude 프로젝트(프로젝트 지식 + 지침 + 대화).8장 · Claude 프로젝트

4. 팀 꾸리기 — 역할 파일 · 생성 지시문 · 3~5명

역할 정의 파일

.claude/agents/<이름>.md — 필수 칸은 name·description. 한 번 쓰면 서브에이전트(맡긴 일을 자기 컨텍스트에서 하고 결과만 돌려주는 도우미)로도, 에이전트 팀의 팀원으로도 씁니다. 프로젝트 폴더에 두면 팀이 함께, ~/.claude/agents/ 에 두면 나만.

역할 정의 · 서브에이전트

에이전트 팀 실험 기능

리더 1 + 팀원 여럿이 공유 작업 목록과 메시지로 협업합니다. 토큰(AI 가 읽고 쓰는 글의 양을 세는 단위)을 훨씬 많이 쓰므로 나란히 탐색할 가치가 있는 일에 씁니다.

에이전트 팀 · 한계

생성 지시문에 넣을 것

목표 · 출력 형식 · 쓸 도구와 출처 · 작업 경계. 팀원마다 다른 파일을 맡깁니다 — 같은 파일을 고치면 덮어쓰게 됩니다.

생성 지시문

팀 크기

대부분 3~5명으로 시작하고, 팀원 한 명당 작업 5~6개. “집중한 3명이 흩어진 5명보다 나은 경우가 많다”고 원문은 말합니다. 패턴은 가장 단순한 것부터.

5. 개인 팀 vs 회사 팀 — 범위로 나눕니다

지침 파일·스킬·역할 정의·MCP 서버는 어디에 저장하느냐에 따라 범위(scope — 어느 프로젝트에서 읽히고 누구와 나눠지는지)가 정해집니다. 범위는 넷이고, 넓은 범위부터 읽혀 이어 붙습니다.

범위지침 파일스킬 · 역할MCP함께 쓰는 사람
조직관리형 CLAUDE.md(회사 IT 관리자가 모든 컴퓨터에 깔아 두는 파일)관리 설정으로 배포관리 설정으로 제공조직의 모든 사용자
사용자~/.claude/CLAUDE.md~/.claude/skills/ · ~/.claude/agents/사용자 범위나만 (모든 프로젝트)
프로젝트./CLAUDE.md · AGENTS.md.claude/skills/ · .claude/agents/.mcp.json버전 관리로 팀원 모두
로컬./CLAUDE.local.md—로컬 범위(기본값)나만 (이 프로젝트)
이 가이드의 제안

개인 팀 = 사용자 범위 + 개인용 폴더 하나, 회사 팀 = 회사 저장소의 프로젝트 범위 + 조직 범위, 회사 일 속 “나만의 메모”는 로컬 범위. 에이전트 팀의 팀원은 CLAUDE.md·MCP 서버·스킬을 불러오므로, 같은 폴더(저장소)에서 띄우면 같은 맥락을 갖습니다. 자동 메모리는 그 컴퓨터에만 있으니 팀이 함께 봐야 할 사실은 저장소의 파일에 적습니다.

6. 시작 순서 — 활용편으로 따라 하기

  1. 준비 — 무엇을 쓸지(Claude Code · Claude 프로젝트) 고르고 팀마다 폴더 하나 만들기. 시작 전 준비
  2. 팀 목표 한 장 — 목표 파일을 쓰고 모든 세션이 읽게 하기. 실습 1
  3. 프로젝트 지침 파일 — /init 으로 시작하고 짧게 다듬기. 실습 2 (지식 창고 폴더는 실습 3 PARA)
  4. 개인 팀 — 나만의 공통 선호를 사용자 범위에. 실습 4
  5. 역할 하나 — 검토 담당 서브에이전트 정의. 실습 5
  6. 팀 띄우기 — 에이전트 팀을 띄우고 모두 같은 맥락인지 확인. 실습 6 실험 기능
  7. 필요해지면 — 반복 절차를 스킬로(실습 7), 인수인계 노트로 긴 일 잇기(실습 8), 회사 팀 공용 도구 연결·프로젝트 공유(실습 9).
  8. 막히면 — 에이전트가 지침·기억을 안 따를 때. 실습 10

7. 주의할 점

지침은 강제가 아니라 맥락입니다

Claude 는 CLAUDE.md 와 자동 메모리를 강제 설정이 아니라 맥락으로 다룹니다. 반드시 막아야 할 것은 훅(정해진 순간에 내 명령을 자동 실행하는 장치)·권한 규칙(deny)·관리 설정으로 겁니다. 같은 줄을 계속 놓친다면 훅으로 옮길 신호입니다. 안 따를 때는 /context all(지금 세션에 읽힌 파일 목록을 보여 주는 명령) 로 읽혔는지부터 확인합니다.

강제 장치 · 문제 해결

비밀 정보와 승인

세컨드 브레인에 적힌 것은 그 팀의 모든 에이전트에게 보인다고 생각합니다. 메모리·MCP 설정에 비밀 정보를 두지 않고, 공유하는 .mcp.json 에는 ${API_KEY} 처럼 환경 변수(비밀번호 같은 값을 파일 대신 컴퓨터 설정에 두고 이름으로 부르는 방식)로 적습니다. MCP 서버는 믿을 수 있는지 먼저 확인합니다(프롬프트 주입(가져온 글 속에 숨은 지시가 에이전트를 엉뚱하게 움직이게 하는 공격) 위험). 팀원은 내 대신 권한을 승인할 수 없고, 리더의 권한 모드(확인 창을 얼마나 띄울지 정한 설정)로 시작합니다 — 승인은 리더 세션에서 내가 합니다.
