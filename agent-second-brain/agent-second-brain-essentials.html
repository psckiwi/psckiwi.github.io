CHAPTER 01

에이전트는 무엇을 기억하나 — 컨텍스트의 한계

공용 기억을 설계하려면 먼저 에이전트의 “기억”이 어떻게 생겼는지 알아야 합니다. 에이전트가 아는 것은 지금 펼쳐 놓은 글, 곧 컨텍스트뿐입니다. 이 장에서는 컨텍스트의 한도와 약점, 그리고 그 약점을 피하는 세 가지 방법(압축 · 메모 · 필요할 때 불러오기)을 차례로 보고, 이것이 이 가이드의 “다섯 층” 구조로 어떻게 이어지는지 정리합니다.

컨텍스트 창 — 에이전트가 한 번에 펼쳐 보는 책상

Anthropic 의 컨텍스트 엔지니어링 글은 컨텍스트를 “모델이 답을 만들 때 함께 들어가는 토큰(AI 가 읽고 쓰는 글의 양을 세는 단위)의 묶음”이라고 정의합니다. 쉽게 말해 에이전트가 지금 책상 위에 펼쳐 둔 모든 글입니다. 컨텍스트 창(context window — 그 책상의 넓이, 한 번에 담을 수 있는 글의 한도)을 넘는 글은 올려놓을 수 없습니다.

책상 위에는 사람이 쓴 프롬프트(에이전트에게 보내는 지시문)만 있는 것이 아닙니다. 원문은 에이전트가 관리해야 할 컨텍스트로 시스템 지시, 도구, MCP, 외부 데이터, 대화 기록을 듭니다. 에이전트가 “생각 → 도구 사용 → 결과 확인”을 여러 차례 되풀이하며 일할수록 다음 차례에 쓸 만한 글이 계속 생기고, 무엇을 책상에 올릴지 매번 다시 골라야 합니다. 원문은 이 고르는 일을 컨텍스트 엔지니어링이라고 부르며, 좋은 문구를 찾는 프롬프트 작성의 다음 단계라고 설명합니다.

사실원문이 말하는 것공용 기억에 주는 뜻
새 세션 = 빈 책상Claude Code 의 모든 세션은 새 컨텍스트 창에서 시작남기고 싶은 것은 파일로 적어야 다음 세션이 봅니다
요청마다 전체 전송요청할 때마다 대화 전체를 보냄. 관계없는 일 세 개가 쌓인 세션은 네 번째 일의 매 차례에 셋을 다시 읽음책상에 쌓인 글은 쓸 때마다 비용이 듭니다
창은 넓어짐요즘 모델 대부분은 100만 토큰 창, 한도 가까이에서 자동 압축 — 창이 모자라는 일은 드묾문제는 “모자람”보다 “흐려짐”과 “비용”입니다(다음 소절)

컨텍스트 썩음 — 많이 넣을수록 흐려집니다

책상이 넓으면 무엇이든 다 올려 두면 될 것 같지만, 원문은 반대로 말합니다. 건초 더미에서 바늘 찾기 같은 시험에서 드러난 현상으로, 컨텍스트 창 안의 토큰이 늘어날수록 그 안의 정보를 정확히 떠올리는 힘이 떨어집니다. 원문은 이를 컨텍스트 썩음(context rot)이라 부르고, 정도의 차이는 있어도 모든 모델에서 나타난다고 적습니다.

원문은 사람의 작업 기억에 빗대어 언어 모델에도 주의력 예산(attention budget — 많은 글을 읽을 때 쓰는 집중력의 한도)이 있다고 말합니다. 새 토큰은 하나하나 이 예산을 조금씩 씁니다. 그래서 컨텍스트는 “쓸수록 효과가 줄어드는 한정된 자원”으로 다뤄야 합니다.

결론은 한 문장입니다. 좋은 컨텍스트란 원하는 결과가 나올 가능성을 가장 높이는, 꼭 필요한 정보만 담은 가장 작은 글 묶음입니다(원문 표현은 “신호가 강한 토큰의 가장 작은 묶음”). 공용 기억에 옮기면 “모두에게 항상 읽히는 파일은 짧고 알차게” 써야 한다는 뜻입니다.

지침 파일에 미치는 영향

Claude Code 메모리 문서는 CLAUDE.md 를 파일당 200줄 아래로 권합니다. 길수록 컨텍스트를 더 쓰고 지침을 덜 따르기 때문입니다.

강조보다 짧게

모범 사례 문서: 긴 파일 속에서 한 줄이 묻힌다면 강조를 더할 일이 아니라 파일을 줄일 일입니다. 꼭 지켜야 할 규칙은 훅이나 거부 규칙으로.

일과 일 사이 정리

창이 넓어진 지금도 /clear(지금 대화를 비우고 새로 시작하는 명령) 로 관계없는 일 사이를 끊는 것은 여전히 할 만합니다. 집중된 컨텍스트가 더 나은 답을, 더 적은 비용으로 줍니다.

구조화된 메모 — 책상 밖 노트에 적고, 다시 펼쳐 읽기

두 번째 방법이 구조화된 메모(structured note-taking — 에이전트가 컨텍스트 창 바깥 파일에 메모를 남기고 나중에 다시 읽어 들이는 것)입니다. 원문은 이를 “에이전트의 기억(agentic memory)”이라고도 부릅니다. 적은 노력으로 오래가는 기억을 만드는 방법으로, Claude Code 가 할 일 목록을 만드는 것이나 직접 만든 에이전트가 NOTES.md 파일을 관리하는 것이 그 예입니다.

원문은 코딩이 아닌 예로 포켓몬 게임을 하는 Claude를 듭니다. 이 에이전트는 수천 단계에 걸쳐 “1번 도로에서 1,234걸음째 훈련 중, 피카츄가 목표 10레벨 중 8레벨 올랐다” 같은 기록을 정확히 이어 갑니다. 메모 구조를 따로 알려 주지 않았는데도 탐험한 곳의 지도, 달성한 일, 상대별로 잘 통한 공격 같은 전략 메모를 스스로 남겼습니다. 컨텍스트가 초기화된 뒤에는 자기 메모를 읽고 몇 시간짜리 훈련과 던전 탐험을 이어 갔습니다.

이 가이드의 제안 — 메모를 “팀의 것”으로 원문의 메모는 대개 에이전트 한 명이 자기 다음 차례를 위해 남깁니다. 같은 파일을 팀 전원이 읽는 자리(예: 프로젝트 폴더)에 두고 양식을 정해 두면, 한 에이전트의 메모가 리더·다른 팀원·다음 세션 모두의 맥락이 됩니다. 이것이 이 가이드가 말하는 “팀이 함께 읽고 쓰는 세컨드 브레인”의 가장 작은 형태입니다.
한눈에 정리
  • 에이전트가 아는 것은 지금 컨텍스트 창(책상)에 올라온 글뿐이고, 새 세션은 빈 책상에서 시작합니다.
  • 글이 많을수록 정확히 떠올리는 힘이 완만하게 떨어집니다(컨텍스트 썩음). 좋은 컨텍스트는 “꼭 필요한 정보만 담은 가장 작은 묶음”입니다.
  • 긴 일에는 압축(요약해 이어 가기), 구조화된 메모(창 밖 파일에 적고 다시 읽기), 서브에이전트(요약만 돌려받기)를 일의 성격에 맞게 씁니다.
  • 자료는 미리 다 넣지 말고 경로·이름 같은 표시만 두고 필요할 때 찾게 합니다. Claude Code 는 CLAUDE.md 만 먼저 넣는 혼합형입니다.
  • 이 원리로 공용 기억을 다섯 층(항상 읽힘 · 필요할 때 · 스스로 쌓음 · 인수인계 · 바깥 연결)으로 나눕니다.

CHAPTER 02

세컨드 브레인 설계 — CODE 와 PARA 를 에이전트용으로

1장에서 “어느 층에 둘까”를 정했다면, 이 장은 “무엇을, 어떤 모양으로 둘까”를 정합니다. 사람의 세컨드 브레인(배운 것을 뇌 바깥 한곳에 모아 둔 디지털 지식 창고)을 만드는 방법으로 널리 쓰이는 Forte Labs 의 CODE(네 단계)와 PARA(네 칸 정리법)를 먼저 원문대로 살펴보고, 이를 에이전트 팀의 공용 기억에 옮기는 방법을 제안합니다. 핵심은 두 가지입니다. 모든 정보를 팀의 목표와 프로젝트에 묶어 정리하고, 모든 메모를 다음 에이전트가 바로 쓸 수 있게 적는 것입니다.

CODE — 세컨드 브레인을 만들고 쓰는 네 단계

Forte Labs 의 티아고 포르테는 세컨드 브레인을 만드는 방법을 CODE 네 단계로 정리합니다. Capture(모으기) · Organize(정리하기) · Distill(추리기) · Express(표현하기)입니다. 원문은 이것이 세컨드 브레인을 만드는 단계이자 이후 계속 함께 일하는 단계라고 말합니다. 직업이나 메모 도구에 상관없이 쓸 수 있고, 누구나 이미 어떤 형태로든 하고 있는 일이라고도 덧붙입니다.

단계원문의 뜻 (사람용)에이전트 팀으로 옮기면 (이 가이드의 제안)
모으기정말 중요한 것만, 마음에 와닿는 것만 한곳에 모음저장소(파일과 변경 이력을 함께 보관하는 프로젝트 폴더)·자료를 읽어서는 알 수 없는 결정·절차만 공용 기억에 적음
정리하기주제가 아니라 “실행에 쓸모”로 정리 — PARA폴더를 팀의 프로젝트·영역 기준으로 나눠, 에이전트가 이름과 자리로 찾게 함
추리기핵심만 남긴 짧은 요약을 겹겹이항상 읽히는 층은 요약만, 세부는 필요할 때 읽는 파일로
표현하기쌓은 지식으로 실제 결과물을 만들고 나눔세션마다 결과물 하나를 끝내고, 그 결과를 다시 공용 기억에 남김

PARA — 주제가 아니라 “실행”으로 나누는 네 칸

정리하기 단계에서 원문이 쓰는 방법이 PARA 입니다. 원문은 삶의 모든 정보가 단 네 칸에 들어간다고 말합니다.

Projects · 프로젝트

어떤 목표를 두고 하는 짧은 기간의 일. 예: 웹페이지 디자인 끝내기, 연구 보고서 쓰기.

Areas · 영역

시간을 두고 계속 챙기는 책임. 예: 마케팅, 인사, 건강, 재정. 끝나는 날이 없습니다.

Resources · 자원

앞으로 쓸모 있을지 모르는 관심 주제. 예: 그래픽 디자인, 사진, 습관 만들기.

Archives · 보관

앞의 세 칸에서 더는 활발하지 않은 것. 끝냈거나 멈춘 프로젝트, 관심이 식은 자원.

핵심 원칙은 “실행 가능성으로 정리하라”입니다. 학교에서 배운 대로 “마케팅”, “심리학” 같은 넓은 주제로 나누면, 바쁜 날 필요한 정보 하나를 찾느라 큰 칸을 뒤져야 합니다. 원문은 대신 지금 맡고 있는 프로젝트와 목표를 기준으로 정리하라고 합니다. 디자인 프로젝트를 시작하면 그에 필요한 메모·문서·자료가 한자리에 모여 있어야 한다는 것입니다.

에이전트에게도 이 정리법이 잘 맞는 이유는 1장에서 본 “필요할 때 불러오기”에 있습니다. 컨텍스트 엔지니어링 글은 폴더 구조·이름 규칙·날짜가 에이전트에게 “이 정보를 언제 어떻게 쓸지” 알려 주는 신호라고 말합니다. 프로젝트별로 나뉜 폴더는 에이전트가 지금 맡은 일에 필요한 파일만 골라 읽게 해 줍니다. 또 Claude Code 는 하위 폴더에 있는 CLAUDE.md(매 세션 읽히는, 사람이 쓴 지침 파일) 를 시작 때 읽지 않고, Claude 가 그 폴더의 파일을 읽거나 고칠 때 불러옵니다. 그래서 프로젝트마다 짧은 안내를 붙여 둘 수 있습니다.

팀 목표 문서 — 모두가 같은 목표를 보게 하는 한 장

이 가이드가 답하려는 질문의 절반은 “모든 에이전트가 같은 목표를 갖게 하려면?”입니다. PARA 원문이 그 실마리를 줍니다. 원문의 핵심 원칙은 정보를 “지금 약속한 프로젝트와 목표”에 따라 정리하라는 것이고, 프로젝트는 처음부터 “어떤 목표를 두고 하는 일”로 정의됩니다. 또 원문은 영역만 늘어놓은 목록으로는 지금의 노력을 장기 목표에 잇지 못한다고 경고합니다. 목표가 적혀 있고, 그 목표에 묶인 프로젝트 목록이 눈앞에 있어야 진행이 보인다는 것입니다.

이 가이드의 제안 — 팀 목표 문서를 하나 두고, 항상 읽히게 하기 팀마다 목표 문서 한 장(예시 이름 GOAL.md)을 만들고, 프로젝트 지침 파일 CLAUDE.md 에서 @GOAL.md 로 불러옵니다. 아래 사실 두 가지를 조합한 방법입니다.
  • CLAUDE.md 는 @경로 문법으로 다른 파일을 불러올 수 있고, 불러온 파일은 펼쳐져 그 CLAUDE.md 와 함께 컨텍스트에 들어갑니다(Claude Code 메모리 문서).
  • 에이전트 팀(리더 하나와 팀원 여럿이 함께 일하는 Claude Code 실험 기능)의 팀원은 생길 때 CLAUDE.md 를 읽고, 서브에이전트(맡긴 일을 자기 컨텍스트에서 하고 결과만 돌려주는 도우미)도 기본 제공 Explore·Plan 등 일부를 빼면 CLAUDE.md 를 읽습니다(에이전트 팀 · 서브에이전트 문서).
그래서 목표 문서는 리더·팀원·다음 세션 모두의 시작 컨텍스트에 들어갑니다. 대신 불러온 파일도 컨텍스트 비용은 그대로이므로 짧게 씁니다.

목표 문서에 무엇을 적을지는 원문의 원칙에서 끌어옵니다. 목표(무엇을 이루려 하나), 그 목표에 묶인 끝이 있는 프로젝트들, 끝났다고 말할 기준, 그리고 저장소를 읽어서는 알 수 없는 결정입니다. 아래 양식은 이 가이드가 만든 예시입니다.

카파시의 LLM 위키 — AI 가 쓰고 고치는 지식 창고

지금까지는 사람의 세컨드 브레인 정리법을 에이전트용으로 옮겼습니다. 반대로 정리하는 일 자체를 AI 에게 맡기는 방법도 있습니다. 안드레 카파시(Andrej Karpathy)가 공개한 「LLM Wiki」 글이 말하는 LLM 위키(AI 가 원문을 읽고 마크다운 위키를 직접 쓰고 고쳐 가는 지식 창고 방식)입니다. 원문은 스스로를 “아이디어 파일”이라고 소개합니다. 자기 에이전트(원문 예: OpenAI Codex, Claude Code, OpenCode / Pi)에 그대로 붙여 넣도록 만든 글로, 큰 생각만 전하고 세부는 에이전트가 사용자와 함께 만들어 간다는 것입니다.

RAG 와 무엇이 다른가. 원문은 흔한 방식부터 짚습니다. 파일을 올려 두면 AI 가 질문을 받을 때마다 관련 조각을 찾아 답을 만드는 RAG(질문할 때마다 자료 더미에서 관련 부분을 찾아 답에 붙이는 방식, 8장)입니다. NotebookLM, ChatGPT 파일 올리기, 대부분의 RAG 시스템이 이렇게 동작한다고 원문은 말합니다. 이 방식도 되긴 하지만 AI 가 질문마다 지식을 처음부터 다시 찾아냅니다. 문서 다섯 개를 엮어야 하는 미묘한 질문이면 매번 조각을 찾아 다시 맞춰야 하고, 아무것도 쌓이지 않습니다.

LLM 위키에서는 새 원문이 들어오면 AI 가 나중에 찾으려고 색인만 해 두지 않습니다. 읽고 핵심을 뽑아 이미 있는 위키에 엮어 넣습니다. 관련된 쪽을 고치고, 주제 요약을 다시 쓰고, 새 자료가 옛 주장과 어긋나는 곳을 표시합니다. 지식을 한 번 정리해 두고 계속 최신으로 유지하는 것이지, 질문마다 다시 끌어내는 것이 아닙니다.

원문의 핵심 문장

“the wiki is a persistent, compounding artifact.”
뜻: 위키는 사라지지 않고, 쓸수록 불어나는 결과물입니다. 서로 잇는 링크는 이미 있고, 모순은 이미 표시돼 있으며, 종합은 지금까지 읽은 모든 것을 반영합니다.

세 층. 원문은 구조를 세 층으로 나눕니다. 맨 아래 원문(raw sources)은 직접 골라 모은 글·논문·그림·데이터 파일입니다. 고치지 않는 기준 자료라서 AI 는 읽기만 하고 절대 바꾸지 않습니다. 가운데 위키(the wiki)는 AI 가 만든 마크다운 파일 폴더입니다. 요약, 대상별 쪽, 개념 쪽, 비교, 개요, 종합이 들어가며 이 층은 AI 가 전부 맡습니다 — 사람은 읽고, AI 가 씁니다. 그리고 스키마(the schema)는 위키의 구조·약속·작업 순서를 AI 에게 알려 주는 문서로, 원문 예는 Claude Code 의 CLAUDE.md, Codex 의 AGENTS.md 입니다.

세 작업 — 넣기 · 묻기 · 점검. 위키는 세 가지 일로 굴러갑니다. 아래 단계를 눌러 보세요.

1단계 · 넣기 (Ingest) — 새 원문을 원문 폴더에 넣고 AI 에게 처리하라고 합니다. 원문이 드는 흐름 예: AI 가 원문을 읽고, 핵심을 사람과 이야기하고, 위키에 요약 쪽을 쓰고, 목차를 고치고, 관련된 대상·개념 쪽을 고치고, 일지에 한 줄을 덧붙입니다. 원문 하나가 위키 10~15쪽을 건드릴 수도 있습니다. 원문 저자는 하나씩 넣으며 요약을 읽고 무엇을 강조할지 직접 이끄는 쪽을 좋아하지만, 여러 개를 한꺼번에 넣고 덜 지켜보는 방법도 있다고 합니다. 어떤 방식이든 정해지면 스키마에 적어 다음 세션도 따르게 합니다.
2단계 · 묻기 (Query) — 위키에 질문합니다. AI 는 관련 쪽을 찾아 읽고 인용을 붙여 답합니다. 답은 질문에 따라 마크다운 쪽, 비교표, 슬라이드(Marp), 차트(matplotlib) 등 여러 모양일 수 있습니다. 원문이 꼽는 중요한 깨달음은 좋은 답은 위키에 새 쪽으로 되돌려 넣을 수 있다는 것입니다. 부탁해서 얻은 비교, 분석, 새로 찾은 연결은 대화 기록 속에 사라지면 안 되는 값진 것이고, 이렇게 하면 탐구한 내용도 넣은 원문처럼 위키에 쌓입니다.
3단계 · 점검 (Lint) — 때때로 AI 에게 위키 건강 검진을 시킵니다. 원문의 점검 목록: 쪽끼리 어긋나는 내용, 새 원문 때문에 낡은 주장, 들어오는 링크가 없는 외톨이 쪽, 자주 언급되는데 자기 쪽이 없는 개념, 빠진 상호 링크, 웹 검색으로 채울 수 있는 빈 곳. AI 는 새로 물어볼 질문과 찾아볼 원문을 제안하는 데도 능하다고 원문은 말합니다.

두 특별 파일 — index.md 와 log.md. 위키가 커져도 AI(와 사람)가 길을 잃지 않게 두 파일을 둡니다. 쓰임이 다릅니다.

index.md — 내용 목차

위키의 모든 쪽을 링크 · 한 줄 요약(필요하면 날짜·원문 수)과 함께 갈래별로 적은 목록입니다. AI 는 넣기 때마다 고치고, 질문을 받으면 목차부터 읽고 관련 쪽으로 들어갑니다. 원문은 이것이 중간 규모(원문 약 100개, 위키 수백 쪽)에서 놀랄 만큼 잘 되며, 임베딩 기반 RAG(글을 숫자로 바꿔 비슷한 조각을 찾는 검색 장치)를 따로 갖추지 않아도 된다고 합니다.

log.md — 시간순 일지

넣기 · 묻기 · 점검이 언제 있었는지 덧붙이기만 하는 기록입니다. 위키가 어떻게 자라 왔는지 보여 주고, AI 가 최근에 무엇을 했는지 알게 해 줍니다. 원문 팁: 항목마다 같은 머리말로 시작하면 간단한 명령으로 읽을 수 있습니다.

## [2026-04-02] ingest | Article Title

원문 예시 그대로입니다. 그러면 grep "^## \[" log.md | tail -5 로 최근 다섯 항목을 볼 수 있습니다.

사람의 일과 AI 의 일. 원문은 위키를 사람이 직접 쓰는 일은 없다(또는 드물다)고 말합니다. 원문 저자는 한쪽에 AI 에이전트, 다른 쪽에 Obsidian(마크다운 메모 앱)을 띄워 두고, AI 가 대화에 따라 고친 결과를 실시간으로 훑어본다고 합니다. 그 비유가 “Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.”(뜻: Obsidian 은 작업 화면, AI 는 프로그래머, 위키는 코드입니다)입니다.

왜 잘 되나. 원문은 지식 창고 관리에서 지루한 것은 읽거나 생각하는 일이 아니라 장부 정리라고 말합니다. 상호 링크 고치기, 요약을 최신으로 두기, 새 자료가 옛 주장과 어긋날 때 표시하기, 수십 쪽에 걸친 일관성 지키기입니다. 사람은 관리 부담이 가치보다 빨리 커져서 위키를 버리지만, AI 는 지루해하지 않고 링크 고치기를 잊지 않으며 한 번에 15개 파일을 고칠 수 있습니다. 원문은 이 생각이 배니바 부시의 메멕스(Memex, 1945 — 문서 사이에 연결 길을 낸 개인 지식 창고 구상)와 닮았고, 부시가 풀지 못한 “누가 관리하나”를 AI 가 맡는다고 덧붙입니다.

이 밖에 경쟁 분석, 실사, 여행 계획, 강의 메모, 취미 탐구처럼 시간을 두고 지식을 모으며 흩어지지 않게 정리하고 싶은 모든 일에 쓸 수 있다고 원문은 말합니다.

원문은 일부러 추상적입니다 원문 끝의 메모: 이 글은 생각을 설명할 뿐 특정 구현이 아니며, 폴더 구조 · 스키마 약속 · 쪽 양식 · 도구는 모두 분야·취향·쓰는 AI 에 따라 다르고, 앞의 모든 것은 고르고 버릴 수 있는 선택지라고 합니다. 예를 들어 글만 다루면 그림 처리는 필요 없고, 위키가 작으면 목차 파일만으로 충분합니다. 올바른 사용법은 이 글을 자기 에이전트와 나누고 함께 맞는 판을 만드는 것입니다. 그래서 아래 연결 방법도 하나의 예입니다.
이 가이드의 제안 — LLM 위키를 이 가이드의 공용 기억에 끼우기

아래 대응은 원문에 없는 이 가이드의 연결 방법입니다. 원문 층은 받아 둔 자료, 스키마는 지침 파일(3장), 위키는 PARA 와 함께 쓰는 팀 지식 창고, log.md 는 인수인계 노트(7장), 점검은 정기 점검(9장)에 대응합니다. 에이전트 팀이라면 여러 팀원이 같은 위키를 읽고, 쓰기는 한 명(또는 리더)이 맡기를 권합니다. 같은 파일을 여럿이 고치면 덮어쓰기 쉽기 때문입니다(6장).

CHAPTER 03

항상 읽히는 층 — CLAUDE.md 와 AGENTS.md

팀 안의 모든 에이전트가 같은 목표와 맥락으로 일하게 만드는 가장 기본 도구는 지침 파일입니다. 사람이 써 두면 에이전트가 세션을 시작할 때마다 읽습니다. 이 장은 지침 파일을 어디에 두고, 어떻게 짧고 분명하게 쓰고, 안 읽힐 때 무엇을 확인하는지 다룹니다.

지침 파일이란 — 팀 전원이 매번 읽는 공용 기억

무엇인가 — Claude Code(Anthropic 이 만든, 글로 지시하면 파일을 읽고 고치고 명령을 실행하는 AI 에이전트 도구)의 세션은 늘 빈 컨텍스트 창에서 시작합니다. 컨텍스트(에이전트가 한 번에 보고 있는 글 전체)가 비어 있으니 어제 대화에서 정한 것을 오늘의 에이전트는 모릅니다. 원문은 세션을 넘어 지식을 이어 주는 장치를 두 가지로 설명합니다.

왜 "팀의 공용 기억"인가 — 에이전트 팀실험 기능에서도 같은 일이 일어납니다. 원문은 이렇게 적습니다.

뜻: 팀원은 만들어질 때 보통 세션과 같은 프로젝트 맥락 — CLAUDE.md, MCP 서버, 스킬 — 을 불러옵니다. 그리고 리더의 대화 기록은 넘어가지 않고, 리더가 준 생성 지시문(spawn prompt — 리더가 팀원을 만들 때 주는 첫 지시)만 받습니다.
쉽게 말하면지침 파일은 회사 휴게실 벽에 붙인 "우리 팀 규칙" 게시판과 같습니다. 새로 들어온 사람도, 오늘 출근한 사람도 문을 열면 먼저 그 게시판을 봅니다. 말로만 전한 내용(대화)은 그 자리에 있던 사람만 알지만, 게시판에 붙인 것은 모두가 압니다.

주의할 점 — 강제 설정이 아니라 맥락 — 원문은 Claude 가 지침 파일을 "강제되는 설정이 아니라 맥락(context, not enforced configuration)"으로 다룬다고 분명히 적습니다. Claude 는 읽고 따르려 하지만 반드시 지킨다는 보장은 없습니다. 지시가 구체적이고 짧을수록 더 꾸준히 따릅니다.

반드시 막아야 하는 것은 지침 파일이 아니라 훅·권한 규칙으로"이 폴더는 절대 고치지 마"처럼 예외 없이 지켜야 하는 것은 훅(hook — 정해진 순간마다 Claude Code 가 자동으로 실행하는 명령)이나 거부 규칙(permissions.deny)으로 겁니다. 이것들은 Claude 가 무엇을 판단하든 Claude Code 가 매번 적용합니다. 자세한 구분은 9장에서 다룹니다.

  • 지침은 강제 설정이 아니라 맥락입니다. 반드시 막아야 할 것은 훅·권한 규칙·관리 설정으로 겁니다.
  • 범위 4종: 조직(관리자 배포) · 사용자 ~/.claude/CLAUDE.md(나만, 모든 프로젝트) · 프로젝트 ./CLAUDE.md(팀이 git 으로 공유) · 로컬 ./CLAUDE.local.md(나만, 이 프로젝트). 팀 전원이 같은 목표를 읽게 하는 자리는 프로젝트 범위입니다.
  • 찾은 파일은 덮어쓰지 않고 넓은 범위 → 좁은 범위, 위 폴더 → 작업 폴더 순으로 이어 붙습니다. 하위 폴더 지침은 그 폴더를 만질 때 읽힙니다.
  • 잘 쓰기: 같은 정정을 두 번 하면 한 줄 더하기 · 확인할 수 있게 구체적으로 · 파일당 200줄 아래 · 충돌 정리. 일부 파일용은 .claude/rules/(paths), 여러 단계 절차는 스킬로.
  • @경로 가져오기는 정리에 좋지만 컨텍스트는 줄이지 않습니다. AGENTS.md 는 여러 도구가 함께 읽는 오픈 형식이며, CLAUDE.md 가 있으면 @AGENTS.md 로 가져옵니다.
  • 안 따를 때: /context all 로 읽혔는지 → 위치 → 구체성·충돌 → 훅이 맞는지. /memory 로 고치고, /doctor 로 덜어 낼 것을 찾습니다.

CHAPTER 04

필요할 때 읽히는 층 — 스킬

3장의 지침 파일은 매 세션 처음부터 읽힙니다. 그런데 팀의 배포 순서, 장애 대응 절차, 보고서 쓰는 법처럼 길지만 가끔 필요한 지식까지 거기에 넣으면 모든 일이 무거워집니다. 이런 것을 폴더로 묶어 필요할 때만 꺼내 읽히는 장치가 스킬입니다.

스킬이란 — 필요할 때만 펼치는 절차서

무엇인가 — 스킬(Skill — 절차나 지식을 SKILL.md 파일이 든 폴더로 묶어, 필요할 때만 불러오는 것)은 Claude 가 할 수 있는 일을 넓혀 줍니다. SKILL.md 에 지시를 적어 두면 Claude 가 그것을 자기 도구함에 넣고, 관련 있는 일이 오면 스스로 꺼내 쓰거나 내가 /스킬-이름 으로 바로 부릅니다.

왜 필요한가 — 원문은 이렇게 설명합니다. 더 뛰어난 모델은 공학 지식은 더 많이 알지만, 우리 팀이 출시를 어떻게 하는지, 장애 대응 문서에 무엇이 적혀 있는지, API 문서를 어떤 모양으로 쓰길 원하는지는 모릅니다. 그런 지식을 스킬에 담습니다. 그리고 CLAUDE.md 와 달리 스킬의 본문은 쓸 때만 읽히므로, 긴 참고 자료도 필요해지기 전까지는 컨텍스트(에이전트가 한 번에 보고 있는 글 전체)를 거의 쓰지 않습니다.

쉽게 말하면CLAUDE.md 가 휴게실 벽의 "팀 규칙" 게시판이라면, 스킬은 책장에 꽂힌 업무 매뉴얼 바인더입니다. 평소에는 책등의 제목만 보이고, 그 일을 할 때 해당 바인더를 꺼내 펼칩니다. 바인더가 많아도 벽 게시판처럼 늘 눈앞을 가리지 않습니다.

알아 둘 것

  • 예전 "사용자 정의 명령"은 스킬로 합쳐졌습니다. .claude/commands/deploy.md 파일과 .claude/skills/deploy/SKILL.md 스킬은 둘 다 /deploy 를 만들고 똑같이 동작합니다. 스킬은 여기에 보조 파일 폴더, 누가 부를지 정하는 설정, Claude 가 알아서 불러오는 기능을 더합니다.
  • 여러 AI 도구가 함께 쓰는 표준: Claude Code 스킬은 Agent Skills 오픈 표준을 따르고, 그 위에 몇 가지 기능을 더했습니다.
  • 처음부터 들어 있는 스킬: /doctor, /code-review, /batch, /debug, /loop, /claude-api 같은 내장 스킬(bundled skills)이 있고, 내가 만든 스킬과 같은 방법으로 부릅니다.

언제 무엇에 — CLAUDE.md · 규칙 · 스킬 · 훅

스킬을 만들 때 — 원문이 꼽는 신호는 두 가지입니다. ① 같은 지시·체크리스트·여러 단계 절차를 채팅에 계속 붙여 넣고 있을 때, ② CLAUDE.md 의 한 부분이 "사실"이 아니라 "절차"로 커졌을 때입니다.

한눈에 정리

  • 안 불리면 설명의 단어부터 고칩니다. 중간에 잊으면 계속 지킬 지시로 고쳐 쓰거나 다시 부르고, 꼭 지킬 것은 훅으로.

이 소절은 개발자용입니다. Claude Code 나 Claude 프로젝트만 쓴다면 “직접 만든 에이전트도 파일 폴더로 기억을 이어 간다”는 것만 알고 보안으로 넘어가도 됩니다.

핵심: Claude 는 "부탁"만, 실제 저장은 내 프로그램이

메모리 도구는 클라이언트 쪽(client-side)에서 돌아갑니다. Claude 는 "이 파일 보여 줘", "이 파일 만들어 줘" 하고 요청만 하고, 그 요청을 실제 저장소에서 실행해 결과를 돌려주는 것은 내 애플리케이션입니다. 그래서 데이터를 어디에·어떻게 둘지 내가 정합니다. /memories 는 앞머리 경로일 뿐이고, 내 처리기(handler — 요청을 받아 실제로 실행하는 코드)가 이를 사용자별 폴더나 데이터베이스 키 같은 실제 저장소에 연결합니다.

한 번의 흐름 — 고객 문의 답장 예

1. 사용자 요청 — "Help me respond to this customer service ticket." 뜻: 이 고객 문의에 답장하도록 도와줘.

사용자
Help me respond to this customer service ticket.

2. Claude 가 기억 폴더부터 확인 — 메모리 도구가 켜져 있으면 Claude 는 일을 시작하기 전에 자동으로 기억 폴더를 봅니다.

{ "type": "tool_use", "name": "memory",
  "input": { "command": "view", "path": "/memories" } }

3. 내 앱이 폴더 내용을 돌려줌 — /memories/customer_service_guidelines.xml, /memories/refund_policies.xml 두 파일이 있다고 알려 줍니다.

{ "command": "view", "path": "/memories/customer_service_guidelines.xml" }

5. 기억을 바탕으로 답함 — "Based on your customer service guidelines, I can help you craft a response…" 뜻: 저장된 응대 지침에 따라 답장 작성을 돕겠습니다.

시작하기 — 두 단계

  1. 요청에 도구 추가요청의 tools 에 {"type": "memory_20250818", "name": "memory"} 를 넣는 것이 설정의 전부입니다. 이름은 반드시 memory, 입력 형식은 따로 정의하지 않습니다.
  2. 처리기 구현메모리 명령마다 클라이언트 쪽 처리기를 만듭니다. /memories 밖의 경로는 반드시 거절해야 하므로 아래 보안을 먼저 읽습니다.

도구를 넣으면 API 가 시스템 프롬프트에 "무엇보다 먼저 기억 폴더를 보라, 진행하면서 상태·진행·생각을 기억에 적어라"는 지시를 자동으로 덧붙입니다. 그 안의 한 줄이 이 도구의 정신을 잘 보여 줍니다 — "ASSUME INTERRUPTION"(뜻: 중단될 것을 가정하라 — 컨텍스트 창은 언제든 초기화될 수 있으니, 기억 폴더에 적지 않은 진행은 잃을 수 있다).

압축과 함께 쓰기

압축(compaction — 대화가 길어지면 오래된 부분을 요약해 줄이는 것)은 컨텍스트를 작게 유지하고, 메모리는 요약을 거쳐도 반드시 살아남아야 할 정보를 지킵니다. 원문은 오래 도는 에이전트에 둘 다 쓰기를 권합니다.

여러 세션에 걸친 일

첫 세션이 진행 기록·기능 목록을 먼저 만들고, 이후 세션은 그것을 읽고 시작하며, 끝날 때 갱신하는 패턴이 있습니다. 자세한 내용은 7장 인수인계 노트에서 다룹니다.

한눈에 정리
  • 자동 메모리는 Claude 가 스스로 적는 메모(사람·교정·진행 상황·찾을 곳 네 종류)입니다. 지침 파일(사람이 씀)과 구분합니다.
  • 저장소마다 ~/.claude/projects/<project>/memory/ 하나 — 워크트리끼리 공유, 이 컴퓨터에만 있음. 시작 때 MEMORY.md 처음 200줄 또는 25KB 만 읽고, 주제 파일은 필요할 때 읽습니다.
  • /memory 로 기억 파일을 보고·고치고·자동 메모리를 켜고 끕니다. "기억해"는 자동 메모리로, "CLAUDE.md 에 추가해"는 지침 파일로 갑니다.
  • 서브에이전트는 메인의 자동 메모리를 받지 않습니다. 역할 파일에 memory: project(권장 기본)·user·local 을 적으면 역할마다 자기 기억이 생깁니다.
  • Claude API 메모리 도구는 /memories 파일 폴더로 대화를 넘어 기억합니다. Claude 는 요청만, 실행·저장은 내 애플리케이션이 합니다.
  • 보안: 비밀 정보 거르기, 크기 한도, 오래된 기억 지우기, /memories 밖 경로 막기. 기억은 강제 설정이 아니라 맥락이라, 꼭 막을 것은 훅으로.

이 장의 나머지 소절과 🔧 세부는 완전 가이드 5장에 있습니다.

CHAPTER 06

팀 꾸리기 — 서브에이전트와 에이전트 팀

이제 여러 에이전트를 한 팀으로 묶을 차례입니다. 역할을 파일 하나로 정의하고, 그 역할을 서브에이전트나 팀원으로 불러 씁니다. 이 장의 핵심 질문은 "새로 생긴 팀원은 무엇을 알고 시작하나"입니다 — 그 답이 왜 팀에 세컨드 브레인이 필요한지를 보여 줍니다.

역할 정의 — 한 번 쓰고 여러 번 쓰기

한 줄 비유 역할 정의 파일은 직무 기술서입니다. "검토 담당은 이런 일을 하고, 이 도구만 쓰고, 이런 기준으로 본다"를 한 장에 적어 두면, 그 사람을 잠깐 불러 일을 맡길 때(서브에이전트)도, 팀 회의에 정식 팀원으로 앉힐 때(에이전트 팀)도 같은 기술서를 씁니다.

역할 정의 파일은 .claude/agents/<이름>.md 같은 마크다운 파일입니다. 맨 위 --- 사이 머리말에 이름·설명·도구 같은 설정을 적고, 그 아래 본문이 그 역할의 시스템 프롬프트(에이전트에게 맨 먼저 주어지는 기본 지시문)가 됩니다. 꼭 필요한 칸은 name(이름)과 description(언제 이 역할에게 맡길지)뿐입니다.

---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.

뜻: 이름 code-reviewer, "코드 품질·모범 관행을 검토함", 쓸 도구는 읽기·찾기(Read, Glob, Grep)만, 모델은 sonnet. 본문 — "너는 코드 검토자다. 불려 오면 코드를 분석해 품질·보안·모범 관행에 대해 구체적이고 실행할 수 있는 의견을 줘라."

어디에 두나 — 누가 쓸 수 있는가

파일을 둔 위치가 "누가 이 역할을 쓸 수 있는지"를 정합니다. 같은 이름이 여러 곳에 있으면 우선순위가 높은 쪽이 이깁니다.

위치범위우선순위
관리 설정(managed settings)조직 전체 — 관리자가 배포1 (가장 높음)
--agents 실행 옵션이번 세션만(디스크에 저장 안 됨)2
.claude/agents/이 프로젝트 — 저장소에 올려 팀이 함께 씀3
~/.claude/agents/내 모든 프로젝트 — 개인용4
플러그인의 agents/플러그인을 켠 곳5 (가장 낮음)
이 가이드의 제안 — 개인 팀과 회사 팀 원문은 프로젝트 역할(.claude/agents/)을 버전 관리에 올려 팀이 함께 쓰고 고치라고 권합니다. 그래서 회사 팀의 역할(예시 이름: reviewer, researcher)은 회사 저장소의 .claude/agents/ 에, 내 개인 업무에서만 쓰는 역할은 ~/.claude/agents/ 에 두면 범위가 자연스럽게 나뉩니다. 범위 전반은 9장에서 다룹니다.

에이전트 팀 — 리더와 팀원 실험 기능

에이전트 팀은 Claude Code 세션 여럿을 한 팀으로 움직이는 기능입니다. 세션 하나가 리더(team lead)가 되어 일을 나누고 맡기고 결과를 모읍니다. 팀원(teammate)은 각자 자기 컨텍스트 창에서 따로 일하면서 서로 직접 메시지를 주고받습니다. 나도 리더를 거치지 않고 어느 팀원에게나 바로 말할 수 있습니다. 원문은 이 기능이 실험 기능이며 기본으로 꺼져 있다고 밝힙니다.

언제 쓰나

원문은 나란히 탐색하는 것이 실제로 가치를 더할 때 가장 효과적이라고 합니다. 가장 강한 쓰임은 넷입니다 — 여럿이 다른 측면을 조사하고 서로의 결과를 따져 보는 조사·검토, 각자 다른 조각을 맡는 새 모듈·기능, 서로 다른 가설을 동시에 시험하는 디버깅, 화면·서버·테스트를 각각 맡는 여러 층에 걸친 변경. 반대로 순서대로 해야 하는 일, 같은 파일을 고치는 일, 서로 얽힌 일이 많으면 한 세션이나 서브에이전트가 낫습니다. 팀은 조율에 드는 수고가 있고, 한 세션보다 토큰을 훨씬 많이 씁니다.

시작하기 — 말로 부탁하기

기능을 켠 뒤, 할 일과 원하는 팀원을 자연어로 설명하면 Claude 가 팀원을 만들고 조율합니다.

I'm designing a CLI tool that helps developers track TODO comments across
their codebase. Spawn three teammates to explore this from different angles:
one on UX, one on technical architecture, one playing devil's advocate.

뜻: 코드 속 TODO 주석을 추적하는 CLI 도구를 설계하고 있어. 팀원 셋을 만들어 다른 각도에서 살펴봐 — 하나는 사용 경험, 하나는 기술 구조, 하나는 일부러 반대 의견을 내는 역할.

공유 작업 목록 (예시 — 원문의 작업 상태를 바탕으로 그린 흉내)
ux 사용 흐름 정리completed · 완료
architect 저장 구조 비교in progress · 진행 중
(미배정) 반대 의견 검토pending · 대기
(미배정) 최종 설계 정리blocked · 앞 작업 기다림

작업은 대기·진행 중·완료 세 상태이고, 다른 작업에 기대는 작업은 앞 작업이 끝날 때까지 막힘으로 보입니다. 리더가 직접 배정하거나, 팀원이 일을 끝낸 뒤 배정 안 된·막히지 않은 다음 작업을 스스로 집어 갑니다(동시에 집지 않도록 파일 잠금을 씀). 팀원을 끝낼 때는 이름으로 부탁합니다 — "Ask the researcher teammate to shut down"(뜻: researcher 팀원에게 종료하라고 해).

팀원이 시작 때 받는 것 — 그래서 세컨드 브레인이 필요합니다

이 가이드가 답하려는 질문 — "팀 안의 모든 에이전트가 같은 목표와 맥락을 갖게 하려면?" — 의 열쇠가 이 소절입니다. 원문은 팀원이 만들어질 때 받는 것을 분명히 적어 둡니다.

팀원이 받는 것

  • 일반 세션과 같은 프로젝트 맥락 — CLAUDE.md, MCP 서버, 스킬
  • 리더가 준 생성 지시문
  • 리더가 정해 준 이름 — 누구에게나 이름으로 메시지 가능

팀원이 받지 못하는 것

  • 리더의 대화 기록 — 리더가 나와 나눈 이야기, 이미 읽은 파일
  • (서브에이전트의 경우) 메인 대화의 자동 메모리, 이미 부른 스킬, 출력 스타일 — 대신 CLAUDE.md 와 Claude 가 쓴 위임 메시지를 받습니다
그래서 — 목표와 맥락은 "대화"가 아니라 "파일"에

리더와 오래 이야기해 정한 목표도, 팀원에게는 파일에 적혀 있거나 생성 지시문에 들어 있지 않으면 없는 것입니다. 원문 사실(팀원은 CLAUDE.md·MCP·스킬을 읽는다)을 뒤집어 보면, 팀 전체가 공유해야 할 목표·용어·결정은 모두가 시작 때 읽는 파일에 두면 된다는 뜻이 됩니다. 이것이 이 가이드가 말하는 세컨드 브레인 — 팀이 함께 읽고 쓰는 공용 기억 파일 묶음 — 입니다.

이 가이드의 제안 — 세 군데에 나눠 담기
  1. 항상 알아야 할 것(팀 목표 한 단락, 지켜야 할 규칙, 용어): 프로젝트 CLAUDE.md 또는 그 CLAUDE.md 가 가져오는 파일(예시 이름 GOAL.md) — 3장.
  2. 필요할 때 꺼낼 것(절차, 참고 지식): 스킬 — 4장.
  3. 이번 일에만 필요한 것(맡은 파일, 마감, 출력 형식): 생성 지시문 — 다음 소절.
서브에이전트에게 꼭 전해야 할 규칙이 있으면 위임할 때 지시에 다시 적으라고 원문은 권합니다(예: "vendor/ 폴더는 무시").
한눈에 정리
  • 역할 정의 파일(.claude/agents/<이름>.md, 필수 칸은 name·description)을 한 번 쓰면 서브에이전트로도, 에이전트 팀의 팀원으로도 씁니다. 프로젝트 폴더에 두면 팀이 함께, ~/.claude/agents/ 에 두면 나만 씁니다.
  • 서브에이전트는 자기 컨텍스트에서 일하고 요약만 돌려줍니다 — 긴 출력 격리, 나란히 조사, 차례로 잇기.
  • 에이전트 팀실험 기능은 리더 1 + 팀원 여럿이 공유 작업 목록과 메시지로 협업합니다. 토큰을 훨씬 많이 쓰므로 나란히 탐색이 가치 있는 일에.
  • 팀원이 시작 때 받는 것은 CLAUDE.md·MCP 서버·스킬 + 생성 지시문뿐, 리더의 대화 기록은 넘어가지 않습니다. 그래서 팀 목표·맥락은 대화가 아니라 모두가 읽는 파일(세컨드 브레인)에 둡니다.
  • 생성 지시문에는 목표·출력 형식·도구와 출처·작업 경계를 넣습니다. 팀원마다 다른 파일을 맡깁니다.
  • 팀은 대부분 3~5명으로 시작하고, 팀원당 작업 5~6개. 패턴은 가장 단순한 것부터.
  • 한계: 이어 열면 팀원이 안 돌아옴, 세션당 팀 하나, 팀 안의 팀 없음, 리더 고정. 팀원은 내 대신 권한을 승인할 수 없습니다.

CHAPTER 07

이어 달리기 — 인수인계 노트와 긴 작업

몇 시간, 며칠짜리 일은 한 세션 안에 끝나지 않습니다. 새 세션은 앞 세션이 한 일을 전혀 모른 채 시작합니다. 이 장은 다음 세션·다른 에이전트가 바통을 이어받을 수 있게 인수인계 노트를 남기는 방법을 다룹니다. 세컨드 브레인에서 "지금 어디까지 왔나"를 맡는 층입니다.

긴 작업의 문제 — 새 세션은 앞 일을 모른다

쉽게 비유하면 교대 근무하는 공장을 떠올려 보세요. 그런데 이 공장은 이상해서, 새로 출근한 사람은 앞 근무조가 무엇을 했는지 하나도 기억하지 못합니다. 교대 일지가 없으면 새 사람은 "어디까지 했지?"를 추측하느라 시간을 다 씁니다. 원문(Anthropic 엔지니어링 블로그)이 든 비유가 바로 이것입니다 — 에이전트의 세션 하나하나가 그 근무조입니다.

에이전트는 세션(에이전트를 한 번 켜서 끌 때까지의 작업 한 판) 단위로 일하고, 새 세션은 앞 세션의 기억 없이 시작합니다. 컨텍스트 창(에이전트가 한 번에 담을 수 있는 글의 한도)에는 한도가 있고, 복잡한 일은 창 하나 안에 끝나지 않습니다. 그래서 세션과 세션 사이에 다리가 필요합니다.

압축만으로는 부족했다

Claude Agent SDK(Anthropic 이 만든, 에이전트를 직접 만들 때 쓰는 도구 모음)에는 압축(compaction — 대화가 길어지면 앞부분을 요약해 창을 비우는 기능, 1장)이 있습니다. 이론상 그러면 끝없이 일할 수 있을 것 같지만, 원문 실험에서는 "claude.ai 를 똑같이 만들어 줘" 같은 큰 지시 하나만으로는 제품 수준의 웹 앱을 완성하지 못했습니다. 압축이 다음 에이전트에게 늘 완벽하게 분명한 지시를 넘겨주지는 않기 때문입니다.

실패 1 — 한 번에 다 하려 함

앱 전체를 한 번에 만들려다 구현 도중 컨텍스트가 바닥납니다. 다음 세션은 반쯤 만들어지고 기록도 없는 기능을 물려받아, 무슨 일이 있었는지 추측하고 기본 동작을 되살리는 데 시간을 씁니다.

실패 2 — 너무 일찍 "다 했다"

일이 꽤 진행된 뒤, 새 세션이 둘러보고 진척이 있는 것을 보고는 일이 끝났다고 선언해 버립니다. 남은 일이 무엇인지 알려 주는 목록이 없어서입니다.

원문은 이 문제를 둘로 나눕니다. ① 처음에 모든 기능의 토대가 될 환경을 준비해 한 단계씩 일하게 만들고, ② 매 세션이 목표를 향해 조금씩 나아가되 끝날 때는 깨끗한 상태로 두게 하는 것입니다. "깨끗한 상태"란 큰 버그가 없고 정리·기록이 되어 있어, 다음 사람이 엉뚱한 뒷정리 없이 바로 새 일을 시작할 수 있는 상태를 말합니다.

진행 기록 파일과 git — 다음 사람을 위한 메모

원문의 해결책은 두 가지 역할입니다. 맨 처음 세션만 다른 지시를 받아 환경을 준비하고, 그 뒤의 모든 세션은 조금씩 일하고 기록을 남깁니다. 원문 각주에 따르면 둘은 첫 지시만 다를 뿐, 시스템 프롬프트·도구·하네스(에이전트를 감싸 도구 사용과 반복 실행을 맡는 틀)는 똑같습니다.

남기는 것하는 일
claude-progress.txt에이전트들이 한 일을 적어 두는 기록 파일. 각 세션이 끝날 때 진행 요약을 씁니다.
git 기록git(파일이 어떻게 바뀌었는지 이력을 저장하는 도구)에 설명이 붙은 커밋(변경 묶음 하나를 이력에 저장하는 일)을 남깁니다. 잘못된 변경을 되돌리고 잘 돌아가던 상태로 돌아갈 수 있습니다.
feature_list.json해야 할 기능 전체 목록과 각 기능의 통과 여부(다음 소절).
init.sh개발 서버(만든 앱을 내 컴퓨터에서 미리 띄워 보는 프로그램)를 켜는 스크립트. 다음 세션이 "앱을 어떻게 실행하지?"를 헤매지 않게 합니다.

원문의 핵심 통찰은 새 컨텍스트 창으로 시작한 에이전트가 작업 상태를 빨리 파악하게 하는 것이었고, 그것을 claude-progress.txt 와 git 기록이 해냈습니다. 원문은 이 방법을 "유능한 엔지니어가 매일 하는 일"에서 가져왔다고 말합니다 — 퇴근 전에 커밋하고 메모를 남기는 습관입니다. 덕분에 에이전트가 무슨 일이 있었는지 추측하며 시간을 버리지 않게 되었습니다.

이 가이드의 제안 — 코딩이 아닌 일에도 원문 실험은 웹 앱 개발에 맞춰져 있고, 원문은 이 교훈이 과학 연구·재무 모델링 같은 다른 긴 작업에도 "일부 또는 전부 적용될 것 같다"고 앞으로의 과제로 남겼습니다. 이 가이드는 회사 보고서·조사처럼 며칠 걸리는 일에도 같은 틀을 권합니다: 할 일 목록 한 파일 + 진행 기록 한 파일 + 세션 시작 때 둘을 읽게 하는 한 줄. 아래는 이 가이드가 만든 예시이며, 원문에는 이 파일의 정해진 양식이 없습니다.
# claude-progress.txt (예시 양식 — 원문에 정해진 양식 없음)
2026-11-10 세션 3
- 한 일: 3번 기능(로그인 화면) 끝, 브라우저로 직접 확인함 → feature_list 통과로 바꿈
- 커밋: "로그인 화면 추가"
- 다음: 4번 기능(비밀번호 찾기). 서버는 ./init.sh 로 켬
- 주의: 테스트 계정은 CLAUDE.local.md 에 있음

세션 시작 루틴 — 매번 같은 순서로 상태 파악

준비물이 갖춰지면, 모든 코딩 에이전트는 일을 시작하기 전에 정해진 순서로 "현재 위치"부터 확인하라는 지시를 받습니다. 아주 기본적인 단계도 있지만 그래도 도움이 됩니다. 원문은 이 덕분에 매 세션 "코드를 어떻게 시험하지?"를 알아내는 데 드는 토큰(AI 가 읽고 쓰는 글의 양을 세는 단위 — 비용·속도의 기준)을 아낀다고 말합니다.

1. 지금 어느 폴더인지 확인

pwd(지금 있는 폴더 위치를 보여 주는 명령)를 실행합니다. 원문 지시: "이 폴더 안의 파일만 고칠 수 있다."

2. 진행 기록과 git 로그 읽기

claude-progress.txt 와 git 기록(git log --oneline -20 — 최근 커밋 20개를 한 줄씩)을 읽어 최근에 무엇을 했는지 따라잡습니다.

3. 기능 목록에서 하나 고르기

feature_list.json 을 읽고 아직 안 된 것 중 가장 우선순위가 높은 기능 하나를 고릅니다.

4. 앱을 켜고 기본 동작부터 시험

init.sh 로 개발 서버를 켜고, 새 기능에 손대기 전에 기본 end-to-end 시험(사용자처럼 처음부터 끝까지 실제로 써 보는 시험)을 돌립니다. claude.ai 복제 예에서는 늘 새 채팅을 열고 메시지를 보내 답을 받아 봤습니다. 앱이 망가진 채 남겨져 있었다면 바로 고칩니다 — 그대로 새 기능을 시작하면 문제가 더 커지기 때문입니다.

5. 기능 하나 → 끝날 때 커밋과 기록

고른 기능 하나를 만들고 직접 시험한 뒤에만 통과로 바꿉니다. 세션을 끝낼 때 git 커밋과 진행 기록 갱신을 남깁니다. 이것이 다음 세션의 1~2단계가 읽을 노트가 됩니다.

원문은 실제 세션 첫머리가 대체로 이렇게 흘러간다고 보여 줍니다(아래 화면 흉내는 원문 대화를 옮기고 뜻을 단 것입니다).

세션 첫머리 — 원문 예

[Assistant] I'll start by getting my bearings and understanding the current state of the project.

뜻: 먼저 현재 위치와 프로젝트 상태부터 파악하겠습니다.

[Tool Use] <bash - pwd> · <read - claude-progress.txt> · <read - feature_list.json>

뜻: 폴더 확인 → 진행 기록 읽기 → 기능 목록 읽기

[Tool Use] <bash - git log --oneline -20>

뜻: 최근 작업 기록 보기

[Assistant] Now let me check if there's an init.sh script to restart the servers.

뜻: 서버를 다시 켤 init.sh 가 있는지 보고 개발 서버를 켭니다.

[Assistant] … verify that some fundamental features are still working.

뜻: 기본 기능이 아직 잘 되는지 확인한 뒤 → 다음 기능 작업 시작

이 가이드의 제안 — 시작 루틴을 지침 파일에 원문은 이 순서를 각 세션의 지시(프롬프트)로 주었습니다. Claude Code 에서는 매 세션 시작 때 읽히는 지침 파일 CLAUDE.md(3장)에 "세션을 시작하면 진행 기록과 git 로그를 먼저 읽는다" 같은 짧은 줄을 두면 같은 효과를 노릴 수 있습니다. 다만 지침 파일은 강제 설정이 아니라 맥락이므로, 반드시 지켜야 하는 확인은 9장 「반드시 막을 것」의 방법을 씁니다.

서브에이전트 결과는 파일로 — "전화 게임" 줄이기

여러 에이전트가 함께 일할 때도 인수인계가 생깁니다. 서브에이전트(메인 에이전트가 맡긴 일을 자기 컨텍스트에서 하고 결과만 돌려주는 도우미, 6장)가 찾아낸 것을 지휘 에이전트(일을 나누고 모으는 역할)에게 말로 전하고, 지휘 에이전트가 다시 정리해 전하면 — 말이 건너갈 때마다 내용이 조금씩 빠집니다. 원문(Anthropic 멀티 에이전트 연구 시스템)은 이것을 "전화 게임"(귓속말 전달 놀이)이라고 부릅니다.

결과는 파일로

서브에이전트가 도구로 결과를 바깥 저장소(파일)에 저장하고, 지휘 에이전트에게는 가벼운 참조만 돌려줍니다. 여러 단계를 거치며 정보가 새는 것을 막고, 큰 결과를 대화 기록으로 복사하는 토큰도 줄입니다. 코드·보고서·데이터 시각화처럼 모양이 정해진 결과물에 특히 잘 맞습니다.

계획은 메모리에

원문의 지휘 연구 에이전트는 먼저 접근 방법을 생각한 뒤 계획을 메모리에 저장합니다. 컨텍스트 창이 200,000 토큰을 넘으면 잘려 나가므로, 계획만은 꼭 남겨 두려는 것입니다.

단계가 끝나면 요약해 보관

대화가 수백 턴(주고받기 한 번)에 이르면, 끝난 작업 단계를 요약해 바깥 메모리에 저장하고 다음 일로 넘어갑니다. 한도가 다가오면 깨끗한 컨텍스트의 새 서브에이전트를 띄우고 신중하게 인수인계해 흐름을 잇습니다.

이 가이드의 제안 — 팀 공용 결과 폴더 세컨드 브레인 관점에서는, 팀원(서브에이전트·에이전트 팀원)이 결과를 넣는 공용 폴더 하나를 정해 두고 "결과는 이 폴더에 파일로 쓰고, 나에게는 파일 경로만 알려 달라"고 맡길 때 적어 주기를 권합니다. 폴더 이름(예: outputs/)은 이 가이드의 예시 이름입니다. 에이전트 팀이라면 두 팀원이 같은 파일을 고치면 덮어쓰기가 생기므로, 원문(agent-teams)대로 팀원마다 맡는 파일을 나눕니다.
한눈에 정리
  • 새 세션은 앞 세션을 기억하지 못합니다. 압축만으로는 부족하고, 파일로 남긴 인수인계 노트가 세션 사이의 다리입니다.
  • 첫 세션은 진행 기록(claude-progress.txt)·기능 목록(feature_list.json)·init.sh·첫 git 커밋을 준비합니다.
  • 기능 목록은 전부 "실패"로 시작하고, 통과 여부 칸만 바꾸며, 끝까지 확인한 뒤에만 통과로 바꿉니다.
  • 매 세션: 폴더 확인 → 기록·git 로그 읽기 → 기능 하나 고르기 → 앱을 켜고 기본 시험 → 일 → 커밋과 기록 갱신.
  • 메모리 도구도 같은 패턴(첫 세션 준비 → 매 세션 읽기 → 끝날 때 갱신)이며, "언제든 끊긴다고 가정하라"가 핵심입니다.
  • 여러 에이전트는 결과를 파일로 남기고 경로만 주고받아 "전화 게임"의 손실을 줄입니다.

CHAPTER 08

바깥 지식 잇기 — MCP 와 Claude 프로젝트

팀의 지식은 폴더 안 파일에만 있지 않습니다. 일정표·문서 도구·이슈 관리·데이터베이스에도 흩어져 있지요. 이 장은 에이전트가 그런 바깥 도구를 직접 읽고 쓰게 잇는 표준 MCP와, 코딩을 하지 않는 팀이 지식·지침을 한곳에 묶어 함께 쓰는 Claude 프로젝트를 다룹니다.

MCP 란 — AI 앱용 USB-C 포트

MCP(Model Context Protocol — AI 앱을 외부 도구·데이터에 잇는 표준 연결 방식)는 AI 애플리케이션을 바깥 시스템에 연결하는 오픈소스 표준입니다. Claude 나 ChatGPT 같은 AI 앱이 MCP 로 데이터(로컬 파일·데이터베이스), 도구(검색 엔진·계산기), 워크플로(일의 정해진 순서 — 원문 예: 전문 프롬프트)에 연결해 필요한 정보에 닿고 일을 해낼 수 있습니다.

원문의 비유 MCP 는 AI 앱용 USB-C 포트입니다. USB-C 가 여러 전자 기기를 한 가지 방식으로 잇게 해 주듯, MCP 는 AI 앱을 바깥 시스템에 한 가지 방식으로 잇습니다. 한 번 만들면 MCP 를 지원하는 여러 앱(Claude, ChatGPT, Visual Studio Code, Cursor 등)에서 두루 쓸 수 있습니다.

언제 연결하나. Claude Code 문서의 기준은 간단합니다: 이슈 관리 도구나 모니터링 화면 같은 다른 도구의 내용을 채팅에 복사해 붙이고 있다면 그 도구의 서버를 연결할 때입니다. 연결하면 Claude 가 내가 붙여 넣은 조각이 아니라 그 시스템을 직접 읽고 다룹니다.

이 가이드의 제안 — 세컨드 브레인과 MCP 세컨드 브레인의 파일(목표·지침·노트)은 "팀이 정리해 둔 지식"이고, MCP 는 "살아 움직이는 바깥 지식"(오늘의 일정, 최신 이슈, 데이터베이스)을 잇는 통로입니다. 파일에는 어떤 도구에서 무엇을 찾는지만 적고, 바뀌는 내용 자체는 MCP 로 그때그때 읽게 하면 노트가 낡지 않습니다(필요할 때 읽기 — 1장).
연결 전에 믿을 수 있는지 확인 원문 경고: 연결하는 서버마다 믿을 수 있는지 먼저 확인하세요. 바깥 내용을 가져오는 서버는 프롬프트 주입(가져온 글 속에 숨은 지시가 에이전트를 엉뚱하게 움직이게 하는 공격) 위험에 노출될 수 있습니다.

MCP 서버를 둘 범위 — 나만 · 이 프로젝트 팀 · 내 모든 프로젝트

Claude Code 에서 MCP 서버는 세 가지 범위(scope — 그 설정이 어디까지 적용되고 누구와 나눠지는지) 중 하나에 둡니다. 범위가 정하는 것은 두 가지입니다: 어느 프로젝트에서 켜지나, 그리고 팀과 나눠지나.

범위켜지는 곳팀과 공유저장 위치쓰기 좋은 곳(원문)
로컬 (local, 기본값)지금 프로젝트만아니오~/.claude.json개인 개발용 서버, 실험 설정, 버전 관리에 넣고 싶지 않은 비밀 정보가 든 서버
프로젝트 (project)지금 프로젝트만예 — 버전 관리로프로젝트 맨 위 폴더의 .mcp.json팀이 함께 쓰는 도구·서비스

겹칠 때의 순서. 같은 서버가 여러 곳에 정의되어 있으면 Claude Code 는 한 번만 연결하고, 가장 우선순위가 높은 곳의 정의 전체를 씁니다(범위끼리 칸을 섞지 않음). 순서는 로컬 → 프로젝트 → 사용자 → 플러그인이 준 서버 → claude.ai 커넥터이고, 조직이 관리 설정(managedMcpServers)으로 제공한 서버는 이 모두보다 위입니다.

헷갈리기 쉬운 이름 MCP 의 "로컬 범위"는 일반 설정의 "로컬 설정"과 다릅니다. MCP 로컬 범위 서버는 홈 폴더의 ~/.claude.json 에 저장되고, 일반 로컬 설정은 프로젝트 폴더의 .claude/settings.local.json 에 있습니다.

Claude 프로젝트 — 코딩 안 하는 팀의 공용 지식 공간

터미널이나 저장소를 쓰지 않는 팀이라면 claude.ai 의 프로젝트가 세컨드 브레인 역할을 합니다. 프로젝트는 자기만의 대화 기록과 지식 창고를 가진 독립된 작업 공간입니다. 프로젝트마다 문서를 올리고, 맥락을 주고, 그 주제에 집중한 대화를 Claude 와 나눕니다. 무료 계정을 포함한 모든 사용자가 쓸 수 있고, 무료 사용자는 프로젝트를 최대 5개까지 만듭니다.

관련 문서·글·코드·파일을 프로젝트의 지식 창고에 올리면, Claude 가 그 프로젝트 안의 각 대화에서 맥락과 배경을 이해하는 데 씁니다.

개인 팀과 회사 팀 — 범위 · 보안 · 관리

이 가이드가 처음에 던진 질문으로 돌아옵니다: 개인 일을 하는 에이전트 팀과 회사 일을 하는 에이전트 팀을 따로 꾸리되, 각 팀 안에서는 모든 에이전트가 같은 목표와 맥락을 갖게 하려면? 열쇠는 앞 장들의 파일을 어느 범위에 두느냐입니다. 그리고 반드시 지켜야 할 규칙·비밀 정보·오래된 기억을 어떻게 관리하는지도 다룹니다.

이 가이드의 제안 — 나누는 기준 한 줄 개인 팀 = 사용자 범위 + 개인용 폴더(저장소) 하나, 회사 팀 = 회사 저장소의 프로젝트 범위 + 조직 범위, 그리고 회사 일 속 "나만의 메모"는 로컬 범위. 주의할 점이 하나 있습니다: 사용자 범위(~/.claude/)는 원문대로 "내 모든 프로젝트"에 읽히므로, 회사 저장소에서 일할 때도 읽힙니다. 그래서 사용자 범위에는 어디서 읽혀도 괜찮은 공통 선호만 두고, 개인 팀의 목표·개인 일정 같은 것은 개인용 폴더의 프로젝트 지침에 둡니다.

개인 팀 구성 예 — 사용자 범위 + 개인용 폴더

개인 일을 하는 에이전트 팀의 세컨드 브레인을 이 가이드는 이렇게 꾸리기를 제안합니다. 폴더 이름 my-brain/(활용편과 같은 예시), 파일 이름 GOAL.md 와 PARA 폴더 이름은 이 가이드의 예시 이름이고, 나머지 경로(~/.claude/…, CLAUDE.md, .claude/agents/, claude-progress.txt 등)는 원문 이름입니다.

1. 사용자 범위에 공통 선호

~/.claude/CLAUDE.md 는 원문 기준 "모든 프로젝트에 쓰이는 개인 선호"(코드 스타일 선호, 개인 도구 단축 등) 자리입니다. 주제별로 나누려면 ~/.claude/rules/ 에 preferences.md·workflows.md 처럼 둡니다. 원문은 사용자 규칙이 프로젝트 규칙보다 먼저 읽히고, 둘이 충돌하면 어느 쪽을 따를지 모르니 일관되게 유지하라고 합니다.

2. 개인용 폴더 하나를 개인 팀의 본부로

폴더 하나를 만들고 그 안 CLAUDE.md 에 개인 팀의 목표 파일을 @GOAL.md 처럼 불러오게(import) 적습니다. 불러온 파일은 그 CLAUDE.md 와 함께 컨텍스트에 들어갑니다. 지식 창고는 PARA(2장)로 정리합니다.

3. 역할을 정의하고 팀을 띄우기

개인 팀의 역할(예: 조사 담당, 일정 정리 담당)을 그 폴더의 .claude/agents/ 에 두거나, 여러 개인 폴더에서 쓰려면 ~/.claude/agents/ 에 둡니다. 에이전트 팀의 팀원은 만들어질 때 일반 세션과 같은 CLAUDE.md·MCP 서버·스킬을 불러오므로, 그 폴더에서 띄운 팀원 모두가 같은 목표를 읽습니다. 리더의 대화 기록은 넘어가지 않으니, 생성 지시문(spawn prompt — 리더가 팀원을 만들 때 주는 첫 지시)에 그 일만의 맥락을 담습니다(6장).

4. 바깥 도구는 사용자·로컬 범위 MCP

개인 일정·메모 앱처럼 나만 쓰는 도구는 MCP 사용자 범위(모든 프로젝트) 또는 로컬 범위(이 폴더만)에 둡니다. 원문은 버전 관리에 넣고 싶지 않은 비밀 정보가 든 서버에 로컬 범위를 권합니다.

5. 긴 일은 인수인계 노트로

며칠 걸리는 개인 프로젝트는 진행 기록 파일과 할 일 목록을 두고, 세션을 시작할 때 읽게 합니다(7장).

회사 팀 구성 예 — 회사 저장소 + 조직 범위

회사 일을 하는 팀은 세컨드 브레인을 모두가 받는 곳, 즉 회사 저장소(프로젝트 범위)에 둡니다. 원문은 프로젝트 지침을 "버전 관리로 팀원과 공유하는 지침"(프로젝트 구조, 코딩 표준, 공통 작업 방식)이라고 설명합니다. 아래 구성은 이 가이드의 제안이고, 경로와 기능은 원문 그대로입니다.

에이전트 팀의 권한 — 팀원은 내 대신 승인할 수 없다

원문 보안 규칙 에이전트끼리 메시지를 보내면, 받는 쪽은 그 메시지가 사용자가 아니라 다른 Claude 세션에서 왔다고 전달받습니다. 팀원은 권한 요청을 내 대신 승인하거나 동의를 대신할 수 없고, 거절당한 행동을 다른 팀원에게 넘겨 검사를 피할 수도 없습니다. 팀원의 권한 요청은 리더 세션에 뜨니, 거기서 직접 승인합니다.
  • 새 팀원은 리더의 권한 모드로 시작합니다(bypassPermissions 포함). 만들 때 팀원마다 다른 모드를 줄 수 없습니다 — 리더를 위험한 모드로 띄우면 팀원도 같다는 뜻입니다.
  • 권한 요청이 너무 자주 리더에게 올라오면, 팀원을 띄우기 전에 자주 쓰는 작업을 권한 설정에서 미리 허용해 둡니다.
  • 팀의 품질 관문은 훅으로: TeammateIdle(팀원이 쉬려 할 때), TaskCreated(작업이 만들어질 때), TaskCompleted(작업이 완료 표시될 때). 훅 명령이 종료 코드 2(명령이 끝나며 돌려주는 숫자 — 2는 “막음” 신호)로 끝나면 그 동작을 막고 되돌려 보낼 수 있습니다.
강제 장치는 적게 (원문) 어느 범위든 강제 목록은 작게 유지하세요. 훅과 deny 규칙은 가끔 엉뚱할 때도 작동하고, 누군가 하나하나 관리해야 합니다. 원문은 "40개쯤 되었다면 대부분은 Claude 가 스스로 판단해도 될 선호일 것"이라고 말합니다. 반대로 선호일 뿐인 것에 훅을 걸었다면 지우고 Claude 에게 맡깁니다.
